# 2. System Architecture Overview

VeriProc is structured around two primary concerns: a **backend control plane** that manages triggers, work orders, and persistent run state; and one or more **execution layers** that run the actual science algorithms. A shared filesystem carries all data artefacts; the database carries all control state. This clean separation allows execution backends to be swapped without touching the API or workflow definitions.

A key design choice distinguishes VeriProc from S4P: there are **no permanently running station processes**. Each work order spawns a fresh, ephemeral SLURM job in its own container. The backend tracks that job to completion, then evaluates the station's trigger rules against the produced outputs to decide whether to create downstream work orders.

## High-Level Components

| Component | Role | Technology |
|---|---|---|
| **VeriProc Backend** | Receives triggers, generates work orders, dispatches to executor, manages run lifecycle, serves REST API | Python / FastAPI; Postgres or SQLite (config switch); YAML configs |
| **State Store** | Durable storage for run and station state; indexed for fast API queries | SQLite (`file://`) in development; Postgres (~10 tables) in production |
| **Execution Layer** | Spawns one ephemeral job per work order (no persistent runner); executes the station `command` inside a dedicated container; backend tracks job state to completion | SLURM (default); adapter interface for K8s / HTCondor |
| **Shared Storage** | Holds product/aux source data, per-run working roots (symlinked inputs, work order, logs, outputs) | NFSv4 / AWS EFS; working root path: `<working_root_base>/<station_id>/<run_id>/` |
| **Triggers** | Watches for new data and notifies the backend | Inotify (NFS) / S3 event polling; configurable regex patterns |
| **Client Frontends** | Submit work orders and query status via REST API | External; any HTTP client |

## Station and Work Order Examples

Stations are declared in a single YAML configuration file that specifies resource requirements, the container image, and the command template for each processing step.

**`scene-station.yaml`**

```yaml
station_id: SCENE-L2
resources:
    cpu: 8
    mem_gb: 32
exec_mode: apptainer
image: /shared/images/scene-l2.sif
command: "scenel2-proc --workorder {workorder}"
workorder_template: conf/workorder-scenel2.yml
triggers: 
    - type: dir_poll
      file: CO2_1A_GEO______
      folder: /custom/folder/to/look/at
      period: 5m
    - type: upstream
      station_id: SCENE-L1

product_folders:
    - {rolling_archive}
    - /path/to/static/products

aux_folders:
    - {rolling_archive}
    - /path/to/static/aux

inputs:
  products:
    - file: CO2_1A_GEO______
      margins: [0, 0]
    - file: NO2_1B_RAD______
      margins: [0, 0]
  aux:
    - file: AX_____PREO___AX
      mandatory: False
      satid_strict: True
    - file: SCE_2__CNF____AX
    - file: SCE_2__CAMF___AX
      margins: [7200,  7200]
    
outputs:
  - file: output_csm.nc
    mandatory: True
  - file: output_eng.nc
    mandatory: False
```

The backend creates a dedicated `working_root` for each run, symlinks all resolved inputs into its `input/` subdirectory, and writes the populated work order file there. All paths in the work order point inside the working root.

**`workorder-scenel2.yaml`** *(written to `<working_root>/workorder.yaml`)*

```yaml
station_id: SCENE-L2
order:
  start: "2025-07-03T11:15:39Z"
  end: "2025-07-03T11:30:00Z"
facility:
  acquisition_station: Svalbard
  processing_station: EUM
  environment: OPERATIONAL
  test: False
log_level: DEBUG
dyn_params:
  mode: NOMINAL
  CpuCores: 8
temporary_folder: ./temp
inputs:
  - file_type: CO2_1A_GEO______
    path: ./input/CO2_1A_GEO______ON_20250703T111539.nc
  - file_type: NO2_1B_RAD______
    path: ./input/NO2_1B_RAD______ON_20250703T111539.nc
  - file_type: SCE_2__CNF____AX
    path: ./input/SCE_2__CNF____AX_20250101T000000.nc

outputs:
  - file_type: SCE_2__CSM______
    directory: ./output
  - file_type: SCE_2__ENG____AX
    directory: ./output
```

The resulting working root layout on shared storage:

```
<working_root_base>/SCENE-L2/abc123/
  workorder.yaml          ← populated from workorder_template
  input/
    CO2_1A_GEO______ON_20250703T111539.nc  → symlink to source
    NO2_1B_RAD______ON_20250703T111539.nc  → symlink to source
    SCE_2__CNF____AX_20250101T000000.nc    → symlink to source
  output/
    SCE_2__CSM______ON_20250703T111539.nc  ← written by algorithm
  logs/
    job.stdout
    job.stderr
  temp/
```

## Main Data and Control Flow

1. **Trigger** — A file matching a station's trigger pattern is detected (via `dir_poll` scan or upstream station completion); the backend is notified with the triggering file path.
2. **Deduplication check** — The backend looks up the triggering product file path in the processed-file registry. If it has already been successfully processed by this station, the event is silently discarded. Processing continues only for genuinely new inputs or when forced via the API.
3. **Input resolution** — The backend searches `product_folders` in declared order to locate all required product files matching the station's patterns and temporal margins. It then searches `aux_folders` in order for auxiliary files. Missing mandatory inputs abort the run at this stage.
4. **Working root setup** — A unique working root directory is created at `<working_root_base>/<station_id>/<run_id>/`. All resolved input files are symlinked into its `input/` subdirectory. Output and log subdirectories are created. No source files are copied.
5. **Work order creation** — The station's `workorder_template` is pre-filled with the run's resolved values (input paths relative to working root, output directories, timing bounds, facility metadata) and written to `<working_root>/workorder.yaml`. A `pending` run record is inserted into the database.
6. **Dispatch** — The backend submits a single `sbatch` job with the working root as its working directory. The job starts a fresh container and invokes the station's `command` with the work order path (e.g. `sbatch --cpus-per-task=8 --mem=32G --chdir=<working_root> apptainer exec scene-l2.sif scenel2-proc --workorder workorder.yaml`). The DB record is updated to `dispatched`. The container exits when the algorithm finishes — no long-lived process remains.
7. **Tracking** — The backend periodically polls `sacct` for job state. No in-band callback from the job is required. Stdout/stderr are captured to `<working_root>/logs/`.
8. **Finalisation** — On job completion the backend validates mandatory outputs in `<working_root>/output/`, registers the input product files in the processed-file registry, and transitions the run to `complete` or `failed` in the database.
9. **Downstream chaining** — On success, the backend evaluates the station's `triggers` rules against the newly produced output files. Any rule that matches causes a new work order to be created for the downstream station, restarting the cycle from step 2.
10. **Query** — Clients call the REST API at any point; the backend reads from the DB and returns the current run state, working root path, logs, and artifact paths.

```
Trigger (dir_poll / upstream)
        |
        v
  deduplication check → already processed? discard (or force override)
        |
        v
  resolve inputs: search product_folders → aux_folders (in order)
        |
        v
  create working_root/  →  symlink inputs into input/
        |
        v
  fill workorder_template → write working_root/workorder.yaml → DB insert (pending)
        |
        v
  sbatch --chdir=working_root → ephemeral container (command --workorder workorder.yaml)
        |
   poll sacct  →  logs → working_root/logs/
        |
        v
  validate working_root/output/ → register inputs → DB update (complete / failed)
        |
        v
  evaluate downstream triggers → new work orders (if matched)
        |
        v
  Status API  ←  client query (DB read)
```

Fault tolerance relies on DB and filesystem idempotency: work orders are created only once per `run_id` (unique DB constraint), the processed-file registry prevents duplicate dispatch on restart, and output validation is re-run on recovery to correctly classify any jobs that completed while the backend was down.
