# 2. System Architecture Overview

VeriProc is structured around three layers: a **backend control plane** that manages tasks and persistent state; a **job order generation layer** that translates orchestrator-level tasks into station-level execution descriptors; and one or more **execution layers** that run the actual science algorithms. A shared filesystem carries all data artefacts; the database carries all control state. This clean separation ensures that station algorithms are fully isolated from the orchestration infrastructure — they see only a self-contained job order — and that execution backends can be swapped without touching the API or workflow definitions.

A key design choice distinguishes VeriProc from S4P: there are **no permanently running station processes**. Each task spawns a fresh, ephemeral SLURM job in its own container. The backend tracks that job to completion, then creates downstream tasks based on the algorithm's output descriptors or the station's `downstream` configuration.

## High-Level Components

| Component | Role | Technology |
|---|---|---|
| **VeriProc Backend** | Receives tasks, generates job orders, dispatches to executor, manages run lifecycle, creates downstream tasks, serves REST API | Python / FastAPI; Postgres or SQLite (config switch); YAML configs |
| **State Store** | Durable storage for task, run, and station state; indexed for fast API queries and lineage traversal | SQLite (`file://`) in development; Postgres (~10 tables) in production |
| **Execution Layer** | Spawns one ephemeral job per task (no persistent runner); executes the station `command` inside a dedicated container; backend tracks job state to completion | SLURM (default); adapter interface for K8s / HTCondor |
| **Shared Storage** | Holds product/aux source data, per-task working roots (symlinked inputs, job order, logs, outputs) | NFSv4 / AWS EFS; working root path: `<working_root_base>/<station_id>/<task_id>/` |
| **Client Frontends** | Submit tasks and query status via REST API | External; any HTTP client |

## Station Configuration, Tasks, and Job Orders

VeriProc separates orchestration concerns into two layers:

- **Task** — the orchestrator-level token that identifies *what* to process and *where*. A task carries the destination station, the time window, and a history log of the stations it has already visited. Tasks travel between stations; they are the unit of routing and provenance.
- **Job order** — the station-level execution descriptor generated by the framework from the incoming task and the station config. It contains resolved input/output paths, execution parameters, and everything the algorithm needs to run. The algorithm sees *only* the job order — it has no knowledge of tasks, pipelines, or VeriProc internals.

### Station Config

Stations are declared in YAML configuration files. A station config specifies the execution environment, input/output patterns, and downstream routing.

**`scene-station.yaml`**

```yaml
station_id: "SCENE L2"
proc_type: sce2
resources:
    cpu: 8
    mem_gb: 32
exec_mode: apptainer
image: /shared/images/scene-l2.sif
command: "scenel2-proc --joborder {joborder}"

downstream:
    - ghgS
    - arch

input_folders:
    - {rolling_archive}
    - /path/to/static/aux

inputs:
    - file: CO2_1A_GEO______
      type: product
      margins: [0, 0]
    - file: NO2_1B_RAD______
      type: product
      margins: [0, 0]
    - file: AX_____PREO___AX
      type: aux
      mandatory: False
      satid_strict: True
    - file: SCE_2__CNF____AX
      type: aux
    - file: SCE_2__CAMF___AX
      type: aux
      margins: [7200,  7200]
    
outputs:
  - file: output_csm.nc
    mandatory: True
  - file: output_eng.nc
    mandatory: False
```

Note: there is no `workorder_template` field. The framework generates the job order automatically from the station config and the incoming task.

### Task

A task is submitted via the API or created by the framework at the end of a station run. It identifies the target station (via the `proc_type` prefix), the time window, and the processing history.

**Example task** *(submitted via API or created by the framework)*

```yaml
id: sce2_123456
start: 20250703T111245.630
end: 20250703T111250.630

history:
    - id: inge_123454
      time: 20260310T111210.550
    - id: sce1_123455
      time: 20260310T111215.550
```

The `id` field is a compound identifier: a 4-letter `proc_type` prefix identifying the destination station, an underscore, and a globally unique numeric sequence. The `history` section carries the lineage — every station the data has already passed through, with the timestamp of completion. This enables provenance tracking and supports fractional processing patterns where data is split, processed in parallel, and reassembled.

### Job Order

The framework generates a job order by combining the task's time window with the station config's input/output definitions and the resolved file paths. The algorithm receives it as its sole interface to the system.

**`joborder.yaml`** *(written to `<working_root>/joborder.yaml`)*

```yaml
station_id: SCENE-L2
order:
  start: "2025-07-03T11:12:45.630Z"
  end: "2025-07-03T11:12:50.630Z"
facility:
  acquisition_station: Svalbard
  processing_station: EUM
  environment: OPERATIONAL
  test: False
log_level: DEBUG
dyn_params:
  mode: NOMINAL
  CpuCores: 8
temporary_folder: ./temp
inputs:
  - file_type: CO2_1A_GEO______
    path: ./input/CO2_1A_GEO______ON_20250703T111245.nc
  - file_type: NO2_1B_RAD______
    path: ./input/NO2_1B_RAD______ON_20250703T111245.nc
  - file_type: SCE_2__CNF____AX
    path: ./input/SCE_2__CNF____AX_20250101T000000.nc

outputs:
  - file_type: SCE_2__CSM______
    directory: ./output
  - file_type: SCE_2__ENG____AX
    directory: ./output
```

The `order.start` and `order.end` values are taken directly from the task. The algorithm does not know where these times came from or what happens next — it simply processes the requested window.

### Task Output Descriptor

When the algorithm finishes, it may write a **`task-out.yaml`** file into the working root describing the downstream tasks to create. This gives the algorithm full control over routing — essential for fractional processing where one job may produce multiple tasks (e.g. splitting a 3-minute granule into 10-second units), or aggregation stations that must emit a single recombined task.

**`task-out.yaml`** *(written by the algorithm, read by the framework)*

```yaml
tasks:
  - station: ghgS
    start: 20250703T111245.630
    end: 20250703T111250.630
  - station: arch
    start: 20250703T111245.630
    end: 20250703T111250.630
```

If the algorithm does not produce a `task-out.yaml`, the framework falls back to the station config's `downstream` list and creates one task per downstream station using the same time window as the completed task. The framework appends the current task to the `history` of each downstream task automatically.

### Working Root

The backend creates a dedicated `working_root` for each task, symlinks all resolved inputs into its `input/` subdirectory, and writes the generated job order there. All paths in the job order point inside the working root.

The resulting working root layout on shared storage:

```
<working_root_base>/SCENE-L2/sce2_123456/
  joborder.yaml           ← generated by framework from station config + task
  input/
    CO2_1A_GEO______ON_20250703T111245.nc  → symlink to source
    NO2_1B_RAD______ON_20250703T111245.nc  → symlink to source
    SCE_2__CNF____AX_20250101T000000.nc    → symlink to source
  output/
    SCE_2__CSM______ON_20250703T111245.nc  ← written by algorithm
  task-out.yaml           ← written by algorithm (optional)
  logs/
    job.stdout
    job.stderr
  temp/
```

## Main Data and Control Flow

1. **Task arrival** — A task arrives via the REST API (external submission) or is created by the framework after a preceding station completes successfully. The task identifies the destination station via its `proc_type` prefix, the time window, and the processing history.
2. **Deduplication check** — The backend checks whether this task's time window has already been processed by the target station. If so, the task is discarded unless `force` is set via the API.
3. **Input resolution** — The backend searches the station's `input_folders` in declared order to locate all required product and auxiliary files matching the station's patterns and temporal margins. The task's `start`/`end` times are used as the temporal anchor. Missing mandatory inputs abort the task at this stage.
4. **Working root setup** — A unique working root directory is created at `<working_root_base>/<station_id>/<task_id>/`. All resolved input files are symlinked into its `input/` subdirectory. Output, log, and temp subdirectories are created. No source files are copied.
5. **Job order generation** — The framework combines the task's time window with the station config to produce a fully resolved `joborder.yaml`, written to the working root. This replaces the old template-based approach — no separate template file is needed. A `pending` run record is inserted into the database, linking the task ID to the run.
6. **Dispatch** — The backend submits a single `sbatch` job with the working root as its working directory. The job starts a fresh container and invokes the station's `command` with the job order path (e.g. `sbatch --cpus-per-task=8 --mem=32G --chdir=<working_root> apptainer exec scene-l2.sif scenel2-proc --joborder joborder.yaml`). The DB record is updated to `dispatched`. The container exits when the algorithm finishes — no long-lived process remains.
7. **Tracking** — The backend periodically polls `sacct` for job state. No in-band callback from the job is required. Stdout/stderr are captured to `<working_root>/logs/`.
8. **Finalisation** — On job completion the backend validates mandatory outputs in `<working_root>/output/` and transitions the run to `complete` or `failed` in the database.
9. **Downstream task creation** — On success, the framework checks whether the algorithm wrote a `task-out.yaml` in the working root. If present, the framework creates one downstream task per entry, appending the current task to each new task's `history`. If absent, the framework falls back to the station config's `downstream` list and creates tasks with the same time window. Each new task re-enters the flow at step 2.
10. **Query** — Clients call the REST API at any point; the backend reads from the DB and returns the current task state, run state, working root path, logs, and artifact paths.

```
Task arrives (API / upstream completion)
        |
        v
  deduplication check → already processed? discard (or force override)
        |
        v
  resolve inputs: search input_folders (in order), anchor on task start/end
        |
        v
  create working_root/  →  symlink inputs into input/
        |
        v
  generate joborder.yaml from station config + task → DB insert (pending)
        |
        v
  sbatch --chdir=working_root → ephemeral container (command --joborder joborder.yaml)
        |
   poll sacct  →  logs → working_root/logs/
        |
        v
  validate working_root/output/ → DB update (complete / failed)
        |
        v
  read task-out.yaml (or use station downstream list) → create downstream tasks
        |
        v
  Status API  ←  client query (DB read)
```

Fault tolerance relies on DB and filesystem idempotency: tasks are created only once per `task_id` (unique DB constraint), the deduplication registry prevents duplicate dispatch on restart, and output validation is re-run on recovery to correctly classify any jobs that completed while the backend was down.

## Fractional Processing

Some processing chains require **fractional processing**: a larger input granule (e.g. 3 minutes of data) is split into smaller processing units (e.g. 10-second granules), processed in parallel, and then aggregated back.

VeriProc supports this pattern through the task and `task-out.yaml` mechanism:

1. **Splitting** — A splitter station receives a task with a 3-minute window. Its algorithm writes a `task-out.yaml` containing N tasks, each with a 10-second sub-window, all targeting the downstream processing station. Each sub-task inherits the history of the parent task.
2. **Parallel processing** — The N sub-tasks are independent and are dispatched concurrently by the framework (subject to executor capacity). Each runs in its own working root with its own job order.
3. **Aggregation** — An aggregation station is triggered when all sub-tasks for a given parent window have completed. It receives a task covering the original 3-minute window, processes the collected sub-outputs, and emits a single consolidated output.

The task history carries the splitter's task ID, so the aggregator can trace lineage back through the split point without needing to know about the individual sub-tasks.
