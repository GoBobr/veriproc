# 1. Introduction and Goals

VeriProc is a lightweight orchestration system for satellite Earth Observation (EO) processing pipelines. It is inspired by NASA's S4P model of simple, file-driven stations, but it replaces station daemons, token files, and loosely defined control flow with a REST API, declarative YAML configuration, explicit persistence, and ephemeral executor jobs.

The system is intended for cloud and hybrid HPC environments in which a shared filesystem is available to both the control plane and the compute backend. VeriProc separates orchestration from science code: the backend manages routing, identity, persistence, deduplication, rolling-archive interaction, and recovery, while station algorithms receive only a generated job order and produce artifacts inside an isolated working directory.

This document is a normative specification. It is intended to drive implementation, testing, and operations.

## 1.1 Normative Language

The key words **Must**, **Must not**, **Should**, **Should not**, and **May** are to be interpreted as normative requirement terms:

- **Must / Must not** define mandatory behavior.
- **Should / Should not** define recommended behavior that may be relaxed only with documented justification.
- **May** defines optional behavior or an allowed extension.

Unless explicitly marked informative, statements in this specification are normative.

## 1.2 System Intent

VeriProc must provide a control plane for station-based EO processing with the following architectural properties:

- A **task** must represent a request to process a defined time window at a destination station.
- A **job order** must be the only orchestration-visible interface presented to the station algorithm.
- A **run** must represent a single execution attempt for a task.
- A **job** must represent the concrete scheduler submission that carries out a run.
- A **working root** must contain the durable execution record for a run: generated job order, resolved inputs, outputs, task output descriptor, and logs.
- A **rolling archive** must represent a configured read-write data directory used for current input selection and, where enabled by station policy, for publishing selected outputs back to short-term operational storage.
- The backend must remain authoritative for control state; the shared filesystem must remain authoritative for artifact bytes.

VeriProc must not require permanently running station worker processes. Each execution must be an isolated, short-lived scheduler job whose lifetime matches one run.

## 1.3 Design Goals

The system must satisfy the following goals.

### 1.3.1 Deterministic orchestration

- The backend must transform a validated task plus a specific station revision into a deterministic job order.
- The backend must persist the resolved execution context needed to reproduce or audit a completed run.
- The backend must distinguish between routing identity, execution identity, and processing identity.

### 1.3.2 Strong execution isolation

- Each run must execute in a dedicated working root.
- All resolved inputs, whether regular files or directories, must be exposed to the algorithm through symlinks under `input/`.
- The algorithm must write outputs, logs, and optional downstream routing descriptors only within the working root.
- The algorithm must not need to know about the REST API, task graph, scheduler protocol, or state store.

### 1.3.3 Durable and recoverable state

- The system must persist enough state to recover after backend restart without duplicating canonical work.
- All externally visible operations that may be retried must be defined to be idempotent or detect duplicates safely.
- Recovery rules must cover failures between filesystem actions, database writes, and scheduler submissions.

### 1.3.4 Scientifically safe deduplication

- Deduplication must not rely only on station plus time window.
- The system must define a **processing fingerprint** that captures the scientifically relevant execution context.
- Two completed runs may be considered duplicates only if their processing fingerprints are equal.
- Reprocessing with changed inputs, changed auxiliary files, changed station revision, changed algorithm image, or other output-affecting context must produce a distinct fingerprint.

### 1.3.5 Explicit provenance

- The system must preserve both a human-readable routing history and machine-queryable provenance links.
- It must be possible to determine which run produced an artifact.
- It must be possible to determine which resolved inputs were consumed by a run.
- It must be possible to determine parent-child relationships between upstream and downstream tasks.

### 1.3.6 Fractional processing support

- The system must support fan-out and fan-in workflows in which a wide time window is split into sub-windows, processed independently, and aggregated.
- Split processing must have explicit grouping semantics so that completion, retry, timeout, and duplicate handling are well defined.

### 1.3.7 Executor portability

- The control-plane contract must be stable across execution backends.
- SLURM is the primary distributed executor family for the MVP. The preferred distributed executor names are `slurm-native`, where the station executable runs directly on the allocated SLURM node, and `slurm-docker`, where the station executable runs inside a Docker container launched by the SLURM node wrapper.
- Additional executors such as Kubernetes or HTCondor may be supported through adapters without changing task, run, or job order semantics.

### 1.3.8 Controlled customization

- The default working-root and job-order generation behavior must be well defined and sufficient for the MVP.
- The default working-root generation behavior must support declarative relative path templates under the configured working-root base, including nested and flat layouts.
- A deployment may provide user-defined working-root generation and job-order generation modules through top-level instance configuration.
- Custom generators must preserve the normative contracts of this specification: deterministic output, working-root containment, manifest persistence, idempotent recovery, and schema validation.
- Custom generators must be versioned or fingerprinted so that their effect on execution context can be audited and included in processing fingerprints when output-affecting.

### 1.3.9 Rolling archive support

- The system must support one or more configured rolling archive directories.
- Rolling archives must be declared in the top-level VeriProc instance configuration and referenced from station configurations by identifier.
- Each rolling archive definition must include a filesystem location and a retention policy.
- Stations may use rolling archives as ordered input sources and may publish validated outputs back into selected rolling archives according to station policy.

## 1.4 Required Capabilities

The MVP system must implement the following capabilities.

### 1.4.1 Task intake and validation

- The REST API must accept task submissions in YAML or an equivalent structured payload.
- A submitted task must be validated before it is persisted or dispatched.
- Task submission must support an idempotency mechanism so that client retries do not create unintended duplicates.

### 1.4.2 Job order generation

- The backend must render the station's configured joborder contract from the task, the selected station revision, deployment configuration, resolved station context, and resolved input manifest. The system-default renderer must support `yaml`, `toml`, `json`, and `none`; `none` means no joborder file is generated.
- The backend must support a system-default job-order generator and may support a deployment-configured custom generator module.
- When a joborder file is generated, its schema version must be explicit under the generated `veriproc_meta` group.
- The generated job order, or the explicit `none` joborder contract together with the resolved manifest and execution arguments, must freeze the execution context for that run before dispatch.
- In the default job-order model, station-provided fields such as `log_level` and `dyn_params` must appear at the root of the document when declared through `joborder.include` or generator policy.
- In the default job-order model, VeriProc-owned audit and identity fields such as schema version, joborder identifier, station identity, task identity, retry index, run reference, manifest reference, and generator identity must appear under `veriproc_meta` rather than at the root. Workload-facing fields such as `order`, `inputs`, and `outputs` remain at the root.
- `dyn_params`, when present, must represent algorithm-facing variable parameters derived from station configuration and run context.
- The generated job order should keep inputs as a single flat list when `file_type` is globally unique for the station's declared inputs.
- Each input entry in that flat list may resolve to one filesystem object or to multiple filesystem objects for the same `file_type`. A resolved object may be a regular file or a directory whose entry name satisfies the same naming contract.

### 1.4.3 Input resolution and manifest persistence

- The top-level instance configuration must define ordered `product_categories`, each with a category name and an ordered folder list.
- Station configuration may override category folder lists through `rolling_folders` without redefining the global category model.
- Each declared station input must reference a category name and a `file_type`; category names determine the folder list to scan, while `file_type` identifies the logical input.
- Category folder order represents user priority. The first folder has the highest priority, but input resolution must scan every configured folder before applying the final per-group winner rule.
- Category folder lists may reference configured rolling archives by identifier.
- The backend must persist a resolved input manifest for every run, including enough metadata to support audit and replay of the classical matching decision: effective filename pattern, parsed filename components, interval grouping, source folder priority, and winner comparison outcome.
- Missing mandatory inputs must fail the task before dispatch.
- Missing optional inputs must be recorded explicitly.

### 1.4.3.1 Runtime environment contract

- The execution layer must inject a documented set of environment variables into every scheduler job.
- At minimum, the runtime environment must expose working-root, station, task, task-scoped run, and processing-window identity through variables such as `VERIPROC_WORKING_ROOT`, `VERIPROC_STATION_ID`, `VERIPROC_TASK_ID`, `VERIPROC_RETRY_INDEX`, `VERIPROC_RUN_REF`, `VERIPROC_WINDOW_START`, and `VERIPROC_WINDOW_END`.
- When a joborder file is generated, the runtime environment must expose its path through `VERIPROC_JOBORDER_PATH`.
- These variables must be available to the launched process as ordinary process environment variables and must correspond to the station context references used by structured `execution.args`.
- Environment-variable injection must not replace the job order as the primary execution contract when a joborder file is enabled; it is a convenience layer for algorithms and wrappers.
- The local execution adapter must capture standard output and standard error independently as `logs/run_out.log` and `logs/run_err.log`.
- SLURM executor wrappers must preserve the same runtime environment and log contract on the allocated node. They must write process stdout and stderr under the run working root and persist an exit-code marker for reconciliation when scheduler accounting is delayed or unavailable.

### 1.4.3.2 Rolling archive intake and publication

- The backend must resolve rolling archive identifiers through top-level instance configuration before input selection.
- When station configuration enables output publication, the backend must copy, move, or link validated output artifacts from the working root to the configured rolling archive target after successful output validation. Directory artifacts must be transferred as one logical directory tree rooted at the artifact path.
- Rolling archive publication must be idempotent and recorded as artifact or publication metadata.
- Rolling archive retention must be treated as an operational policy; removing expired files must not remove the durable run record.

### 1.4.4 Dispatch and tracking

- Each run must be dispatched as one ephemeral scheduler job.
- The backend must track scheduler identity separately from run identity.
- Run state transitions must be explicit, persisted, and recoverable.

### 1.4.5 Output validation and downstream routing

- Completion must require output validation, not just scheduler success.
- Declared outputs may be regular files or directories. Directory outputs follow the same declared naming convention as regular-file outputs, and baseline validation treats the directory root as the declared artifact without requiring recursive child inspection.
- The backend must validate any algorithm-produced `task-out.yaml` before creating downstream tasks.
- If `task-out.yaml` is absent, the backend must fall back to the station's default downstream routing.

### 1.4.6 Query and audit support

- The API must expose task state, run state, job identifiers, working root location, logs, artifacts, and provenance links.
- The API must distinguish canonical completed runs from forced or superseded reruns.

## 1.5 Scope

**In scope for the MVP**

- Backend control plane with a switchable Postgres/SQLite state store
- Top-level instance configuration for storage roots, rolling archives, and optional generator modules
- YAML-defined station specifications and generated joborders in YAML, TOML, JSON, or an explicit no-file `none` mode
- SLURM execution through `slurm-native` and `slurm-docker` adapters behind the stable executor contract
- Shared-filesystem working roots with symlinked inputs and durable artifacts
- Rolling archive input selection and optional validated-output publication
- Downstream task creation, including split and aggregation workflows
- Grouped fan-out/fan-in in which one splitter stage creates parallel child tasks and one aggregation stage consumes the canonical completed result of each child task, or the canonical completed subset when an explicit partial-aggregation policy permits failed children to be excluded
- Crash recovery, idempotency rules, and queryable provenance

**Out of scope for the MVP**

- Deployments without a shared POSIX filesystem
- Backend-managed autoscaling logic beyond executor configuration and queue limits
- Real-time streaming or sub-second latency processing
- Multi-tenant isolation and policy enforcement
- Rich GUI workflow editing or graph authoring tools
- Non-relational state stores beyond SQLite and Postgres
- Multi-stage parallel branch aggregation in which readiness is evaluated over terminal tasks of branch pipelines such as `A -> B[i] -> C[i] -> Aggregation`, unless explicitly specified by deployment policy

A future extension may support multi-stage branch fan-in by introducing explicit terminal-branch membership rules that define which per-branch task result is counted toward split-group readiness.

## 1.6 Non-Goals and Constraints

The MVP makes the following constraints explicit:

- The system is single-tenant by default.
- The system assumes shared storage is available and sufficiently consistent for scheduler and backend access.
- The system does not guarantee domain correctness of scientific outputs beyond the validation hooks configured for a station.
- The system does not treat a scheduler-reported success as sufficient proof of a valid run.

## 1.7 Primary Identity Rules

The specification distinguishes the following identities:

- **Task identity** identifies one immutable routing request.
- **Run identity** identifies one task-scoped execution attempt. A run is canonically identified by the composite `(task_id, retry_index)`.
- **Job identity** identifies one scheduler submission for a run.
- **Processing fingerprint** identifies one scientifically relevant execution context for deduplication and canonicality.
- **Artifact identity** identifies one filesystem object produced or referenced by a run.
- **Station revision identity** identifies the exact configuration and algorithm context used to generate a job order.

These identities must not be conflated. In particular:

Each persisted entity must have one canonical identity model used for persistence, foreign keys, provenance, API identity, and machine-queryable references. For runs, that identity model is the task-scoped composite `(task_id, retry_index)`.
- Canonical task identifiers must not encode station names, parent run references, downstream ordinals, retry reasons, scheduler identifiers, working-root paths, or human-readable lineage fragments.
- A deployment may configure the timestamp segment of the preferred task identifier grammar to use the task creation time or the task processing-window start time. When the processing-window start time is used, it is an operator-readable generation component only; clients and backend logic must not infer authoritative processing-window state from the task identifier.
- Human readability must be provided through API fields, CLI columns, and generated path names, not through alternate durable identifiers.
- A run has no defined identity without its parent task. A bare retry index is not meaningful outside a task.
- Retrying a task must create a new run under the same task with a new `retry_index`.
- Re-submitting an equivalent task may or may not create a new run, depending on idempotency and deduplication policy.
- Two runs for the same task may have different processing fingerprints if their execution context differs.

## 1.8 Primary Operational Guarantees

VeriProc must provide the following guarantees:

- A canonical completed run must be reproducible from persisted metadata, subject to availability of referenced external inputs and images.
- A forced rerun must not silently overwrite the canonical status of an earlier completed run.
- A backend restart must not by itself justify duplicate downstream task creation or duplicate canonical dispatch.
- Every artifact returned by the API must be attributable to the run that produced it.

## 1.9 Target Use Case

The primary target is single-tenant L1 to L2 satellite processing pipelines such as CO2M granule processing, with the expectation that the same orchestration model will later be extended to additional processing levels, missions, and executor backends.
