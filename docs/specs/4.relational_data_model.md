# 4. Relational Data Model and Persistence Rules

This chapter defines the durable relational representation of VeriProc control-plane state. It converts the conceptual entities defined earlier into persisted records, constraints, and transactional rules suitable for implementation in a relational state store.

Unless explicitly marked informative, statements in this chapter are normative.

## 4.1 Scope of the Persistence Model

The persistence model defines the authoritative relational representation of control-plane state. A conforming implementation must persist enough information to support task intake, run preparation, scheduler tracking, output validation, downstream routing, split-group coordination, deduplication, audit, and crash recovery.

The database must be authoritative for the following record classes:

- tasks and backend-maintained task status summaries
- readable task history entries, if stored separately from the task payload
- provenance links or equivalent relationship records
- station revisions or immutable references to a versioned station registry
- runs
- jobs
- resolved input manifests and manifest entries
- artifact metadata
- rolling archive publication metadata
- split groups and child membership bookkeeping
- processing fingerprints or run fingerprint fields
- deduplication records
- idempotency records
- persisted instance-configuration identities, when the implementation records them in the state store
- generation-hook identities when they affect execution context

The shared filesystem remains authoritative for artifact bytes, including job orders, logs, output files, manifest exports, and `task-out.yaml` files. The database must store enough metadata to locate, identify, validate, and audit those files, but storing the bytes in the database is optional and not required by this specification.

Resolved input manifest records and entries are authoritative in the database. A serialized manifest may also be exported to the working root for audit or replay, but that export must be reproducible from or consistent with the database records and must not be the only durable source for API queries or recovery.

The database must remain the system of record for API queries and recovery decisions. Filesystem state, scheduler state, and station-generated descriptors may inform reconciliation, but they must not replace committed control-plane records.

## 4.2 Persistence Design Principles

The relational model must follow these principles.

**Identity**

Each persisted domain concept must have exactly one canonical identity model. Most domain concepts use a single canonical identifier. Runs use a composite canonical key because a run is defined only as an attempt for a task.

Task identity remains a single dedicated canonical key, `task_id`. Job identifiers, artifact identifiers, split-group identifiers, station revision identifiers, and processing fingerprint identifiers remain distinct from task identity and from each other.

The canonical run key is `(task_id, retry_index)`. The `retry_index` value is scoped to the parent task and must not be used alone as a foreign key, provenance reference, API identity, deduplication reference, or machine-queryable run reference.

Readable context must be stored in first-class fields or query projections, not encoded into identifiers. The preferred display form `task-20250703T111239000-a7sf7f/r5` is a rendering of `(task_id, retry_index)` and must not become a second persisted identity.

An implementation may store an internal unique run key when needed for physical database design. If present, it must be constrained so that each internal key maps to exactly one `(task_id, retry_index)` and each `(task_id, retry_index)` maps to at most one active run record. The internal key must not replace the canonical composite in normative relational semantics.

**Immutability**

Routing content must be immutable after task creation. Run identity is the immutable composite `(task_id, retry_index)`. Task association, retry index, station revision, working-root path after assignment, and processing fingerprint after computation must be immutable once the run has reached the point at which those fields are defined. Mutable operational fields such as state, timestamps, retry counters, scheduler-native status, validation summaries, and failure reasons may change according to documented lifecycle rules.

**Normalization boundaries**

The normalized source of truth must preserve the conceptual relationships between tasks, runs, jobs, manifests, artifacts, split groups, and deduplication records. Implementations may add denormalized summary columns or projections for efficient API queries, but those projections must be derived from the normalized records and must not be the only durable representation of required relationships.

**Auditability**

The database must retain sufficient immutable metadata to explain why a run was prepared, which station revision and instance configuration were used, which inputs were selected or missing, which outputs were validated, which downstream tasks were created, and which run owns canonical status for a processing fingerprint.

**Recoverability**

State transitions that cross external side effects must be persisted in a way that supports restart after partial failure. Preparation, dispatch, finalization, downstream creation, artifact recording, rolling-archive publication, split-group readiness, and deduplication ownership must be recoverable or safely classifiable after backend restart.

**Idempotency**

Externally visible operations that may be retried must be protected by unique constraints, idempotency records, transactional checks, or equivalent relational mechanisms. Idempotency must distinguish exact retries from conflicting reuse of identifiers or idempotency keys.

**Configuration freezing**

Every run must reference the exact station revision used to prepare it. The run must also reference the effective instance configuration identity and generation-hook identities when those values can affect execution context, audit, input resolution, job-order generation, or processing fingerprint computation.

## 4.3 Core Tables and Persisted Record Types

A conforming implementation may choose physical table names, column types, and JSON support appropriate to its relational database, but it must provide the persisted record types and constraints defined in this section.

### 4.3.0 `run` Reference Convention

Any table that conceptually references a run must store or be able to enforce the composite reference `(task_id, retry_index)`. Column names may vary by implementation, but examples in this chapter use `run_task_id` and `run_retry_index` when the referencing row is not itself scoped to a task.

Tables already scoped to a task may store only `retry_index` for a same-task run summary field, provided the owning `task_id` is part of the row and the constraint to `runs(task_id, retry_index)` is unambiguous.

An implementation may use an internal unique run key as a physical foreign key only if it also enforces uniqueness of `(task_id, retry_index)` and preserves the composite key in API projections, provenance representations, conformance tests, and audit exports. Normative semantics are defined in terms of `(task_id, retry_index)`.

### 4.3.1 `tasks`

**Purpose**

The `tasks` record stores one immutable routing request plus backend-maintained status summary fields.

**Primary key**

- `task_id`

**Required fields**

- `task_id`
- destination station identity or destination `proc_type`
- processing window start and end timestamps
- task creation timestamp
- force flag
- routing content or normalized equivalent
- current task summary state
- submission origin, either client-submitted or backend-created

**Optional fields**

- parent task identifier
- parent run task identifier and parent run retry index, when the task was derived from a run
- split-group identifier
- priority
- client metadata
- idempotency record reference
- latest run retry index, when a latest run exists for this task
- canonical run retry index, when a canonical run exists for this task
- failure summary
- completion timestamp

**Immutable vs mutable fields**

Destination, processing window, force flag, parent references, split-group association, client metadata, and routing content must be immutable after creation. Summary state, latest run reference, canonical run reference, failure summary, and completion timestamp may be updated by the backend.

**Foreign-key relationships**

- parent task reference should point to `tasks.task_id` when present
- parent run reference, when present, should reference `runs(task_id, retry_index)` through the parent task identifier and parent run retry index
- split-group reference should point to `split_groups.group_id` when present
- latest run and canonical run references should point to `runs(task_id, retry_index)` for this task when present

**Uniqueness constraints**

- `task_id` must be unique.
- If the implementation derives deterministic downstream task identifiers, the derived identifier or downstream-creation key must be unique.
- If a task is created through an idempotency record, the idempotency scope and key must resolve to one task result.

**Required indexes**

- destination station or `proc_type`
- processing window start and end
- task state
- creation timestamp
- parent task identifier
- parent run task identifier and parent run retry index, if stored
- split-group identifier
- canonical run retry index, if stored as a task summary field

**Deletion and retention expectations**

Task records are audit records and must not be physically deleted while referenced by runs, provenance links, artifacts, split groups, or deduplication records. Implementations may support archival or tombstoning if API queryability and referential integrity are preserved according to deployment retention policy.

**Transactional notes**

A task must be committed before any run is created for it. Downstream task creation must be transactionally coupled with provenance or relationship creation and any split-group membership records required for that child.

### 4.3.2 `task_history_entries`

**Purpose**

`task_history_entries` stores the readable routing history as ordered data when the implementation does not store the full history only inside an immutable task payload.

**Primary key**

- implementation-defined `history_entry_id`, or the composite key `(task_id, sequence_number)`

**Required fields**

- task identifier
- sequence number
- station identifier or task identifier for the traversed step
- completion timestamp or recorded event timestamp

**Optional fields**

- task-scoped run reference, represented by `task_id` and `retry_index`
- summary text
- source task identifier
- source run reference

**Immutable vs mutable fields**

History entries must be immutable after insertion. New downstream tasks may receive copied or extended history entries, but existing entries must not be mutated.

**Foreign-key relationships**

- `task_id` must reference `tasks.task_id`.
- Run references should reference `runs(task_id, retry_index)` when present.

**Uniqueness constraints**

- `(task_id, sequence_number)` must be unique.

**Required indexes**

- `task_id`
- source run reference, if stored

**Deletion and retention expectations**

History entries must follow the retention of their task. They must not be used as the only persisted provenance mechanism.

**Transactional notes**

History extension for a downstream task must occur in the same transaction as downstream task creation or be recoverable without creating duplicate history entries.

### 4.3.3 `provenance_links` or `task_relationships`

**Purpose**

Relationship records store machine-queryable provenance independently of readable routing history.

**Primary key**

- `provenance_link_id`, or a composite key over source object, target object, and relationship type

**Required fields**

- source object type
- source object identifier
- target object type
- target object identifier
- relationship type
- creation timestamp

**Optional fields**

- contribution role
- creation reason
- split-group identifier
- producing run reference, represented by `(task_id, retry_index)`
- metadata payload

**Immutable vs mutable fields**

Provenance links must be immutable after creation.

**Foreign-key relationships**

The implementation must enforce referential integrity for object types stored in the same database. If polymorphic links prevent native foreign keys, equivalent application-level validation and database constraints must ensure referenced records exist before the link is committed.

**Uniqueness constraints**

- The same source, target, and relationship type must not be recorded more than once unless an explicit relationship version or role distinguishes the records.

**Required indexes**

- source object type and identifier
- target object type and identifier
- relationship type
- split-group identifier, if stored

**Deletion and retention expectations**

Provenance links must be retained at least as long as either side of the relationship remains queryable.

**Transactional notes**

Required provenance links for downstream task creation, artifact recording, split-group membership, and aggregation must be created in the same transaction as the corresponding domain record or through an idempotent reconciliation process that cannot produce duplicate links.

### 4.3.4 `station_revisions`

**Purpose**

`station_revisions` records immutable station-configuration identities used by runs. An implementation may store the full validated station document, a content hash, or an immutable reference to an external versioned configuration store.

**Primary key**

- `station_revision_id`

**Required fields**

- station revision identifier
- station identifier
- `proc_type`
- station schema version
- immutable content hash or equivalent revision marker
- publication or effective timestamp
- validation status

**Optional fields**

- source repository commit
- human-readable label
- full validated configuration document
- execution image identity or digest
- split-group policy summary
- input and output definition summaries

**Immutable vs mutable fields**

Station revision identity, station identifier, `proc_type`, content hash, schema version, and validated configuration content must be immutable. Operational metadata about import or deprecation may be mutable if it does not change the meaning of runs that reference the revision.

**Foreign-key relationships**

- Runs must reference `station_revisions.station_revision_id` or an equivalent immutable station registry identity.

**Uniqueness constraints**

- `station_revision_id` must be unique.
- The pair `(station_id, content_hash)` should be unique.

**Required indexes**

- station identifier
- `proc_type`
- content hash
- publication or effective timestamp

**Deletion and retention expectations**

A station revision referenced by a run must remain queryable for the retention period of that run. Physical deletion must not break audit or replay of existing runs.

**Transactional notes**

A run must reference a validated station revision before preparation can proceed.

### 4.3.5 `instance_configuration_revisions`

**Purpose**

`instance_configuration_revisions` records the effective identity of deployment-level configuration used by runs when the implementation persists this identity in the state store.

**Primary key**

- `instance_configuration_revision_id`

**Required fields**

- instance configuration revision identifier
- instance identifier
- schema version
- content hash or equivalent immutable identity
- effective timestamp
- validation status

**Optional fields**

- full validated configuration document
- storage root summary
- naming policy summary
- integrity policy summary
- rolling archive summary
- product category summary
- facility summary
- generator references

**Immutable vs mutable fields**

The effective configuration identity and validated content must be immutable.

**Foreign-key relationships**

- Runs should reference the instance configuration revision used for preparation.
- Generation-hook records may reference the configuration revision that declared them.

**Uniqueness constraints**

- `instance_configuration_revision_id` must be unique.
- `(instance_id, content_hash)` should be unique.

**Required indexes**

- instance identifier
- content hash
- effective timestamp

**Deletion and retention expectations**

A configuration revision referenced by a run must remain queryable for the retention period of that run or must be recoverable from an immutable external configuration registry.

**Transactional notes**

The effective configuration identity must be frozen on the run before preparation uses configuration-dependent behavior.

The persisted configuration content or summary must include the effective `naming` and `integrity` policies. These policies are authoritative for generated path/filename segment rules and checksum handling for runs prepared under this configuration revision.

### 4.3.6 `generation_hook_identities`

**Purpose**

Generation-hook records identify custom or system-default working-root and job-order generators used for a run when those identities affect audit or processing fingerprints.

**Primary key**

- `generation_hook_identity_id`

**Required fields**

- hook type, such as `working_root` or `job_order`
- hook implementation type
- module or implementation name, or system-default marker
- version, content hash, or equivalent immutable identity

**Optional fields**

- configuration payload hash
- declared timeout policy
- validation mode
- instance configuration revision identifier

**Immutable vs mutable fields**

Hook identity fields must be immutable.

**Foreign-key relationships**

- Runs should reference the hook identities used during preparation, either directly or through a run-hook association table.
- Hook records may reference `instance_configuration_revisions`.

**Uniqueness constraints**

- The tuple `(hook_type, implementation_name, version_or_hash, configuration_hash)` should be unique when those fields are available.

**Required indexes**

- hook type
- implementation name
- version or content hash

**Deletion and retention expectations**

Hook identities referenced by runs must remain queryable for the retention period of those runs.

**Transactional notes**

Hook identity references must be stored before or during run preparation and must be available when computing processing fingerprints if output-affecting.

### 4.3.7 `runs`

**Purpose**

The `runs` record stores one execution attempt for one task.

**Primary key**

- Composite primary key `(task_id, retry_index)`.

An implementation may use an internal surrogate primary key for physical storage, but it must enforce a unique constraint on `(task_id, retry_index)` and all conceptual references to runs must remain expressible as that composite key.

**Required fields**

- task identifier
- station revision identifier
- current run state
- retry index or attempt ordinal
- working-root path once materialized
- creation timestamp

**Optional fields**

- internal unique run key for implementation use only
- instance configuration revision identifier
- working-root generator identity
- job-order generator identity
- station identifier projection for operator queries
- task window start projection for operator queries
- task window end projection for operator queries
- canonical classification
- active job identifier
- job-order artifact identifier
- manifest identifier
- scheduler uncertainty or reconciliation marker
- finalization summary
- failure reason
- timestamps for preparation, dispatch, runtime start, finalization, terminal state, and cancellation

**Processing fingerprint storage**

Processing fingerprint persistence is required for every prepared run. The fingerprint value and algorithm version may be stored as columns on `runs` or through a separate processing-fingerprint record as defined in Section 4.3.17. If stored on `runs`, those fields must be populated before the run is eligible for dispatch. If stored separately, the fingerprint record must reference the run by `(task_id, retry_index)`.

**Generator identity storage**

Working-root and job-order generator identities are required when the generator is custom, output-affecting, audit-relevant, or included in the processing fingerprint. Implementations may omit a physical generator-identity reference only when using a documented fixed system-default generator whose identity is implicit, stable, and not output-affecting under deployment policy.

**Readable query projections**

The authoritative station identity and processing window for a run are derived from the task and station revision relationships. Implementations may denormalize station identifier, task-window start, and task-window end onto `runs` or into materialized views for operator query efficiency. Such fields are projections or query aids only. They must not become alternate identities and must be rebuildable from authoritative task and station-revision records.

The preferred run display reference, such as `task-20250703T111239000-a7sf7f/r5`, may be stored or rendered as a projection. If stored, it must be derivable from `task_id` and `retry_index` and must not be used as a separate key.

**Immutable vs mutable fields**

Task identifier, retry index, station revision, working-root path after assignment, generator identities after assignment, and processing fingerprint after computation must be immutable. State, active job reference, finalization summary, failure reason, canonical classification until terminal finalization, and timestamps may be updated according to the run lifecycle.

**Foreign-key relationships**

- `task_id` must reference `tasks.task_id`.
- Station revision must reference `station_revisions.station_revision_id` or equivalent immutable station registry record.
- Instance configuration revision should reference `instance_configuration_revisions` when persisted.
- Active job should reference `jobs.job_id` when present.
- Job-order artifact should reference `artifacts.artifact_id` when present.
- Manifest identifier should reference `resolved_input_manifests.manifest_id` when present.

**Uniqueness constraints**

- `(task_id, retry_index)` must be unique and is the conceptual primary key.
- `retry_index` must be unique only within one task. It must not be globally unique or cross-task meaningful.
- `working_root_path` must be unique once assigned.
- An internal unique run key, when used, must be unique and must map one-to-one with `(task_id, retry_index)`.
- A retry-safe run creation key, when used, must be unique within its task or retry request scope.

**Required indexes**

- task identifier
- `(task_id, retry_index)`
- station revision identifier
- run state
- creation timestamp
- processing fingerprint
- canonical classification
- working-root path
- active job identifier

**Deletion and retention expectations**

Run records are durable audit records and must not be physically deleted while referenced by jobs, manifests, artifacts, provenance links, split groups, or deduplication records.

**Transactional notes**

Run creation must occur after task commit. Allocation of `retry_index` must be protected by a uniqueness constraint or equivalent transaction rule so that concurrent retries cannot create two runs with the same `(task_id, retry_index)`. State transitions must be persisted before or immediately after external side effects according to the recovery rules. Finalization must transactionally coordinate canonical classification, artifact recording, publication records, deduplication ownership, and downstream effects as defined in this chapter.

### 4.3.8 `jobs`

**Purpose**

The `jobs` record stores a concrete scheduler submission associated with one run.

**Primary key**

- `job_id`

**Required fields**

- job identifier
- run task identifier
- run retry index
- executor type
- submission attempt number
- submission timestamp
- scheduler identifier once known, or an explicit pending or unknown-submission marker before it is known

**Optional fields**

- scheduler-native state
- queue, partition, or resource class
- scheduler accounting fields
- submission payload hash
- cancellation request timestamp
- cancellation completion timestamp
- terminal scheduler timestamp
- last scheduler poll timestamp
- reconciliation status

**Immutable vs mutable fields**

Job identifier, run task identifier, run retry index, executor type, and submission attempt number must be immutable. Scheduler identifier must be immutable once known. Scheduler-native state, poll timestamp, cancellation fields, and reconciliation status may change until terminal handling completes.

**Foreign-key relationships**

- `(run_task_id, run_retry_index)` must reference `runs(task_id, retry_index)`.

**Uniqueness constraints**

- `job_id` must be unique.
- `(executor_type, scheduler_identifier)` must be unique when scheduler identifier is known.
- A run must have at most one active non-terminal job under the default policy.
- `(run_task_id, run_retry_index, submission_attempt_number)` must be unique.

**Required indexes**

- run task identifier and run retry index
- scheduler identifier
- scheduler-native state
- reconciliation status
- submission timestamp

**Deletion and retention expectations**

Job records must be retained with their run. Scheduler-native status history may be compacted if the latest status and audit-relevant terminal evidence remain available.

**Transactional notes**

The backend must persist scheduler identity as soon as it is known. If submission outcome is uncertain, the job or run record must capture reconciliation status before any resubmission decision is made.

### 4.3.9 `resolved_input_manifests`

**Purpose**

The manifest header record identifies the frozen resolved input manifest for a run.

**Primary key**

- `manifest_id`

**Required fields**

- manifest identifier
- run task identifier
- run retry index
- manifest schema version
- creation timestamp
- freeze timestamp before dispatch
- resolution policy identity or version

**Optional fields**

- exported manifest artifact identifier
- manifest content hash
- resolver implementation version
- validation summary

**Immutable vs mutable fields**

Manifest header content must be immutable once the manifest is frozen. Export artifact reference may be added if the export is created after the database records, but it must not change manifest meaning.

**Foreign-key relationships**

- `(run_task_id, run_retry_index)` must reference `runs(task_id, retry_index)`.
- Exported manifest artifact should reference `artifacts.artifact_id` when present.

**Uniqueness constraints**

- `manifest_id` must be unique.
- Each run must have at most one frozen manifest under the default preparation model.

**Required indexes**

- run task identifier and run retry index
- freeze timestamp
- content hash, if available

**Deletion and retention expectations**

Manifest records must be retained with their run.

**Transactional notes**

A run must not enter dispatching until its resolved input manifest is persisted and frozen.

### 4.3.10 `resolved_input_entries`

**Purpose**

Manifest entry records store the per-declared-input outcome and selected file bindings.

**Primary key**

- `manifest_entry_id`, or the composite key `(manifest_id, declared_input_key, file_sequence)` when each selected file is stored as a row

**Required fields**

- manifest identifier
- declared input key or sequence
- file type
- category
- mandatory flag
- selection outcome, such as `resolved` or `missing_optional`
- source directory precedence or missing reason

**Optional fields**

- source path for selected files
- working-root input path
- file sequence for multi-file inputs
- source rolling archive identifier
- resolved category folder source
- file size
- modification time
- checksum value
- checksum algorithm
- checksum source, such as `sidecar`, `upstream_metadata`, `external_metadata`, or `computed_by_veriproc`
- effective filename pattern
- applied `window_match` policy
- parsed mission identifier
- parsed start timestamp
- parsed end timestamp
- parsed generation timestamp
- parsed file type when the effective pattern contains `<FILE_TYPE>`
- version metadata
- tie-break reason
- contributing child task identifier for aggregation inputs
- contributing child run task identifier and contributing child run retry index for aggregation inputs
- producing artifact identifier when selected from prior VeriProc outputs

**Immutable vs mutable fields**

Manifest entries must be immutable once the manifest is frozen.

**Foreign-key relationships**

- `manifest_id` must reference `resolved_input_manifests.manifest_id`.
- Contributing child task and run references should reference `tasks` and `runs` when present.
- Producing artifact reference should reference `artifacts.artifact_id` when present.

**Uniqueness constraints**

- The implementation must preserve one entry per declared station input and each selected file binding.
- `(manifest_id, declared_input_key, file_sequence)` must be unique when file bindings are row-based.

**Required indexes**

- manifest identifier
- file type
- category
- source rolling archive identifier
- producing artifact identifier, if present
- contributing child task identifier, if present

**Deletion and retention expectations**

Manifest entries must be retained with their manifest.

**Transactional notes**

Mandatory missing inputs must prevent dispatch and must be recorded as preparation failure if a run record already exists. Optional missing inputs must be recorded explicitly.

Under the default instance integrity policy `available_only`, checksum columns remain nullable and the backend must not compute checksums by reading full file contents solely to populate them. Size, modification time, version metadata, and selection metadata should still be recorded when available.

When input selection depends on the structured filename contract, manifest-entry persistence must preserve the effective `filename_pattern`, any `<FILE_TYPE>` substitution derived from the declared input definition, the applied `window_match` policy, and the parsed filename components needed to explain the selection without re-running discovery logic.

### 4.3.11 `artifacts`

**Purpose**

Artifact records store metadata for files associated with a run, including job orders, manifest exports, logs, outputs, and task output descriptors.

**Primary key**

- `artifact_id`

**Required fields**

- artifact identifier
- producing run task identifier and producing run retry index, or external origin reference for externally selected input artifacts
- logical artifact type
- filesystem path
- storage role or namespace
- creation or discovery timestamp

**Optional fields**

- file type
- relative path within working root
- size
- checksum value
- checksum algorithm
- checksum source, such as `sidecar`, `upstream_metadata`, `external_metadata`, or `computed_by_veriproc`
- media type
- validation status
- validation timestamp
- validation summary
- mandatory-output flag
- publication status summary
- content metadata

**Immutable vs mutable fields**

Artifact identifier, producing run reference, logical artifact type, and filesystem path must be immutable. Validation metadata, checksum metadata, size, and publication summary may be added or updated during finalization if they describe the same file identity and comply with the effective integrity policy.

**Foreign-key relationships**

- Producing run must reference `runs(task_id, retry_index)` when the artifact is produced by VeriProc.
- Artifact records should be linked by provenance links from the producing run.

**Uniqueness constraints**

- `artifact_id` must be unique.
- `(producing_run_task_id, producing_run_retry_index, logical_artifact_type, path)` must be unique.
- A run must have exactly one job-order artifact record after job-order creation succeeds.

**Required indexes**

- producing run task identifier and producing run retry index
- logical artifact type
- file type
- validation status
- path
- checksum value, if available

**Deletion and retention expectations**

Artifact metadata must be retained at least as long as the producing run is retained. If bytes are removed by retention policy, the artifact record should remain with a retention or availability marker rather than being silently deleted.

**Transactional notes**

A run must not reach `complete` until required output artifacts have been validated and their records have been persisted.

### 4.3.12 `rolling_archive_publications`

**Purpose**

Publication records store the idempotent publication of validated artifacts into configured rolling archives.

**Primary key**

- `publication_id`

**Required fields**

- publication identifier
- source artifact identifier
- producing run task identifier and producing run retry index
- rolling archive identifier
- target path
- publication mode
- publication state
- creation or publication timestamp

**Optional fields**

- checksum value
- checksum algorithm
- checksum source, such as `sidecar`, `upstream_metadata`, `external_metadata`, or `computed_by_veriproc`
- target size
- target relative path
- failure reason
- retry count
- retention policy identity

**Immutable vs mutable fields**

Source artifact, producing run, rolling archive identifier, target path, and publication mode must be immutable once publication succeeds. Publication state, failure reason, retry count, and timestamps may change while publication is pending or being retried.

**Foreign-key relationships**

- Source artifact must reference `artifacts.artifact_id`.
- Producing run must reference `runs(task_id, retry_index)`.
- Rolling archive identifier must resolve to the effective instance configuration used by the run, or to a persisted rolling archive definition if one is stored relationally.

`target_path` must be interpreted as a path relative to the selected archive root. By default, it should resolve to the published filename at the archive root. Additional directory segments must come only from an explicit persisted publication subpath or equivalent station policy; implementations must not prepend implicit station-derived directories.

**Uniqueness constraints**

- `(source_artifact_id, rolling_archive_id, target_path)` must be unique.
- If target paths are globally unique within an archive, `(rolling_archive_id, target_path)` should be unique unless replacement policy explicitly permits versioned collisions.

**Required indexes**

- source artifact identifier
- producing run task identifier and producing run retry index
- rolling archive identifier
- publication state
- target path

**Deletion and retention expectations**

Publication records must remain queryable after rolling archive retention removes published bytes. Removal of published bytes must not remove the source artifact record or alter producing-run identity.

**Transactional notes**

Publication metadata must be recorded idempotently. If downstream routing depends on published paths, downstream creation must not be committed before required publication records reach successful state.

### 4.3.13 `split_groups`

**Purpose**

Split-group records persist grouped fan-out/fan-in coordination state.

**Primary key**

- `group_id`

**Required fields**

- group identifier
- parent task identifier or parent run reference `(parent_task_id, parent_retry_index)`
- parent processing window
- group evaluation mode, such as `aggregation` or `completion_only`
- grouped evaluation target or stage
- membership basis
- closure state
- readiness state
- grouped evaluation state
- readiness policy identity or serialized policy summary
- creation timestamp

**Optional fields**

- expected child count
- child-key derivation rule identity or summary
- dynamic membership predicate identity or summary
- timeout policy
- partial-aggregation policy
- grouped-evaluation window override
- aggregation target station or stage
- aggregation task identifier
- closure timestamp
- readiness timestamp
- grouped completion timestamp
- failure reason
- producing run task identifier and producing run retry index

**Immutable vs mutable fields**

Group identifier, parent association, parent window, group evaluation mode, grouped evaluation target, membership basis, and aggregation target must be immutable after creation. Membership may change only until closure. Closure state, readiness state, grouped evaluation state, aggregation task reference, and timestamps may change according to the split-group lifecycle.

**Foreign-key relationships**

- Parent task should reference `tasks.task_id` when present.
- Parent run should reference `runs(task_id, retry_index)` when present.
- Producing run should reference `runs(task_id, retry_index)` when present.
- Aggregation task should reference `tasks.task_id` when present.

**Uniqueness constraints**

- `group_id` must be unique.
- A producing canonical run must not create duplicate split groups for the same declared group key.
- Under the default policy, a split group must reference at most one aggregation task.

**Required indexes**

- parent task identifier
- parent run reference, if stored
- closure state
- readiness state
- grouped evaluation state
- aggregation task identifier
- grouped evaluation target

**Deletion and retention expectations**

Split groups and membership records must be retained with their parent task or run and any aggregation task.

**Transactional notes**

Split-group creation must be transactionally coupled with child-task membership creation when membership is known at fan-out time. Readiness transitions and aggregation task materialization must be protected by uniqueness constraints so that retries do not create duplicate aggregation tasks.

### 4.3.14 `split_group_membership`

**Purpose**

Membership records persist the child tasks that belong to a split group and the canonical child result selected for readiness or aggregation.

**Primary key**

- `membership_id`, or the composite key `(group_id, child_key)`

**Required fields**

- group identifier
- child key or member sequence
- child task identifier
- membership state
- creation timestamp

**Optional fields**

- expected window for the child
- contributing canonical run task identifier and contributing canonical run retry index
- contributing artifact identifiers or artifact selection summary
- exclusion state
- exclusion reason
- readiness contribution state
- completion timestamp
- duplicate-handling metadata

**Immutable vs mutable fields**

Group identifier, child key, and child task identifier must be immutable after insertion. Contributing canonical run, readiness contribution, exclusion state, and selected artifact summary may change until the group reaches terminal grouped evaluation state, subject to canonicality rules.

**Foreign-key relationships**

- `group_id` must reference `split_groups.group_id`.
- Child task must reference `tasks.task_id`.
- Contributing canonical run should reference `runs(task_id, retry_index)` when known.

**Uniqueness constraints**

- `(group_id, child_key)` must be unique.
- `(group_id, child_task_id)` must be unique.
- A child task must belong to at most one active split group unless an explicit multi-group membership policy is persisted.

**Required indexes**

- group identifier
- child task identifier
- membership state
- readiness contribution state
- contributing canonical run reference

**Deletion and retention expectations**

Membership records must be retained with the split group.

**Transactional notes**

Membership updates that select a canonical child result must be consistent with the child task's canonical completed run. Readiness evaluation must use membership records for the target `group_id`, not archive scans or routing-history text.

### 4.3.15 `deduplication_records`

**Purpose**

Deduplication records identify canonical ownership of processing fingerprints.

**Primary key**

- processing fingerprint, or an implementation-defined `deduplication_record_id` with a unique processing fingerprint

**Required fields**

- processing fingerprint
- owning run task identifier and owning run retry index
- canonical status
- creation timestamp

**Optional fields**

- fingerprint algorithm version
- superseded-by run task identifier and superseded-by run retry index
- superseded timestamp
- promotion timestamp
- replacement reason

**Immutable vs mutable fields**

Processing fingerprint must be immutable. Ownership metadata may change only through explicit promotion, replacement, or supersession operations. Such changes must preserve previous ownership history either in the record or in an associated audit table.

**Foreign-key relationships**

- Owning run must reference `runs(task_id, retry_index)`.
- Superseded-by run should reference `runs(task_id, retry_index)` when present.

**Uniqueness constraints**

- One processing fingerprint must have at most one current canonical owner.
- A run must not own more than one canonical deduplication record unless an explicit multi-fingerprint policy is defined.

**Required indexes**

- processing fingerprint
- owning run reference
- canonical status
- superseded-by run reference

**Deletion and retention expectations**

Deduplication records must be retained for as long as duplicate detection and canonicality queries are required. They must not be deleted in a way that permits accidental duplicate canonical dispatch.

**Transactional notes**

Creating or updating a deduplication record must occur in the same transaction as canonical run classification and before default downstream effects are emitted.

### 4.3.16 `idempotency_records`

**Purpose**

Idempotency records protect externally visible operations from duplicate effects when clients or backend recovery retry an operation.

**Primary key**

- `(scope, idempotency_key)`, or a generated identifier with a unique `(scope, idempotency_key)` constraint

**Required fields**

- idempotency scope
- idempotency key
- request fingerprint or canonical request hash
- operation type
- first-seen timestamp
- result status

**Optional fields**

- task identifier
- run task identifier and run retry index
- response summary
- expiration timestamp
- conflict timestamp
- failure summary

**Immutable vs mutable fields**

Scope, key, request fingerprint, and operation type must be immutable after first insert. Result status and response summary may be updated when the operation completes.

**Foreign-key relationships**

- Task and run references should point to `tasks` and `runs` when present.

**Uniqueness constraints**

- `(scope, idempotency_key)` must be unique.

**Required indexes**

- scope and key
- request fingerprint
- expiration timestamp
- task identifier

**Deletion and retention expectations**

Idempotency records must be retained for at least the documented retry window. Expired records may be removed only when doing so cannot create ambiguity for supported client retries.

**Transactional notes**

Task submission idempotency must be enforced transactionally. Reusing a key with identical request content must return the recorded logical result. Reusing a key with conflicting content must fail as an idempotency conflict.

### 4.3.17 Processing Fingerprint Fields or Records

**Purpose**

The processing fingerprint is the canonicality and deduplication key for a prepared run.

**Primary key**

If stored separately, the processing fingerprint value or a generated fingerprint record identifier may be used. If embedded, `runs.processing_fingerprint` must be indexed and immutable after computation.

**Required fields**

- processing fingerprint value
- fingerprint algorithm version
- run task identifier and run retry index, or equivalent owner reference constrained to one `(task_id, retry_index)` when stored separately
- computation timestamp

**Optional fields**

- canonicalized fingerprint input document
- fingerprint component hashes
- station revision component
- manifest component
- runtime parameter component
- generator identity component

**Immutable vs mutable fields**

Fingerprint value, algorithm version, and canonicalized inputs must be immutable after computation.

**Foreign-key relationships**

- Run reference must point to `runs(task_id, retry_index)` when fingerprints are stored separately.

**Uniqueness constraints**

- Each prepared run must have exactly one processing fingerprint unless preparation fails before fingerprint computation.
- Multiple runs may share a fingerprint, but only one current canonical deduplication owner is allowed for that fingerprint.

**Required indexes**

- processing fingerprint
- run reference
- algorithm version

**Deletion and retention expectations**

Fingerprint data must be retained with the run and deduplication record.

**Transactional notes**

Fingerprint computation must occur after the execution context affecting outputs is resolved and before the run is eligible for dispatch. Canonical dispatch decisions and finalization deduplication decisions must use the stored fingerprint and must not assume deduplication ownership before the fingerprint has been persisted.

## 4.4 Cardinality and Referential Rules

The relational model must enforce or validate the following cardinalities:

- One task may have zero or more runs.
- One run must reference exactly one task.
- One run must reference exactly one station revision.
- One run must own one distinct working root once preparation materializes filesystem state.
- One run must reference exactly one generated job-order artifact after job-order generation succeeds.
- One run must have zero or one active scheduler job at a time under the default policy.
- One job must reference exactly one run.
- One run must have at most one frozen resolved input manifest under the default preparation model.
- One manifest must contain one entry for each declared station input and must preserve multiplicity when an input resolves to multiple files.
- One artifact produced by VeriProc must reference exactly one producing run.
- One rolling archive publication must reference exactly one source artifact and exactly one target rolling archive.
- One split group must reference one parent task or one parent run, according to the policy that created it.
- One split group may have zero or more member child tasks.
- One member child task must appear at most once in a given split group.
- One child task must belong to at most one active split group unless an explicit multi-group policy is persisted.
- One split group may reference at most one aggregation task under the default policy.
- One aggregation task must reference exactly one split group.
- One processing fingerprint may be associated with multiple runs.
- One processing fingerprint must have at most one current canonical deduplication owner.
- One canonical completed run may drive default downstream effects for its task. Non-canonical runs must not drive downstream effects unless an explicit policy permits it.

Referential integrity must prevent dangling references for required relationships. If a database cannot enforce a polymorphic relationship natively, the implementation must enforce the relationship transactionally and must expose diagnostics for invalid references.

## 4.5 Status and Lifecycle Persistence

The database must store lifecycle state directly for tasks, runs, jobs, and split groups.

Task state must summarize the routing request from the control-plane perspective. It should include enough information for clients to determine whether the task is accepted, active, completed canonically, failed, cancelled, waiting for retry, or superseded by policy. Task state may be denormalized from run and deduplication state, but it must be maintained consistently with those records.

Run state must preserve the internal run lifecycle needed for recovery. At minimum, the database must distinguish the semantics of `pending`, `preparing`, `dispatching`, `dispatched`, `running`, `finalizing`, `complete`, `failed`, `cancelled`, and `orphaned`, or an implementation-documented equivalent state model with the same recovery behavior.

Job state must store scheduler-facing status separately from run state. Scheduler-native state may lag behind run state and must not be treated as sufficient for run completion without output validation and artifact persistence.

Split groups must persist closure state, readiness state, grouped evaluation state, and terminal failure or completion timestamps. A composite group state may be stored for query efficiency, but closure, readiness, and grouped evaluation state must remain recoverable.

Terminal states must record terminal timestamps and should record terminal reasons or summaries. Terminal run states must not be changed except by explicit operator or API actions that create auditable promotion, supersession, or correction records. Retrying a task must create a new run, not mutate a terminal run back into a non-terminal state.

Canonical classification must be persisted on the run or through an associated canonicality record. A completed run must be distinguishable as canonical, non-canonical forced rerun, superseded canonical owner, or not applicable. The API-visible classification must be derivable from persisted run and deduplication records.

## 4.6 Constraints for Idempotency and Recovery

This section defines minimum persistence protections required for idempotent and recoverable behavior.

### 4.6.1 Task Submission Idempotency

Task submission must be protected by a unique `(scope, idempotency_key)` constraint or equivalent. The protected record must include a canonical request hash. An exact retry must return the same logical task result. A conflicting retry with the same key and different canonical request hash must fail transactionally and must not create a second task.

If a client does not provide an idempotency key and the API permits such submissions, the backend may create a new task for each accepted request. This behavior must be documented by the API.

### 4.6.2 Retry-Safe Run Creation

Run creation for a task retry must be protected by a unique task-scoped run key `(task_id, retry_index)` and by any equivalent retry-request key used for recovery safety. If recovery repeats the same run-creation operation, the backend must return or resume the existing run rather than creating an unintended duplicate.

A retry must never reuse a previous run's working root. The working-root path must be unique once assigned.

### 4.6.3 Downstream Task Creation

Downstream task creation from a producing run must be protected by a unique downstream-creation key derived from the producing run, validated descriptor or station default routing rule, target station, target window, split-group membership key where applicable, and downstream declaration identity. Retrying finalization must not create duplicate downstream tasks.

Downstream task creation, provenance link creation, and split-group membership creation must be committed together when they are part of the same downstream effect. If committed separately for implementation reasons, each step must be idempotent and recoverable without duplicate children.

Only the canonical completed run may emit default downstream effects unless a persisted explicit policy authorizes non-canonical downstream creation.

### 4.6.4 Split-Group Creation and Readiness Transitions

Split-group creation must be protected by a unique group identifier and by a producing-run declaration key when groups are created from a run. Membership records must be unique per group and child key. Closure must be irreversible once recorded unless an explicit operator correction policy exists and records an audit event.

Readiness transition to ready must be transactional with the evaluated membership snapshot. Aggregation task creation must be protected so that only one aggregation task is created for a group under the default policy, even if readiness evaluation is retried.

### 4.6.5 Artifact Recording

Artifact records must be protected by unique artifact identifiers and by a uniqueness constraint that prevents duplicate logical records for the same run, logical artifact type, and path. Finalization retries must be able to discover the existing artifact record and continue validation or routing.

A run must not be marked complete until mandatory artifact records and their validation metadata are committed.

### 4.6.6 Rolling-Archive Publication

Rolling-archive publication must be protected by a uniqueness constraint over the source artifact, target archive, and target path. The stored `target_path` must remain relative to the selected archive root, defaulting to the published filename at that root unless an explicit publication subpath is configured. If publication bytes are created before the database commit, recovery must be able to detect the existing target and record or validate the publication without creating a duplicate logical publication.

Publication records required for downstream consumption must be committed successfully before downstream tasks that depend on the publication are committed.

### 4.6.7 Deduplication Ownership

The deduplication record for a processing fingerprint must be protected by a unique canonical ownership constraint. Finalization must create or verify canonical ownership transactionally before a run is classified as canonical and before default downstream effects are emitted.

If a canonical owner already exists for the fingerprint and the current run is not authorized to replace it, the current run must be recorded as non-canonical or failed according to policy and must not emit default downstream effects.

### 4.6.8 Scheduler Submission Uncertainty

Scheduler submission must be persisted so that the backend can distinguish these cases after restart:

- no submission has been attempted
- submission has been attempted but acknowledgement is uncertain
- scheduler identifier is known and persisted
- scheduler reconciliation is required
- scheduler job has been confirmed absent or found

The backend must not blindly submit another job for the same run after uncertainty. It must first reconcile with scheduler-visible state when possible or mark the run `orphaned` according to policy.

## 4.7 Manifest, Artifact, and Publication Persistence

A resolved input manifest must have a header record and entry records. The header identifies the run, schema version, resolution policy, creation time, and freeze time. Entries must record every declared station input, including missing optional inputs. Selected inputs must record their source identity, source precedence, rolling archive identifier when applicable, physical source path, working-root input path, size, modification time, checksum when available, effective `filename_pattern`, applied `window_match` policy, parsed filename components when structured filename matching is used, and tie-break or selection reason.

Multi-file inputs must preserve ordering and multiplicity. The implementation may store each selected file as a separate row or as a structured list inside a manifest entry, but the API and audit model must be able to report each selected file independently.

Artifacts must represent logical files associated with a run, not only mandatory outputs. Job orders, manifest exports, log files, output files, `task-out.yaml`, and other audit objects may all be artifacts. Every artifact record must contain logical type, path, run association or external origin, and enough metadata to evaluate availability and validation status.

Publication records must link a source artifact to a target rolling archive location. Publication must not change the producing-run identity of the source artifact. The target location must remain relative to the selected archive root and must not include implicit station-derived directory prefixes. A published copy, hardlink, or symlink may have its own metadata, but provenance must still identify the original producing run.

Retention cleanup may remove artifact bytes from working roots or rolling archives only according to deployment policy. Such cleanup must not silently remove or corrupt the durable metadata required for audit, provenance, deduplication, or split-group aggregation history.

## 4.8 Split-Group Persistence Rules

Split-group persistence must align with the group semantics defined by station policy or validated `task-out.yaml` declarations.

The split-group record must persist:

- parent task or parent run association
- parent processing window
- group evaluation mode
- grouped evaluation target or stage
- membership basis
- closure state and closure timestamp when closed
- readiness state and readiness timestamp when ready or failed
- grouped evaluation state
- grouped-evaluation window override, when policy defines one
- aggregation target station or stage when group evaluation mode is `aggregation`
- aggregation task reference when materialized
- timeout policy and partial-aggregation policy when applicable
- failure reason when the group cannot progress

Membership records must persist:

- child task identity
- deterministic child key or member sequence
- expected child window or membership metadata when applicable
- membership state
- readiness contribution state
- contributing canonical run reference when available
- selected contributing artifacts when available
- duplicate-handling outcome when duplicates are declared or discovered
- exclusion state and reason when partial aggregation is allowed

Readiness evaluation must be performed per `group_id`. The backend must not infer aggregation membership from archive scanning, filename patterns, overlapping time ranges, station identity, product type, or routing-history text. Those sources may help locate artifact bytes only after membership and canonical child results have been determined from persisted split-group records.

For aggregation-mode groups, the aggregation task must reference exactly one split group. The aggregation run's resolved input manifest must record the exact contributing child task, producing run, and artifact identity for each selected input where those identities are known.

Canonicality changes after aggregation task materialization must not alter the aggregation input set unless an explicit re-aggregation policy is invoked and persisted.

## 4.9 Fingerprint and Canonicality Persistence

Every prepared run must store its processing fingerprint once the output-affecting execution context is known. The fingerprint must be computed during preparation after station revision resolution, input manifest resolution, relevant instance configuration identity, generator identities, runtime parameters, and other fingerprint components are frozen, and before the run is eligible for dispatch. If the fingerprint cannot be computed or persisted, the run must not be dispatched.

The fingerprint may be stored directly on the run record or in a separate processing-fingerprint table. In either case, it must be immutable after computation, must be indexed for deduplication lookup, and must be available before finalization performs canonicality or deduplication ownership decisions.

Run canonical classification and deduplication records must remain consistent:

- A run that completes successfully and becomes the deduplication owner for its fingerprint is canonical.
- A forced rerun must be non-canonical by default, even if it completes successfully.
- A non-canonical run may retain the same or a different fingerprint but must not own the canonical deduplication record unless explicitly promoted or used in an explicit replacement policy.
- Supersession or promotion must record the previous owner, new owner, timestamp, reason, and actor or operation source where available.

Finalization must guarantee transactionally that no two runs become current canonical owners for the same processing fingerprint. The transaction that records canonical ownership must also update the run canonical classification and must complete before default downstream effects are emitted.

If finalization cannot determine canonical ownership safely, the run must not be marked canonical. It must remain in `finalizing`, fail with a diagnostic, or enter an implementation-defined recovery state with equivalent safety.

## 4.10 Query-Oriented Projections

Implementations should materialize or denormalize selected fields to support efficient API queries. Useful projections include:

- task summary state
- latest run reference
- canonical run reference
- active run or active job identifier
- last scheduler identifier
- working-root path for latest or canonical run
- artifact counts by logical type and validation status
- split-group summary state
- downstream child count
- publication summary
- failure summary and terminal timestamp

Such projections must be derived from normalized records. They must not replace required task, run, job, manifest, artifact, split-group, provenance, or deduplication records. If projections become inconsistent, recovery must be able to rebuild them from normalized state or mark them stale until rebuilt.

API responses may use projections, but correctness requirements such as canonical ownership, split-group readiness, and downstream idempotency must rely on normalized transactional state.

## 4.11 Schema Evolution and Migration Rules

The relational schema must have an explicit schema version and migration policy. Database schema changes must preserve the meaning of existing tasks, runs, station revision references, manifests, artifacts, split groups, provenance links, and deduplication records.

Migrations must satisfy these rules:

- Existing run meaning must not change because of a migration.
- Existing task identifiers and existing task-scoped run keys `(task_id, retry_index)` must remain stable.
- Required audit and query fields must remain queryable after migration.
- Migrations that transform normalized records must be deterministic and repeatable.
- Backward-safe handling of persisted data should be provided where practical.
- New nullable fields, new optional records, and new enum values may be added only when older clients and recovery logic can handle their absence or unknown value according to compatibility policy.
- Destructive migrations must require an explicit operator action and must preserve an audit path or backup sufficient for rollback according to deployment policy.

If a migration changes fingerprint computation, job-order schema interpretation, station revision interpretation, or API-visible lifecycle semantics, the implementation must version the affected contract and must not retroactively reinterpret existing runs without an explicit migration rule.

## 4.12 Example Logical Schema

The following example is informative. It illustrates one compact relational layout and does not prescribe physical column types, storage engines, or all secondary indexes.

| Record type | Key fields | Required relationships | Selected constraints |
|---|---|---|---|
| `tasks` | `task_id`, destination, window, force, state | parent task, parent run reference, split group, latest run, canonical run | unique `task_id`; immutable routing content |
| `task_history_entries` | `task_id`, `sequence_number`, station/task reference, timestamp | task | unique `(task_id, sequence_number)` |
| `provenance_links` | source object, target object, relationship type | referenced domain records | unique source-target-type tuple |
| `station_revisions` | `station_revision_id`, `station_id`, `proc_type`, content hash | runs | unique revision; unique `(station_id, content_hash)` |
| `instance_configuration_revisions` | revision id, instance id, content hash | runs, hooks | unique `(instance_id, content_hash)` |
| `generation_hook_identities` | hook type, implementation, version/hash | runs | unique hook identity tuple |
| `runs` | `task_id`, `retry_index`, station revision, state, working root, fingerprint | task, station revision, jobs, manifest, artifacts | unique `(task_id, retry_index)`; unique working root |
| `jobs` | `job_id`, run task, run retry, executor, scheduler id, scheduler state | run | unique `(executor, scheduler_id)` when known; at most one active job per run |
| `resolved_input_manifests` | `manifest_id`, run task, run retry, schema version, freeze time | run | at most one frozen manifest per run |
| `resolved_input_entries` | manifest, declared input, file sequence, outcome | manifest, optional child task/run/artifact | unique `(manifest_id, declared_input_key, file_sequence)` |
| `artifacts` | `artifact_id`, producing run reference, logical type, path | run | unique `(producing_run_task_id, producing_run_retry_index, logical_artifact_type, path)` |
| `rolling_archive_publications` | publication id, source artifact, archive id, target path | artifact, run | unique `(source_artifact_id, archive_id, target_path)` |
| `split_groups` | `group_id`, parent, mode, closure/readiness/evaluation states | parent task/run, aggregation task | unique `group_id`; at most one aggregation task by default |
| `split_group_membership` | group id, child key, child task, contribution state | split group, child task, canonical run | unique `(group_id, child_key)`; unique `(group_id, child_task_id)` |
| `deduplication_records` | processing fingerprint, owning run, canonical status | run | at most one current canonical owner per fingerprint |
| `idempotency_records` | scope, key, request hash, result | task/run when applicable | unique `(scope, idempotency_key)` |

A conforming implementation may split, merge, or extend these records if the externally observable persistence contracts, referential rules, idempotency guarantees, and recovery behavior remain equivalent.
