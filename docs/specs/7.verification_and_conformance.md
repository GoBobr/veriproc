# 7. Verification and Conformance

This chapter defines how VeriProc implementations demonstrate conformance to this specification. It defines verification scope, conformance levels, required test categories, required invariants, minimum MVP compliance scenarios, and the evidence that must accompany a conformance claim.

Unless explicitly marked informative, statements in this chapter are normative.

Verification is part of the VeriProc specification. Passing only happy-path workflow tests is not sufficient. A conforming implementation must demonstrate that it preserves required invariants, handles failure and recovery safely, exposes the required API and CLI behavior, and records enough evidence for operators and implementers to audit the claim.

## 7.1 Scope and Purpose

The purpose of verification is to demonstrate that an implementation behaves according to the normative requirements defined by this specification. Verification must cover control-plane semantics, persistence behavior, API behavior, executor-adapter behavior, recovery behavior, idempotency behavior, provenance behavior, canonicality behavior, split-group behavior when supported, rolling archive behavior when supported, and CLI behavior when a CLI is provided.

Conformance testing must be derived from the specification. Test suites may use implementation-specific fixtures, mocks, or adapters, but the expected behavior must be traceable to the normative requirements in this document.

An implementation must not claim conformance based only on successful task submission and successful scheduler execution. Correctness also includes preserving identity distinctions, freezing execution context before dispatch, preventing duplicate canonical work, recovering safely after partial failure, validating outputs before completion, persisting provenance independently of readable history, and exposing state consistently through the API.

Failure handling and recovery behavior are mandatory parts of correctness. A conforming implementation must demonstrate that restart, retry, uncertain scheduler state, partially written filesystem artifacts, and repeated API requests do not silently corrupt control-plane state or duplicate externally visible work.

If a CLI is provided, CLI conformance must be tested against API semantics. The CLI must be verified as an API client, not as an alternate control-plane implementation. CLI tests must demonstrate that the CLI does not bypass the REST API by directly mutating the database, working roots, scheduler state, rolling archive publication metadata, or station-derived control artifacts.

Implementation conformance claims must be grounded in demonstrable evidence. At minimum, evidence must include automated test results, a scenario matrix, a description of tested configurations, declared deviations, and explicitly deferred features.

## 7.2 Conformance Model

VeriProc conformance is defined at the level of implemented behavior, not at the level of source-code organization, programming language, deployment packaging, or test framework. An implementation may use any internal architecture that preserves the externally visible and persisted semantics required by this specification.

### 7.2.1 Specification Conformance

Specification conformance means that the implementation satisfies all applicable normative requirements for the features it claims to support. A specification-conformant implementation must preserve the identity, persistence, API, recovery, and artifact semantics defined in the preceding chapters.

An implementation must not claim support for a feature unless both of the following are true:

- the required behavior for that feature is implemented
- the verification required for that feature has passed in the claimed conformance environment

If a feature is not implemented, partially implemented, or implemented without the required verification, it must be declared as unsupported, deferred, experimental, or non-conformant. It must not be silently omitted from a conformance claim.

### 7.2.2 MVP Reference Implementation Conformance

MVP reference implementation conformance means that the implementation satisfies the MVP scope defined by this specification and passes the minimum MVP compliance scenarios in Section 7.5.

The MVP may be verified with different executor configurations. A conformance declaration must identify which executor configuration was tested. At minimum, the following conformance profiles may be declared:

- **Core MVP compliant with stub executor**: task intake, persistence, API behavior, manifest and job-order preparation, canonicality, idempotency, finalization, recovery, and CLI behavior are verified with a deterministic executor stub.
- **Core MVP compliant with `slurm-native` adapter**: the same core behavior is verified with the SLURM execution adapter, native node wrapper execution, scheduler-facing polling, cancellation where configured, and reconciliation behavior.
- **Core MVP compliant with `slurm-docker` adapter**: the same core behavior is verified with the SLURM execution adapter plus Docker container launch from the SLURM node wrapper, container cleanup on cancellation, and scheduler-facing reconciliation behavior.
- **MVP compliant with rolling archive publication**: core MVP behavior plus configured rolling archive input resolution and validated-output publication are verified.
- **MVP compliant with split-group aggregation**: core MVP behavior plus grouped fan-out/fan-in readiness, aggregation task materialization, and aggregation input selection are verified.

A system may claim core MVP conformance while explicitly deferring advanced split-group aggregation, rolling archive publication, or other optional behavior only if those deferrals are visible in the conformance report and the implementation does not expose those features as supported.

### 7.2.3 Optional and Deferred Feature Conformance

Optional feature conformance applies to features that are permitted but not mandatory for a given conformance profile. Examples may include additional executor adapters, server-driven configuration validation endpoints, direct artifact content streaming modes, advanced split-group policies, or administrative operations not required for the MVP.

Optional features must follow the same rule as mandatory features: a feature must not be claimed as supported unless required behavior and required verification are both implemented.

Deferred features must be listed in the conformance evidence. A deferred feature must not be represented through API, CLI, documentation, or configuration defaults as fully supported.

### 7.2.4 Non-Conformance and Known Deviations

Known deviations from this specification must be documented. A deviation may be acceptable for internal prototypes, but it must not be hidden in a conformance claim. The conformance report must identify the affected requirement, observed behavior, risk, mitigation, and planned resolution or permanent scope limitation.

## 7.3 Test Taxonomy

A conforming implementation must use a structured verification suite. The suite may be organized according to implementation needs, but it must cover the categories in this section.

### 7.3.1 Unit Tests

Unit tests verify isolated behavior of validation logic, state transition rules, fingerprint input construction, manifest entry normalization, path containment checks, output validation helpers, API representation mapping, CLI argument handling, and error mapping.

Unit tests must not be the only verification evidence for behavior that depends on persistence, filesystem side effects, scheduler interaction, API compatibility, or recovery.

### 7.3.2 Database and Migration Tests

Database tests verify schema constraints, required record classes, referential integrity, immutability enforcement, uniqueness constraints, transactional behavior, projection rebuildability, and migration correctness.

Migration tests must demonstrate that persisted records retain their meaning across schema changes. A migrated run must continue to reference the same task, station revision, working root, manifest, artifacts, jobs, processing fingerprint, and canonicality records according to the pre-migration semantics.

### 7.3.3 API Contract Tests

API contract tests verify request and response shapes, required fields, version signaling, endpoint behavior, error response structure, pagination behavior, deterministic ordering, consistency semantics, canonical versus non-canonical visibility, artifact and log access behavior, and tolerance for additive optional fields.

API contract tests must verify both successful and failing requests. They must preserve the machine-readable server error codes defined by the API error model.

### 7.3.4 Integration Tests

Integration tests verify behavior across the backend, database, shared filesystem abstraction, station configuration store, executor adapter, and API. Integration tests must exercise real persistence and realistic filesystem side effects, even when the executor is a stub.

Integration tests should use deterministic station configurations and deterministic input fixtures so that manifests, fingerprints, job orders, and output validation results are reproducible.

### 7.3.5 End-to-End Workflow Tests

End-to-end workflow tests verify complete operator-visible workflows from submission through run preparation, dispatch, execution result observation, finalization, artifact recording, canonicality decision, downstream routing where applicable, and API or CLI query.

End-to-end tests must not treat scheduler success alone as success. They must verify output validation, artifact persistence, canonical classification, and API visibility.

### 7.3.6 Crash-Recovery and Reconciliation Tests

Crash-recovery tests verify behavior after failure at defined persistence and side-effect boundaries. They must demonstrate that restart either resumes the operation safely, completes an idempotent reconciliation, marks the run failed, or classifies uncertain state as orphaned or requiring operator reconciliation according to the lifecycle rules.

These tests must inject failures between database commits, filesystem writes, scheduler submissions, artifact discovery, artifact metadata commits, canonicality commits, downstream task creation, and cancellation transitions.

### 7.3.7 Executor-Adapter Contract Tests

Executor-adapter tests verify the stable executor contract for submission, query, cancellation where supported, scheduler identifier persistence, scheduler-native state observation, uncertainty handling, and reconciliation.

The SLURM adapter must be tested with SLURM-specific scheduler responses when claiming SLURM conformance. A stub executor may be used for core control-plane conformance, but a stub executor claim must not be represented as SLURM adapter conformance. `slurm-native` conformance must verify wrapper generation, effective `sbatch` arguments, runtime environment injection, independent stdout and stderr logs, exit-code marker handling, scheduler state mapping, and cancellation behavior when `scancel` is configured. `slurm-docker` conformance must additionally verify Docker command construction, station-declared image use, configured bind mounts, user mapping, environment propagation into the container, container cleanup on termination signals, and failure when a station omits the required image.

### 7.3.8 CLI Conformance Tests

CLI tests verify command mapping to API operations, output modes, stdout and stderr separation, exit-code mapping, configuration precedence, profile selection, compatibility behavior, and thin-client constraints.

CLI conformance tests must demonstrate that state-changing CLI commands call only the REST API and do not mutate VeriProc control-plane state through any local alternate path.

### 7.3.9 Backward-Compatibility Tests

Backward-compatibility tests verify that supported API versions, persisted records, migration paths, CLI output contracts, and client-facing error codes remain compatible according to documented versioning policy.

When an incompatible change is intentionally introduced, tests must verify that the version boundary is explicit and that older clients fail clearly rather than receiving silently reinterpreted semantics.

## 7.4 Invariants That Must Be Verified

The following invariants must be verified by automated tests for any implementation claiming the corresponding behavior.

State names used in this chapter refer to the run lifecycle and persistence semantics defined in Sections 2.10 and 4.5, and to the API state and consistency semantics defined in Section 5.6. This chapter does not introduce additional run states.

### 7.4.1 Identity and Immutability Invariants

Tests must verify that task routing content is immutable after task creation. Destination `station_id`, processing window, force flag, parent references, split-group association when created by authorized backend workflows, and client metadata must not be changed by later run lifecycle updates.

Tests must verify that task identity, task-scoped run identity `(task_id, retry_index)`, job identity, station revision identity, artifact identity, split-group identity, and processing fingerprint identity are distinct and are not reused in a way that obscures provenance or lifecycle semantics.

Tests must verify that station identity is represented by `station_id`, that `station_name` is operator-readable only, and that active `station_id` and `station_name` values are each unique within the deployment scope.

Tests must verify that canonical identifiers are opaque durable identifiers and that task IDs, job IDs, artifact IDs, and split-group IDs do not encode parent run references, downstream ordinals, provenance hints, retry reasons, scheduler IDs, or working-root paths. Task IDs may include the destination `station_id` as an operator-readable prefix and may use either the configured task creation time or task processing-window start time as their timestamp segment. Tests must verify that the prefix matches the task's destination `station_id`, that `naming.task_id_timestamp` defaults to `creation`, that both `creation` and `start` policies produce the expected timestamp segment, that clients and backend code continue to use explicit API fields rather than parsing the task ID for authoritative window state, that the full task identifier remains globally unique within the deployment scope, and that a bare `station_id` is not accepted as a task identity. Tests must verify that the run display form, when shown, is derived from `task_id` and `retry_index` rather than treated as a separate opaque canonical ID.

Tests must verify that retrying a task creates a new run key `(task_id, retry_index)` and does not mutate the identity of an existing run.

Tests must verify that each run has a unique working root path and that retries for the same task do not reuse or overwrite a prior run's working root.

Tests must verify that readable working-root paths are generated by expanding `naming.working_root.path_template` under the configured shared-storage root, obey the effective instance naming policy, use compact UTC timestamp segments when configured, and remain distinct from run identity. Conformance tests must cover both a nested layout such as `{station}/{task}/{run}` and a flat layout such as `{task}-{run}` without requiring a custom generator.

Tests must verify determinism for the same validated run context, uniqueness once assigned, containment under `working_root_base`, correct expansion of `{station}`, `{task}`, and `{run}` from the normalized segment templates, and rejection of unsupported placeholders. Tests must reject absolute templates, expanded paths that escape `working_root_base`, empty path components after normalization, and `.` or `..` semantics after expansion and normalization.

If the readable expanded path can collide, tests must verify deterministic collision disambiguation. The configured `collision_suffix` must be appended only to the final expanded path component, must not be added when there is no collision, must not reorder readable components already produced by the path and segment templates, and must not be treated as a second run identifier.

### 7.4.2 Execution Context Invariants

Tests must verify that the resolved input manifest is persisted and frozen before dispatch, consistent with the run persistence rules in Section 4.3.7 and the manifest record rules in Sections 4.3.9 and 4.3.10. Once a run enters dispatching, the resolved input set for that run must not change.

Tests must verify that each input's effective `filename_pattern` is determined correctly from station-local override or instance-wide default, and that any `<FILE_TYPE>` placeholder is substituted from the declared input or output definition rather than inferred from discovery side effects.

Tests must verify that the top-level instance configuration defines the global component rules for supported filename placeholders and that those rules are enforced consistently across all station-local `filename_pattern` overrides.

Tests must verify that mandatory missing inputs prevent dispatch and that optional missing inputs are recorded explicitly.

Tests must verify structured filename parsing for the supported placeholder vocabulary, including extraction of mission identifier, start timestamp, end timestamp, generation timestamp, and parsed file type when the effective pattern contains `<FILE_TYPE>`.

Tests must verify fixed positional extraction according to the effective `filename_pattern` and global component definitions, including wildcard semantics such as `MISSION_ID = CDM?`, fixed-width extraction such as `FILE_TYPE = 16 ASCII characters`, and timestamp parsing for the configured `YYYYMMDDTHHmmSSZ` shape.

Tests must verify the interval-matching policies `overlaps`, `within_window`, and `covers_window`, including the effect of any declared time margins on the effective processing window before the interval comparison is evaluated.

Tests must verify task submission timestamp parsing for processing-window `start` and `end` values. Required accepted forms include RFC 3339 whole-second timestamps, RFC 3339 millisecond timestamps, RFC 3339 timestamps without an explicit timezone (interpreted as UTC), compact UTC seconds `YYYYMMDDTHHmmSS`, compact UTC milliseconds `YYYYMMDDTHHmmSSmmm`, ISO 8601 date `YYYY-MM-DD` (midnight UTC), and compact date `YYYYMMDD` (midnight UTC). Tests must verify UTC normalization and rejection of malformed compact or RFC 3339 timestamp values.

Tests must verify the classical input matching algorithm for structured filename selection. The test suite must cover full scanning of all configured folders, earliest-folder user priority as a final tie-break rather than an early-exit rule, grouping by declared input type plus parsed start and end timestamps, and one selected winner per logical interval group.

Tests must verify deterministic winner selection within a logical interval group by most recent real generation time, then lexicographically greatest post-generation discriminator or suffix, then highest-priority source folder, then the documented stable fallback. If the configured filename contract permits a dummy or unknown generation-time sentinel such as `yyyymmddTHHMMSS`, tests must verify that the sentinel ranks below every real parsed generation time.

Tests must verify that the algorithmic shape is identical for regular-file and directory candidates: both are matched by entry name under the effective `filename_pattern`, both can participate in logical interval grouping, and both use the same winner rule subject only to declared `object_kind` filtering.

Tests must verify the default integrity policy `available_only`: input resolution and manifest freezing must record size, modification time, version metadata, and checksum metadata when available, but must not require full-file checksum computation.

Tests must verify that a resolved input may be a directory whose entry name matches the effective naming convention, that directory inputs are materialized into `working_root/input/` as symlinks to the selected source directory root, and that manifest entries preserve object kind for regular-file and directory inputs. Directory inputs must not require MD5 or other recursive checksum calculation for manifest freezing.

Tests must verify that manifest freezing persists the effective `filename_pattern`, applied `window_match` policy, parsed filename metadata, logical interval grouping key, source folder priority, and winner comparison metadata needed to explain the selected candidate set. Tests must verify the working-root manifest export carries the same traceability fields as the persisted manifest entries.

Tests must verify that debug-level server logs emitted during input resolution are sufficient to trace the classical matching decision for a run. Logs must identify the declared input, effective pattern, resolved folder list or folder priorities, candidate parse and window-filter outcomes at debug level, grouping key, winner comparison keys, and selected source path without requiring full file reads or recursive directory inspection.

Tests must verify that the processing fingerprint is computed after the execution context is frozen and before the run is eligible for dispatch, consistent with Sections 4.3.7 and 4.3.17. The fingerprint must include the output-affecting context required by the specification and must remain immutable once computed.

Tests must verify station context-reference resolution. The suite must cover instance `definitions` injected at the context root, nested references such as `<facility.processing_center>`, full-node substitution preserving mapping or list types, embedded scalar interpolation, rejection of missing references, rejection of reserved-name collisions, preservation of structured filename placeholders such as `<MISSION_ID>`, and freezing of resolved output-affecting values before dispatch. Tests must also verify that `instance_root` (the absolute directory of the loaded instance config file) is injected as a reserved runtime key and is available in all context-resolved fields including `preprocess_script` and `preprocess_args`.

Tests must verify instance `execution_env` handling. The suite must cover loading operator-defined variables from instance configuration, rejection of invalid names and the reserved `VERIPROC_` prefix, propagation into local and SLURM executor wrappers, propagation into Docker container environments for `slurm-docker`, and non-overriding behavior for VeriProc-defined runtime variables.

Tests must verify structured execution configuration. The suite must cover `execution.executable`, `execution.args`, context-resolved argument values such as `<start>`, `<end>`, `<run_ref>`, and `<joborder>`, string argument passing without shell interpretation by default, and failure when an argument references a value unavailable for the station's declared joborder mode.

Tests must verify SLURM executor configuration merging. The suite must cover instance-level defaults for connection, partition, account, QoS, poll commands, cancellation command, and default resources; station-level overrides for partition, account, QoS, CPUs, memory, walltime, extra allowed scheduler arguments, and container image; rejection of unsupported or unsafe scheduler options; canonicalization of `plain-slurm` to `slurm-native` and `docker-slurm` to `slurm-docker` when aliases are accepted; and persistence or API exposure of the effective executor mode.

Tests must verify that the default joborder renderer supports `yaml`, `toml`, `json`, and `none`. For `yaml`, `toml`, and `json`, tests must verify that the generated job order places VeriProc-owned identity and audit fields under `veriproc_meta` unless `joborder.meta: false` is explicitly declared, keeps workload-facing `order`, `inputs`, and `outputs` at the root, references the frozen task, run, station revision, processing window, resolved non-reserved `joborder.include` content, manifest reference where present, resolved inputs, and expected outputs according to the job-order schema. Tests must verify that `joborder.meta: false` omits only the serialized metadata block and does not suppress persisted audit records. For `none`, tests must verify that no joborder file or artifact is created, `VERIPROC_JOBORDER_PATH` is not injected, and references to `<joborder>` or `<joborder.path>` fail before dispatch.

Tests must verify the built-in template joborder renderer. The suite must cover `joborder.renderer: template`, inline templates and station-directory-relative `template_file` loading, template content inclusion in station revision identity, context-resolved `joborder.params`, input lookup helpers, path helpers, `yamlq`/`tomlq`/`jsonq` quoting helpers, declared format validation after rendering, failure on missing or ambiguous required input lookup, rejection of `joborder.include` with the template renderer, and support for processor-specific schemas that do not contain VeriProc root fields.

Tests must verify `joborder.include` merge behavior. The suite must cover context resolution before merge, deterministic deep merge for non-reserved mappings, insertion of scalar and sequence fields, allowed fields such as `facility`, `dyn_params`, `temporary_folder`, `config_files`, and `log_level`, and rejection of attempts to override reserved fields such as `veriproc_meta`, `order`, `inputs`, or `outputs`, as well as legacy top-level VeriProc metadata names such as `schema_version`, `joborder_id`, `task_id`, `retry_index`, `run_ref`, `station`, `generator`, or `manifest`.

Tests must verify `joborder.preprocess_script` behavior. The suite must cover:
- When `preprocess_script` is set, the script is executed **before** the job order is rendered and after the resolved manifest and execution context are frozen.
- `KEY=VALUE` lines written to stdout by the script are parsed and made available as `<prep.KEY>` in `joborder.include` leaves (default renderer) and as `.PrepVars["KEY"]` in the Go template context (template renderer).
- Blank lines and lines beginning with `#` in the script's stdout are silently ignored.
- Any stdout line that is not a valid `KEY=VALUE` pair, not blank, and not a `#` comment causes the run to fail immediately with an error naming the script.
- A non-zero exit code from the script causes the run to fail immediately with an error naming the script and the exit code.
- `{input:FILE_TYPE}` tokens in `preprocess_args` are replaced by the space-joined absolute (or relative, depending on `paths` mode) paths of all present manifest entries of the given file type before the script is invoked.
- `{input:FILE_TYPE}` referencing a file type with no present manifest entries causes the run to fail before the script is invoked.
- Context references (`<name.path>`) in `preprocess_args` elements and in `preprocess_script` itself are resolved against the standard station context before script invocation; `<instance_root>` in particular must resolve to the directory of the instance config file.
- Failures during preprocess script execution transition the run to `failed` and mark the task `failed` (i.e., `preprocess_script` failures are treated as fatal dispatch errors).

Tests must verify that local execution captures standard output and standard error independently as `logs/run_out.log` and `logs/run_err.log`, and that both log files are represented as log artifacts for completed and failed runs.

### 7.4.3 Run Completion and Artifact Invariants

Tests must verify that scheduler success alone does not transition a run to `complete`.

Tests must verify that completion requires output validation, persistence of required artifact metadata, canonicality decision, and downstream reconciliation or documented asynchronous routing policy.

Tests must verify that mandatory output artifacts are validated before the run reaches `complete` and that artifact records identify producing run, logical artifact type, path or access reference, validation status, size when available, checksum metadata when available under policy, and publication status when applicable.

Tests must verify that a declared output's `directory` field, when set, is resolved via the station context before the job order is written and before output validation. The resolved path must appear in the job order under `outputs[].directory`, and the daemon must look in that directory (not the default `output/`) when validating produced files. When `directory` is absent the default `<working_root>/output/` behaviour must be preserved. Context references including `<working_root>` and `<instance_root>` must be supported in `directory` values.

Tests must verify that a declared output may be a directory whose entry name matches the effective naming convention, that directory outputs can be recorded as artifacts with object-kind metadata, and that baseline completion does not require recursive child inspection or recursive checksum validation for directory outputs.

Tests must verify that rolling-archive publication defaults to the archive root and does not create an implicit station-specific directory. When an explicit publication subpath is configured, tests must verify that publication uses exactly that declared subpath and rejects paths that would escape the archive root.

When directory output publication is supported, tests must verify that directory outputs can be copied or moved to rolling-archive or equivalent targets as opaque directory trees, or symlinked at the directory root when policy allows it, without requiring per-child checksum verification.

Tests must verify that checksum generation during output validation occurs only when required by station or deployment integrity policy. Under `available_only`, run completion must remain valid without system-computed checksums.

Tests must verify that artifact bytes and artifact metadata remain distinguishable. If artifact bytes become unavailable due to retention or storage failure, artifact metadata must remain queryable according to retention policy.

### 7.4.4 Canonicality and Deduplication Invariants

Tests must verify that at most one current canonical completed run owns a processing fingerprint under the default deduplication policy.

Tests must verify that a completed duplicate run does not silently replace the canonical owner of the same fingerprint.

Tests must verify that forced runs are non-canonical by default unless an explicit promotion or replacement operation or policy is implemented and verified.

Tests must verify that `latest_run` and `canonical_run` are exposed distinctly through the API and, when applicable, through the CLI. The latest run must not be implied to be canonical unless it is explicitly classified as canonical.

### 7.4.5 Idempotency and Retry Invariants

Tests must verify that repeated task submission with the same idempotency key and the same canonical request content returns the same logical task result.

Tests must verify that repeated task submission with the same idempotency key and conflicting canonical request content is rejected as an idempotency conflict and does not create or mutate a task.

Tests must verify retry-safe run creation for a given retry request or task attempt. Retried preparation must not create duplicate active canonical work for the same task and fingerprint.

Tests must verify that downstream task creation, artifact recording, rolling archive publication when supported, split-group creation, split-group readiness transitions, and deduplication record creation are idempotent or protected by uniqueness constraints.

### 7.4.6 Scheduler and Recovery Invariants

Tests must verify safe handling of scheduler submission uncertainty. If scheduler submission may have succeeded but the scheduler identifier is not durably persisted, restart must enter reconciliation or orphan-handling logic before any resubmission decision.

Tests must verify that the backend does not blindly submit a second job for the same run after uncertain scheduler submission.

Tests must verify that cancellation state is persisted and recoverable. A crash during cancellation must not delete run, job, working-root, artifact, or provenance records.

### 7.4.7 Provenance and Split-Group Invariants

Tests must verify that provenance links are persisted independently of readable task history.

Tests must verify that an artifact returned by the API can be attributed to the run that produced it.

Tests must verify that downstream tasks created by a completed run have machine-queryable provenance links to the producing run.

When split groups are supported, tests must verify that split-group membership, closure, readiness, grouped evaluation state, aggregation task creation, and aggregation input selection are based on persisted split-group records and canonical child-task results, not on inferred filesystem state, rolling archive scans, filename patterns, overlapping time ranges, or readable routing-history text.

When aggregation is supported, tests must verify that an aggregation task references exactly one split group and that its input manifest records the selected contributing child artifacts and producing child runs where available.

### 7.4.8 CLI Thin-Client Invariants

If a CLI is provided, tests must verify that the CLI does not compute processing fingerprints, decide canonicality, evaluate split-group readiness, reconcile scheduler state, resolve rolling archive inputs, create downstream tasks, or mutate database records locally.

Tests must verify that CLI commands that inspect or change VeriProc state map only to documented API operations and do not bypass the API through direct filesystem, scheduler, or database access.

## 7.5 Minimum MVP Compliance Scenarios

The MVP reference implementation must pass the scenario set in this section for its claimed conformance profile. The scenario set is a minimum. Implementations should add additional tests for deployment-specific policy, executor behavior, station configurations, and optional features.

For the **core MVP compliant with stub executor** profile, all core invariants in Section 7.4 are mandatory except those explicitly scoped to unsupported optional features. Rolling archive publication, split-group aggregation, SLURM-specific behavior, and CLI behavior are mandatory only when the corresponding feature or profile is claimed. Unsupported or deferred features must still be declared according to Section 7.10.

### 7.5.1 Task Submission and Idempotency

The implementation must pass these scenarios:

- submit a valid task and persist the immutable task record before any run is created
- retry submission with the same idempotency key and the same canonical request content, returning the same logical task result
- retry submission with the same idempotency key and conflicting canonical request content, returning an idempotency conflict without creating or mutating a task
- reject a task with invalid timestamp ordering before task creation
- reject an unknown or ambiguous destination before task creation
- persist the force flag default as `false` when omitted

### 7.5.2 Run Preparation

The implementation must pass these scenarios:

- create a run for an accepted task with a distinct task-scoped run key `(task_id, retry_index)`
- resolve inputs according to configured product categories, station input definitions, and the classical input matching algorithm
- persist a frozen resolved input manifest before dispatch
- export a working-root manifest that makes the selected input set and classical matching decision traceable
- record missing optional inputs explicitly
- fail preparation before dispatch when a mandatory input is missing
- compute and persist the processing fingerprint after manifest and execution context freeze and before dispatch
- create a unique working root for the run
- verify that the working root is produced by the effective path template, remains under `working_root_base`, and is stored as a non-identity path
- write a schema-valid joborder before scheduler submission for `yaml`, `toml`, and `json` formats, or record the explicit `none` contract and dispatch without a joborder artifact only when station execution does not reference a joborder path

### 7.5.3 Dispatch and Executor Behavior

The implementation must pass these scenarios:

- dispatch a prepared run through a deterministic stub executor for core MVP conformance
- persist job identity and scheduler identity as soon as scheduler identity is known
- expose job status through the API with last-observed timestamps when scheduler-derived state is returned
- reconcile an uncertain scheduler submission without blindly submitting a duplicate job for the same run
- verify runtime environment injection through executor-adapter contract tests where the executor launches a process

An implementation claiming `slurm-native` or `slurm-docker` conformance must also pass equivalent scenarios using the relevant SLURM adapter mode and representative SLURM responses.

### 7.5.4 Finalization and Canonicality

The implementation must pass these scenarios:

- observe scheduler terminal success without immediately marking the run `complete`
- validate mandatory output artifacts before completion
- persist artifact metadata before completion
- record validation failure and transition to failed state when mandatory output validation fails
- create or preserve the canonical deduplication owner for the processing fingerprint during finalization
- prevent a forced rerun from silently replacing the canonical completed run
- expose canonical versus latest run correctly in task and run API responses
- preserve auditability across backend restart after finalization

### 7.5.5 API and Error Behavior

The implementation must pass these scenarios:

- return required success representations for task, run, job, artifact, log, relationship, health, and readiness endpoints that are within the claimed profile
- return required machine-readable error bodies for invalid request, not found, conflict, cancellation unsupported, reconciliation in progress, dependency unavailable, and internal error cases
- support pagination and deterministic ordering for list endpoints
- expose committed database-backed control-plane state through read endpoints
- distinguish scheduler-derived last-observed state from committed run state
- tolerate additive optional fields in client-facing contract tests

### 7.5.6 CLI Behavior

If a CLI is included in the claimed profile, the implementation must pass these scenarios and the requirements in Section 7.9. If no CLI is shipped or claimed, this scenario block is not mandatory for backend-only conformance.

- submit a task through the CLI and verify that the CLI used the task-submission API operation
- run `task get`, `task list`, `run get`, `run list`, `job get` or `run jobs`, `artifact list`, `logs`, `relationships`, `cancel`, `health`, `readiness`, and `version` command equivalents against API fixtures or a test backend
- verify `--output json`, `--output yaml`, and `--output table` where applicable
- verify that primary payloads are written to standard output and diagnostics to standard error
- verify CLI exit-code mapping for success, usage error, validation error, not found, conflict, authentication or authorization failure, unavailable or timeout, and indeterminate state-changing outcome
- verify that the CLI fails clearly when the backend API version is unsupported
- verify that the CLI does not access working roots, rolling archives, the database, or scheduler commands as a control-plane path

### 7.5.7 Cancellation and Restart Auditability

The implementation must pass these scenarios:

- request cancellation of a pending or running run through the API
- distinguish cancellation request accepted from terminal `cancelled` state
- handle repeated cancellation requests according to API policy
- preserve run, job, artifact, working-root, and provenance records after cancellation
- restart after task creation, run preparation, dispatch, finalization, and cancellation failure injection while preserving enough state for API audit queries

## 7.6 API Compliance Requirements

API compliance tests must verify all required API behavior within the claimed conformance profile.

The API must expose explicit version selection or version signaling according to its documented versioning mechanism. Tests must verify that supported versions are accepted, unsupported versions fail clearly, and compatibility metadata is exposed where the implementation claims to provide it.

Tests must verify that required endpoints exist for the claimed profile. For the MVP profile, this includes task submission, task query, run query, job query, artifact metadata query, log metadata or content access, relationship query, cancellation where supported, health, and readiness.

Tests must verify the stable error model defined in Chapter 5. Error responses must include machine-readable error code, human-readable message, and request correlation identifier when available. Field-level validation details, retryability indicators, dependency names, and conflicting resource identifiers should be verified where the API returns them.

Tests must verify pagination and deterministic ordering for list endpoints. Pagination tests must include stable ordering with tie-breakers and must verify that continuation tokens or offsets do not skip or duplicate records under the tested consistency model.

Tests must verify canonical and non-canonical representations. Task responses must distinguish latest run from canonical run. Run responses must expose canonical classification distinctly from run state.

Tests must verify that task and run list/query responses expose enough readable context for CLI rendering, including station, start, end, state, latest run reference, canonical run reference, retry index, canonicality, created-at timestamp, and working-root path where applicable. These fields must be separate from canonical IDs, except that a task identifier may contain the permitted `station_id` prefix and must still be validated against the explicit destination field.

Tests must verify the state consistency semantics defined in Section 5.6. Database-backed reads must reflect committed control-plane state. Scheduler-derived fields must include last-observed timestamps or equivalent metadata when returned.

Tests must verify artifact and log access behavior. Metadata access must remain attributable to producing runs and must expose object kind for artifacts. Content access must obey API access policy. Unavailable content must be distinguishable from missing artifact metadata when the API supports that distinction, and directory artifact metadata must remain queryable without implying that directory content can be streamed as regular-file bytes.

Tests must verify artifact checksum fields are optional unless integrity policy requires them, and that checksum source distinguishes values obtained from sidecars or external metadata from values computed by VeriProc.

Tests must verify machine-readable error payload stability across supported API versions. Additive optional fields must not break conforming clients or CLI tests.

Tests should verify that clients can ignore unknown optional response fields, unknown links, and new metadata blocks. Tests must not require clients to fail solely because the server adds optional fields.

## 7.7 Persistence and Migration Compliance Requirements

Persistence tests must verify that the relational state store provides the required record classes for the claimed profile, including tasks, task history entries when stored separately, provenance links or equivalent relationship records, station revisions or immutable station-registry references, runs, jobs, resolved input manifests, resolved input entries, artifacts, rolling archive publication metadata when supported, split groups when supported, processing fingerprints, deduplication records, idempotency records, instance configuration identities when persisted, and generation-hook identities when required.

Tests must verify uniqueness constraints for task identifiers, task-scoped run keys `(task_id, retry_index)`, job identifiers, scheduler identifiers when known, working-root paths, idempotency scope and key, run retry indexes within a task, manifest association, artifact identity, publication target when supported, split-group membership when supported, and canonical deduplication ownership.

Persistence tests must verify that manifest entries and publication records preserve structured filename metadata, applied interval-matching policy, effective filename-pattern identity, and root-relative publication target paths when those features are used.

Tests must verify that any denormalized station/start/end fields or materialized API projections used for operator readability can be rebuilt from authoritative task and station-revision records and are not treated as alternate identities.

Tests must verify foreign-key relationships or equivalent application-level referential guarantees. Referenced tasks, runs, jobs, station revisions, manifests, artifacts, split groups, and provenance endpoints must exist before relationships that depend on them are committed.

Tests must verify immutable and mutable field boundaries. Immutable routing content, run identity, task association, station revision, retry index, working-root path after assignment, generator identities after assignment, manifest entries after freeze, and processing fingerprint after computation must not be changed by ordinary lifecycle updates.

Tests must verify transactional behavior at external side-effect boundaries. State transitions that cross filesystem writes, scheduler submissions, artifact recording, publication, downstream task creation, split-group readiness, deduplication ownership, and cancellation must be persisted in a way that supports recovery.

Migration tests must verify schema migration correctness. A migration must not reinterpret existing run meaning, task identity, station revision identity, processing fingerprint, manifest content, canonical classification, artifact attribution, or provenance links. If a migration backfills new columns or projections, tests must verify that backfilled values are derived from authoritative normalized state.

Tests must verify that query projections can be rebuilt from normalized state when the implementation relies on denormalized summary columns or materialized views. A rebuilt projection must match the authoritative records according to documented projection rules.

## 7.8 Recovery and Reconciliation Compliance Requirements

Recovery and reconciliation tests must inject failures at defined points and verify safe restart behavior. Recoverability and safe classification of uncertain state are mandatory aspects of conformance.

The implementation must test crash or interruption after task creation but before run creation. Restart must preserve the committed task and must not create duplicate tasks for a retried idempotent submission.

The implementation must test crash or interruption after run creation but before manifest freeze. Restart must resume preparation, fail preparation deterministically, or classify the partial run according to documented lifecycle rules. It must not dispatch without a frozen manifest.

The implementation must test crash or interruption after manifest freeze but before scheduler acknowledgement. Restart must preserve the frozen manifest and processing fingerprint and must not alter the resolved input set before deciding whether dispatch can proceed or reconciliation is required.

The implementation must test crash or interruption after scheduler submission attempt with uncertain outcome. Restart must reconcile with scheduler-visible state when possible or mark the run orphaned or requiring operator reconciliation when ownership cannot be proven. It must not blindly submit a second scheduler job for the same run.

The implementation must test crash or interruption after scheduler completion but before output validation. Restart must re-enter finalization and perform output validation idempotently.

The implementation must test crash or interruption after artifact bytes exist but before artifact metadata commit. Restart must either record the artifacts idempotently, validate them according to station policy, or classify the run as failed or incomplete. It must not report completion based only on existing files.

The implementation must test crash or interruption during finalization before canonicality is committed. Restart must preserve deduplication safety and must not create multiple canonical owners for the same processing fingerprint.

The implementation must test crash or interruption after downstream tasks are created but before completion is marked. Restart must reconcile child-task creation idempotently and must not create duplicate downstream tasks or duplicate provenance links.

When rolling archive publication is supported, the implementation must test crash or interruption during publication. Restart must avoid duplicate logical publication records and must not use rolling archive retention or archive scanning as a substitute for durable run records.

When split groups are supported, the implementation must test crash or interruption during split-group creation, membership recording, closure, readiness transition, and aggregation task materialization. Restart must not mark an open or unsafe group as ready and must not create more than one aggregation task for a split group unless an explicit re-aggregation policy is implemented and verified.

The implementation must test crash or interruption during cancellation flow. Restart must preserve cancellation-request state when committed, reconcile active job state where supported, and avoid deleting audit records.

Recovery tests should be deterministic and repeatable. Failure injection points should be named in test evidence so that the conformance report can identify which recovery gaps were exercised.

## 7.9 CLI Compliance Requirements

CLI compliance applies when an implementation ships a CLI or claims reference CLI behavior. A backend may be conforming without a CLI, but a CLI that is provided as part of a conformance profile must satisfy this section.

CLI tests must verify strict API-first behavior. State-inspection commands must obtain control-plane state from API responses. State-changing commands must call documented API operations. The CLI must not mutate the database, working roots, scheduler state, rolling archive publication records, or station-derived control artifacts directly.

CLI tests must verify command-to-API mapping for submission, task retrieval, task listing, run retrieval, run listing, job retrieval, job listing, artifact listing, log access, relationship query, cancellation, health, readiness, version checking, and configuration validation when present.

CLI tests must verify output modes. Commands with structured payloads must support `--output json`, `--output yaml`, and `--output table` where applicable. Machine-readable output must use stable field names and must not include prompts, progress messages, or diagnostics on standard output.

CLI tests must verify that task-list output shows task ID, station, start, end, state, latest run reference, canonical run reference, and created-at timestamp using API-provided fields. CLI tests must verify that run-list output shows task ID, retry index, run reference, station, start, end, state, canonical classification, created-at timestamp, and working-root path when exposed by the API.

CLI tests must verify that the CLI does not parse station, time-window, retry, downstream, or provenance meaning from canonical IDs or working-root path components as authoritative control-plane state. If a task identifier includes a `station_id` prefix, the CLI must still use API-provided destination fields for filtering, display, and validation. Readable table columns and path displays must not be treated as alternate identities.

CLI tests must verify standard stream behavior. Primary payloads must be written to standard output. Diagnostics, warnings, prompts, and progress messages must be written to standard error unless a command explicitly documents another stream.

CLI tests must verify exit-code mapping according to Section 6.10 and must preserve the API error model defined in Chapter 5. Tests must cover success, usage or argument error, validation or bad request, not found, conflict or invalid state, authentication or authorization failure, unavailable or timeout, and partial or indeterminate outcome.

CLI tests must verify that the CLI does not locally reimplement backend semantics. The CLI must not compute processing fingerprints, decide canonicality, evaluate split-group readiness, reconcile scheduler state, resolve rolling archive inputs, or create downstream tasks locally.

CLI tests must verify configuration and profile precedence. Built-in defaults, configuration file defaults, selected profile, environment variables, and command-line flags must be applied in the documented order.

CLI tests must verify API compatibility behavior. If the configured backend API version is unsupported, the CLI must fail clearly before performing state-changing operations. Local-only commands such as `version` without API checking should remain usable.

CLI tests must verify that local `config validate`, when present, remains a non-mutating utility. If validation is server-driven, tests must verify that it calls a documented validation API endpoint and does not mutate server state.

## 7.10 Evidence and Reporting

An implementation claiming conformance must produce a conformance report. The report may be a document, release artifact, generated test report, or equivalent auditable record, but it must be reproducible enough for an operator or reviewer to understand what was tested.

The conformance report must include:

- implementation name and version
- specification version or document revision used for verification
- claimed conformance profile or profiles
- tested executor configuration, such as stub executor, `slurm-native`, or `slurm-docker`
- tested database backends, such as SQLite, Postgres, or both
- tested API version or versions
- CLI version and CLI test status when a CLI is included
- automated test results with pass, fail, skip, or not-applicable status
- minimum MVP scenario matrix status
- migration test results when migrations are part of the implementation
- crash-recovery and reconciliation test results
- compatibility matrix for supported API and CLI versions
- known deviations from the specification
- explicitly deferred or unsupported features
- reproducible environment notes, including operating system, database version, executor or scheduler version, and relevant configuration profiles

For each claimed conformance profile, the report should map every mandatory scenario in Section 7.5 to at least one automated test identifier or explicitly documented verification record. This mapping should be specific enough that a reviewer can distinguish tested behavior from unverified implementation intent.

Unsupported or deferred features must be declared explicitly. A feature must not be omitted from the report in a way that implies support.

Skipped tests must include a reason. A skipped test for a mandatory feature in the claimed profile must be treated as a conformance gap unless the feature is explicitly declared unsupported or deferred and the conformance profile permits that deferral.

Known deviations must include enough information for operators to assess risk. At minimum, each deviation should identify the affected requirement, observed behavior, operational impact, mitigation, and planned resolution or accepted limitation.

The conformance report should be produced automatically as part of release qualification. Manual verification may supplement automated tests, but it must not replace automated tests for required invariants and minimum MVP scenarios.
