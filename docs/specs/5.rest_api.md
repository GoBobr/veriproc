# 5. REST API and Query Semantics

This chapter defines the normative REST API contract for VeriProc clients and operators. It specifies the supported control-plane interface, resource model, request and response semantics, error model, and consistency expectations.

Unless explicitly marked informative, statements in this chapter are normative.

## 5.1 API Scope and Principles

The REST API is the only supported control-plane interface for clients. Clients must submit tasks, query state, request cancellation, and inspect provenance through the API. Clients must not mutate backend state by writing directly into working roots, modifying database records, changing rolling archive publication metadata, or editing station-derived control artifacts.

The API must expose an explicit version. The version may appear in the URL path, media type, headers, or another documented mechanism. A conforming implementation must document which API versions it serves and which compatibility guarantees apply to each version.

The API must preserve the conceptual distinction between tasks, runs, jobs, job orders, artifacts, split groups, provenance links, station revisions, and processing fingerprints. API representations may be optimized for clients, but they must not conflate these identities.

API resource identifiers must use the canonical identity model for the addressed resource. Task resources use `task_id`. Run resources use the task-scoped composite `(task_id, retry_index)`. The preferred run display form, such as `scen2-20250703T111239000-a7sf7f/r5`, may appear in responses for operator readability, but it is a rendering of the composite and not a separate API identity.

The API must expose readable task and run context through separate fields so clients can render useful tables without decoding identifiers or display references.

API operations that trigger state changes must be validated before durable side effects are committed. Retried operations must either be idempotent or report conflicts according to the idempotency rules defined in this specification.

The MVP reference implementation targets Linux clusters with shared POSIX-visible storage and may be implemented in Go. The API contract remains language-neutral and must not require Go-specific behavior from clients.

## 5.2 Resource Model

The API should expose the following principal resources.

| Resource | Purpose | Required relationships |
|---|---|---|
| Task | Immutable routing request plus backend-maintained status | May reference parent task, parent run by `(parent_task_id, parent_retry_index)`, split group, latest run retry index, and canonical run retry index |
| Run | One execution attempt for one task | Identified by `(task_id, retry_index)`; must reference one task, one station revision, one working root, and zero or more jobs |
| Job | Scheduler submission for a run | Must reference one run and may expose scheduler identifier and scheduler-native state |
| Artifact | Metadata and access handle for a filesystem object associated with a run | Must reference producing run or external origin; may reference publication records |
| Log | Log artifact or log stream associated with a run | Must be attributable to a run and represented as artifact metadata or paged log content |
| Split group | Grouped fan-out/fan-in coordination record | Must expose parent association, membership, closure, readiness, grouped evaluation state, and aggregation task when present |
| Provenance link | Machine-queryable relationship between domain objects | Must expose source, target, and relationship type |
| Station revision | Immutable station-configuration identity | Must expose enough metadata for audit and task validation diagnostics |
| Health/readiness | Operational status of the backend | May expose dependency state, migration state, scheduler adapter readiness, and storage availability |
| Metrics | Operational measurements | May be exposed through a deployment-specific metrics format |

The API may expose additional resources for instance configuration, generation-hook identities, rolling archive definitions, idempotency records, or schema metadata. Such resources must not allow clients to bypass validation or mutate control-plane state outside documented administrative operations.

## 5.3 Submission Endpoint

The API must provide a task-submission operation. The operation should be represented as `POST /tasks` or an equivalent versioned endpoint.

### 5.3.1 Request Shape

A task submission request must include:

- destination `station_id`
- processing window start timestamp
- processing window end timestamp

A task submission request may include:

- client-supplied task identifier, if accepted by deployment policy
- force flag
- parent task identifier
- parent run reference, represented by parent task identifier plus parent retry index when supplied
- split-group identifier when creating a member or aggregation task through authorized backend or operator workflows
- priority
- routing history
- client metadata
- idempotency key

The request payload may be JSON, YAML, or another structured representation supported by the implementation. The API must document supported media types. If more than one media type is supported, they must map to the same canonical task submission semantics.

### 5.3.2 Destination Rules

The request must identify a destination station through `station_id`.

Unknown station identifiers must be rejected before task creation.

### 5.3.3 Window Rules

The processing window must include start and end timestamps. Start must be less than or equal to end. Timestamp format, timezone handling, and precision must be documented. The API should accept RFC 3339 timestamps with whole-second or fractional-second precision, including millisecond precision such as `2025-07-03T11:12:39.000Z`. The API should also accept compact UTC timestamps in the forms `YYYYMMDDTHHmmSS` and `YYYYMMDDTHHmmSSmmm`, for example `20260513T131429` and `20260513T131429000`; compact forms without an explicit timezone are interpreted as UTC. Accepted timestamps should be normalized to a canonical UTC representation in responses.

### 5.3.4 Force and Parent Rules

The force flag must be persisted on the task. If omitted by the client, it must default to `false`. A forced task may create a new run, but successful forced runs must be non-canonical by default unless explicitly promoted by a documented operation or policy.

Parent task and parent run references, if supplied, must refer to existing records and must be consistent with each other when both are present. A parent run reference must include the parent task identifier and the task-scoped retry index. A bare retry index or internal run key is not a valid API parent-run reference. A task created by the backend for downstream routing must persist provenance links independently of readable routing history.

Client-created tasks should not supply split-group membership fields unless an explicit administrative or workflow API permits that behavior. Ordinary client task submission must not be able to bypass split-group policy.

### 5.3.5 Idempotency-Key Semantics

Task submission must support an idempotency mechanism. The idempotency key may be supplied in a header, request field, or both, according to implementation policy. The API must document the idempotency scope and retention window.

When the same idempotency key is reused with the same canonical request content, the API must return the same logical result. The status code may indicate that the resource already existed, but the body must identify the same task.

When the same idempotency key is reused with conflicting canonical request content, the API must reject the request with an idempotency conflict. The conflicting request must not create or mutate a task.

If a request succeeds but the client loses the response, retrying with the same key must be safe within the documented retention window.

### 5.3.6 Validation Failures and Duplicate Behavior

Validation failures must not create tasks. Validation must cover at least request shape, destination resolution, timestamp validity, parent references, split-group authorization if applicable, and schema validity of supplied routing content.

A duplicate request without an idempotency key may create a new task unless the implementation documents an additional deduplication policy. Submission idempotency deduplicates exact client retries; processing-fingerprint deduplication controls canonical execution and must not be replaced by submission idempotency.

### 5.3.7 Response Semantics

A successful submission response must include the task identifier and current task summary state. It should include links or identifiers for retrieving task detail and related runs.

If the task has been accepted but no run has been created yet, the response must make that clear. If a run is created synchronously during submission, the response may include the initial run reference, represented as `task_id`, `retry_index`, and optionally `run_ref`, but clients must still treat run creation and dispatch as separate lifecycle state.

## 5.4 Read and Query Endpoints

The API must expose database-backed query endpoints that reflect committed control-plane state at minimum.

### 5.4.1 Get Task by Identifier

The API must provide an operation equivalent to `GET /tasks/{task_id}`.

The response must identify the task, destination, processing window, force flag, current task state, parent references when present, split-group reference when present, latest run when present, canonical run when present, timestamps, and links or embedded summaries for related resources according to representation policy.

If the task does not exist, the API must return a not-found error.

### 5.4.2 List or Query Tasks

The API must provide an operation equivalent to `GET /tasks`.

Supported filters should include:

- destination station identifier
- task state
- processing window overlap or containment
- creation timestamp range
- parent task identifier
- parent run reference represented by parent task identifier and parent retry index
- split-group identifier
- force flag
- canonical run presence

The API must support pagination. Ordering must be documented and deterministic. The default ordering should be by creation timestamp descending, with a stable tie-breaker such as task identifier.

### 5.4.3 Get Run for a Task

The API must provide an operation equivalent to `GET /tasks/{task_id}/runs/{retry_index}`.

The response must identify the run by `task_id` and `retry_index`, and may include `run_ref` using the preferred display form, for example `scen2-20250703T111239000-a7sf7f/r5`. The response must identify station revision, state, canonical classification, working-root path subject to access policy, processing fingerprint or fingerprint reference subject to access policy, job-order artifact, manifest reference, active job, timestamps, failure reason when present, and finalization summary when present. The working-root path is an opaque operator-visible path; clients must not infer identity or control-plane state from its component structure.

If the task or run attempt does not exist, the API must return a not-found error.

An implementation may also provide an alias equivalent to `GET /runs/{task_id}/{retry_index}` for clients that prefer a run collection path. The task-scoped form under `/tasks/{task_id}` is the preferred resource model.

### 5.4.4 List or Query Runs

The API must provide an operation equivalent to `GET /runs` and should provide `GET /tasks/{task_id}/runs` for task-scoped listing.

Supported filters should include:

- task identifier
- retry index
- station identifier or station revision identifier
- run state
- canonical classification
- processing fingerprint
- creation timestamp range
- terminal timestamp range
- scheduler identifier, when known

The API must support pagination and deterministic ordering. The default ordering should be by creation timestamp descending, with a stable tie-breaker such as `(task_id, retry_index)`.

### 5.4.5 Get Jobs for a Run or Job by Identifier

The API should provide operations equivalent to `GET /tasks/{task_id}/runs/{retry_index}/jobs` and `GET /jobs/{job_id}`.

Job responses must expose the task-scoped run reference, executor type, scheduler identifier when known, scheduler-native state, submission timestamp, last poll timestamp, cancellation timestamps when present, terminal scheduler timestamp when present, and reconciliation status when relevant.

Scheduler-native state may be stale relative to the scheduler. The response must include enough timestamp metadata for clients to understand when scheduler state was last observed.

### 5.4.6 Get Artifacts for a Run or Task

The API must provide an operation equivalent to `GET /tasks/{task_id}/runs/{retry_index}/artifacts`. It should provide an operation equivalent to `GET /tasks/{task_id}/artifacts` that resolves artifacts through task runs according to documented filters.

Supported filters should include:

- logical artifact type
- file type
- validation status
- canonical run only
- latest run only
- publication status

The response must be paginated if the artifact list may be large.

### 5.4.7 Get Logs for a Run

The API must provide a way to retrieve log metadata and should provide paged or streaming access to log content. Operations may be equivalent to `GET /tasks/{task_id}/runs/{retry_index}/logs` for log metadata and `GET /artifacts/{artifact_id}/content` or `GET /tasks/{task_id}/runs/{retry_index}/logs/{log_name}` for content.

The API must define whether logs are returned inline, by byte range, by line page, by cursor, or by a short-lived download reference. Log content access must remain attributable to the producing task-scoped run.

### 5.4.8 Get Split Group by Identifier

The API must provide an operation equivalent to `GET /split-groups/{group_id}`.

The response must expose group identity, parent association, group evaluation mode, membership basis, closure state, readiness state, grouped evaluation state, aggregation target, aggregation task when present, member summary, timestamps, and failure reason when present.

The API should provide a paginated operation equivalent to `GET /split-groups/{group_id}/members` for member task inspection.

### 5.4.9 Get Provenance or Relationships

The API must provide operations to query provenance links for a task or run, equivalent to `GET /tasks/{task_id}/relationships` and `GET /tasks/{task_id}/runs/{retry_index}/relationships`, or a generic relationship endpoint with structured source and target filters.

Relationship queries must not rely only on readable routing history. They must expose machine-queryable source object, target object, relationship type, contribution role when present, and creation reason when present.

### 5.4.10 Cancellation Endpoint

The API must provide a cancellation operation where supported by the executor and station policy. It may be represented as `POST /tasks/{task_id}/runs/{retry_index}/cancel` or an equivalent endpoint that carries both task identity and retry index.

Cancellation behavior is defined in Section 5.8.

### 5.4.11 Consistency, Pagination, Ordering, and Errors

Read endpoints backed by the database must reflect committed control-plane state. Scheduler-derived fields may lag and must expose last-observed timestamps when relevant.

Paginated list endpoints must include a documented page size limit, continuation token or offset mechanism, deterministic ordering, and an indicator of whether more results are available. Continuation tokens, if used, should be opaque to clients.

All read and query endpoints must return a stable error response body for invalid filters, invalid pagination parameters, unknown resources, unsupported operations, and dependency failures.

## 5.5 Response Representations

API responses must use stable field names and must preserve identity distinctions. Implementations may include hyperlinks, embedded summaries, or both. Examples in Section 5.12 illustrate one JSON representation.

### 5.5.1 Task Summary

A task summary must include:

- `task_id`
- destination `station_id`
- processing window
- force flag
- task state
- creation timestamp
- latest run reference when present, represented at minimum by `latest_retry_index` and optionally `latest_run_ref`
- canonical run reference when present, represented at minimum by `canonical_retry_index` and optionally `canonical_run_ref`

The destination and processing-window fields are authoritative task fields, not alternate identities.

A task summary may include parent references, split-group identifier, priority, failure summary, and links.

### 5.5.2 Task Detail

Task detail must include all task summary fields plus immutable routing content, parent references when present, readable routing history when available, provenance-query link or relationship summary, client metadata when access policy permits, and related run summaries or links.

Task detail must distinguish backend-maintained mutable status from immutable routing content.

### 5.5.3 Run Summary

A run summary must include:

- `task_id`
- `retry_index`
- optional `run_ref` display string derived from `task_id` and `retry_index`
- station identity and station revision identifier
- task processing window start and end, either embedded from an API projection or through an included task summary
- run state
- canonical classification
- creation timestamp
- terminal timestamp when present

A run summary may include scheduler identifier, active job identifier, working-root path subject to access policy, failure summary, and links. Station and task-window fields in a run summary may be projections or denormalized query aids, but they must be derived from authoritative task and station-revision records and must not be treated as alternate identities.

### 5.5.4 Run Detail

Run detail must include all run summary fields plus working-root path subject to access policy, job-order artifact identifier when present, manifest identifier when present, processing fingerprint or fingerprint reference subject to access policy, instance configuration revision when available, generator identities when available, active job, job summaries, finalization summary, failure reason, and lifecycle timestamps.

Internal reconciliation or orphan states may be exposed directly if documented. If the API maps internal states into a simplified public state model, it must still expose enough diagnostic information for operators to distinguish active execution, finalization, failure, cancellation, and reconciliation in progress.

### 5.5.5 Job Summary and Detail

A job summary must include job identifier, task-scoped run reference represented by `task_id` and `retry_index`, executor type, scheduler identifier when known, scheduler-native state, submission timestamp, and last-observed timestamp when available.

Job detail should include submission attempt number, queue or partition, cancellation fields, terminal scheduler timestamp, reconciliation status, and scheduler-native diagnostic metadata when available.

### 5.5.6 Artifact Representation

An artifact representation must include artifact identifier, producing task-scoped run reference or external origin, logical artifact type, object kind, path or access reference subject to access policy, creation or discovery timestamp, and availability status. Supported object kinds must include at least regular file and directory.

It should include file type, size when available and meaningful, checksum value, checksum algorithm, checksum source, validation status, validation summary, media type, and publication summary when available. Checksum fields may be absent or null under the default `available_only` integrity policy and may be absent or null for directory artifacts.

Job orders, manifest exports, logs, output objects, and `task-out.yaml` files must be distinguishable by logical artifact type.

### 5.5.7 Split-Group Representation

A split-group representation must include group identifier, parent task or run reference, parent window, group evaluation mode, grouped evaluation target, membership basis, closure state, readiness state, grouped evaluation state, aggregation target when applicable, aggregation task identifier when present, member counts, timestamps, and failure reason when present.

It should include selected canonical child-result summaries when available or provide a link to paginated membership details.

### 5.5.8 Error Response

Error responses must include a stable machine-readable error code, human-readable message, and request correlation identifier when available. They may include field-level validation details, retry guidance, dependency diagnostics, and links to documentation.

### 5.5.9 Paginated List Envelope

Paginated list responses must include:

- list items
- page size or limit
- next page token or equivalent continuation value when more results are available
- applied ordering
- applied filters or a request echo when practical

The envelope may include total counts if the implementation can provide them efficiently and consistently.

### 5.5.10 Canonical and Non-Canonical Visibility

Run representations must expose canonical classification explicitly. A client must be able to distinguish:

- canonical completed run
- completed non-canonical forced rerun
- completed duplicate or superseded run
- run not yet eligible for canonical classification
- failed, cancelled, or orphaned run

Task representations must expose canonical run identity when one exists, using the task-scoped run reference. If no canonical run exists, task detail must not imply that the latest run is canonical.

## 5.6 State and Consistency Semantics

Database-backed reads must reflect committed control-plane state at minimum. An implementation may provide stronger consistency guarantees, but it must document them.

Scheduler-derived fields are observations of scheduler state and may lag behind scheduler reality. The API must expose last-observed timestamps or equivalent metadata when returning scheduler-native state.

Filesystem-derived fields such as artifact availability, byte size, checksum metadata, or log tail may lag behind database state if background validation or retention has changed file availability. The API must distinguish persisted artifact metadata from live file accessibility when those can differ.

`latest_run` for a task must be determined by the backend's documented run ordering, normally run creation timestamp or retry index with a stable tie-breaker. `canonical_run` must be determined by run canonical classification and deduplication ownership, not by scheduler success or recency. Both values must be represented as task-scoped run references. `active_job` must refer to the non-terminal job currently associated with a task-scoped run under the executor policy.

A run must not be reported as complete solely because a scheduler job succeeded. Completion requires output validation, artifact persistence, canonicality decision, and downstream reconciliation according to policy.

## 5.7 Error Model

The API must use a stable error model. HTTP status codes may follow normal REST conventions, but clients must rely on machine-readable error codes for programmatic handling.

The following error categories must be represented:

| Category | Typical HTTP status | Required semantics |
|---|---:|---|
| Invalid request | 400 | Request shape, field values, filters, pagination parameters, or timestamp values are invalid |
| Unknown station | 400 or 404 | Destination `station_id` cannot be resolved |
| Idempotency conflict | 409 | Reused idempotency key has different canonical request content |
| Resource not found | 404 | Requested task, run, job, artifact, split group, or relationship does not exist or is not visible |
| Invalid state transition | 409 | Requested operation is not valid for the current resource state |
| Cancellation unsupported | 409 or 501 | Executor, station policy, or deployment does not support cancellation for the target run |
| Reconciliation in progress | 409 or 423 | Scheduler submission or run ownership is uncertain and requires reconciliation before the operation can proceed |
| Dependency unavailable | 503 | Database, scheduler, shared storage, station registry, or rolling archive dependency is unavailable |
| Internal error | 500 | Unexpected backend failure |

Error response bodies must include:

- `error.code`
- `error.message`
- request identifier or correlation identifier when available

Error response bodies should include:

- field-level validation details when applicable
- retryability indicator when useful
- dependency name for dependency failures when safe to expose
- conflicting resource identifier for idempotency conflicts when safe to expose

The API must not expose sensitive scheduler, filesystem, or configuration details beyond deployment access policy.

## 5.8 Cancellation Semantics

Cancellation is a request to stop or prevent further execution of a run. It is not a deletion operation.

Cancellation may be allowed only when the run is in a cancellable state, such as `pending`, `preparing`, `dispatching`, `dispatched`, or `running`, according to executor and station policy. Cancellation of `finalizing` runs may be allowed only if the implementation can preserve consistency of validation, publication, deduplication, and downstream effects.

If the executor supports cancellation and the run has an active scheduler job, the backend must request scheduler cancellation and persist cancellation-request state. The API response must distinguish cancellation request accepted from cancellation completed.

If the executor does not support cancellation, or station policy forbids it, the API must return cancellation unsupported or invalid state transition and must not mark the run cancelled.

If the target run is already terminal, the API should return the current terminal state and must not create a new cancellation side effect. The response may be successful idempotently or may report invalid state according to documented policy.

After a cancellation request is accepted, subsequent run queries must expose cancellation-request state until the run reaches `cancelled`, `failed`, `complete`, `orphaned`, or another documented terminal or reconciliation state. A run may fail or complete despite a cancellation request if the scheduler or backend observes that execution had already passed the cancellation point; the final state must be persisted and queryable.

Cancellation must not remove working roots, artifacts, logs, jobs, or provenance records. Cleanup is governed by retention policy.

## 5.9 Artifact and Log Access

Artifact metadata must be queryable independently of content access. Metadata responses must identify the artifact, producing run, logical type, object kind, path or access reference subject to policy, size when available and meaningful, checksum, validation status, availability, and publication summary when available.

Regular-file download or streaming may be represented by direct API streaming, ranged content endpoints, pre-signed references, or deployment-specific file access handles. Directory artifact content access is not implied by metadata availability; if supported, the API must document whether access is by directory reference, packaged archive, recursive listing, or another policy-controlled mechanism. The API must document which method is used and must preserve access control and audit requirements.

Log access may be inline, paged by line or byte range, cursor-based, streaming, or by artifact download. If logs may be large, the API should avoid requiring clients to retrieve the whole log in one response.

The job order and exported manifest must be exposed as audit artifacts when allowed by access policy. `task-out.yaml` must be exposed as an audit artifact when present and allowed by access policy. Their artifact metadata must remain attributable to the run. The API may expose parsed summaries for convenience, but the artifact record must remain the durable reference.

If artifact bytes are unavailable due to retention, deletion, or storage failure, metadata queries should still succeed and must report unavailable content distinctly from missing artifact metadata.

## 5.10 Split-Group and Provenance API Exposure

Split-group API responses must allow clients and operators to inspect grouped fan-out/fan-in behavior without relying on routing-history text or archive scans.

For a split group, the API must expose:

- group identifier
- parent task or run
- parent processing window
- group evaluation mode
- membership basis
- closure state
- readiness state
- grouped evaluation state
- grouped-evaluation window override when present
- aggregation target when present
- aggregation task when materialized
- member counts by membership and contribution state
- failure or timeout reason when present

The API should expose paginated member details including child task identifier, child key, expected child window when present, membership state, canonical contributing run when available, selected contributing artifacts when available, exclusion status when applicable, and readiness contribution state.

The API must make clear that readiness and aggregation are evaluated per `group_id`. Clients must not infer group membership from station identity, product type, filename pattern, archive location, overlapping time range, or routing-history text.

Provenance queries must expose machine-queryable links between tasks, runs, artifacts, split groups, and aggregation results. At minimum, clients must be able to determine:

- which run produced an artifact
- which resolved inputs were consumed by a run when those inputs reference prior VeriProc artifacts
- which producing run created a downstream task
- which tasks belong to a split group
- which aggregation task and run consumed selected child results

Readable task history may be returned for human inspection, but it must not be the only API representation of provenance.

## 5.11 Operational and Compatibility Notes

The API versioning strategy must define how clients select a version and how long supported versions remain available. Backward-compatible changes may include adding optional response fields, adding new filter parameters, adding new enum values under an unknown-value handling policy, and adding new resource links.

The API must not remove required fields, change field meanings, change identity semantics, or reinterpret lifecycle states within a version without a documented compatibility break.

Clients should ignore unknown fields. Clients must not assume that absence of an optional field has the same meaning as a false value unless the field definition says so.

Implementations should expose health and readiness endpoints for operations. A health endpoint may report process liveness. A readiness endpoint should report whether required dependencies such as the database, scheduler adapter, station configuration source, shared storage, and rolling archive configuration are usable for control-plane operations.

Metrics endpoints may be deployment-specific. If exposed, they should not be required for correctness of client workflows.
