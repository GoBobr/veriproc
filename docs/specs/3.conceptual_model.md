# 3. Conceptual Model and Terminology

This chapter defines the domain entities used by VeriProc. Each entity is specified using a fixed template so that implementers can answer the same questions consistently: what the entity is, who creates it, what fields it carries, whether it is mutable, what validation applies, how it is persisted, and how failure is handled.

Unless otherwise stated, every persisted entity must have exactly one canonical identity model. Most persisted entities use a single canonical identifier that is globally unique within the deployment scope. Runs are the exception: because a run is defined only as an attempt for one task, the canonical run identity is composite and task-scoped.

Task identifiers remain single dedicated canonical identifiers. The preferred external grammar is `stationid-YYYYMMDDThhmmssmillis-HEX6suffix`, or another deployment-approved task key shape with equivalent uniqueness. The timestamp segment in the preferred grammar is generated from the configured instance policy and may represent task creation time or task processing-window start time. The optional station prefix and configured timestamp segment are operator-readable generation components, not separate task identities. Job identifiers, artifact identifiers, split-group identifiers, station revision identifiers, and processing fingerprint identifiers likewise remain distinct canonical identifiers for their own concepts.

A run is canonically identified by `(task_id, retry_index)`. `retry_index` is a non-negative integer scoped to the parent task and starts at `0`. It is not globally unique and has no meaning without `task_id`.

Human readability belongs in presentation and path naming, not in hidden alternate identities. CLI tables, API projections, and working-root paths may show station, time-window, state, retry index, and run display references as separate fields or generated path components. Those fields and path components are not alternate identifiers.

The preferred operator-facing run display form is `<task_id>/r<retry_index>`, for example `scen2-20250703T111239000-a7sf7f/r5`. This display form is a compact rendering of the composite key. It must not be treated as a new durable identifier or parsed for meaning other than its two API-provided components.

Implementations must not derive task identifiers by concatenating parent run references, downstream ordinals, station names, provenance hints, human-readable lineage fragments, or similar context. Provenance, downstream derivation, split-group membership, parent-child links, retry history, and run attempt identity must be represented by explicit fields and relationships.

## 3.1 Station

**Purpose**

A station is the declarative specification of one processing step.

**Required fields**

- `station_id`
- `station_name`
- execution mode
- execution image or executable reference
- command template
- resource requirements
- input definitions
- output definitions

**Optional fields**

- station-level category-folder overrides through `rolling_folders`
- per-input and per-output `filename_pattern` overrides of the instance-wide filename contract
- per-input `window_match` policy controlling interval-based candidate selection
- default downstream list
- split-group policy for station-default grouped fan-out/fan-in
- dynamic split-declaration policy for `task-out.yaml`-driven grouped fan-out/fan-in
- output publication policy, including any explicit publication subpath below the rolling-archive root
- station-specific runtime parameters
- validation hooks
- timeout policy
- cancellation policy

**Immutable vs mutable fields**

- A persisted station revision is immutable.
- The logical station identity may evolve only by creating a new revision.

**Creation trigger**

- Created by configuration load or configuration publication.

**Validation rules**

- Must validate against the station configuration schema.
- Must reference a valid execution mode.
- Must reference only declared category names in input definitions.
- Must reference only configured rolling archive identifiers when using `rolling:<id>` folder references.
- If a station input or output declares `filename_pattern`, that pattern must use the supported placeholder vocabulary defined by the instance naming policy.
- The global component rules for `MISSION_ID`, `FILE_TYPE`, `START_TIME`, `END_TIME`, and `GENERATION_TIME` must be defined in the top-level instance configuration and must remain fixed for the instance.
- If an effective `filename_pattern` contains `<FILE_TYPE>`, the placeholder value must come from the declared input or output `file_type` for that definition.
- Filename extraction must follow the fixed positional layout implied by the effective `filename_pattern` together with the global component rules; station-level overrides may change the pattern layout, but they must not change the semantics or widths of the global components.
- If a station input declares `window_match`, it must resolve to a recognized matching policy.
- Must define all mandatory output declarations needed for completion checks.
- If default downstream routing can create a split group, must define deterministic split-group policy including membership, closure, readiness, grouped-evaluation mode, and aggregation target and input-selection rules when applicable.
- If `task-out.yaml` may declare split groups, must define whether those declarations are accepted, rejected, or merged with station defaults, and how validated declarations become authoritative.

**Failure behavior**

- An invalid station revision must not be used for run generation.

**Persistence rules**

- The exact station revision used by a run must be recorded durably.

**Notes**

- `station_id` is the canonical station identity used for run generation, provenance, and runtime environment variables.
- `station_name` is a human-readable label for operator presentation purposes and must not be used as a durable station identity.
- A `station_id` value must be globally unique within the deployment scope.
- A `station_name` value must be unique within the deployment scope for operator clarity.
- `rolling_folders` is the station-level override mechanism for category folder search order. It may override top-level `product_categories` for declared input categories, but it does not define new global categories.
- A station input or output may override the instance-wide `filename_pattern` for its declared file type. If no override is present, the instance-wide default remains authoritative.
- The `<FILE_TYPE>` placeholder is a first-class component of the filename-pattern language. When used, it is substituted from the declared input or output definition rather than inferred from candidate discovery.
- The meaning of each placeholder is global to the instance. Station-level overrides may rearrange or omit placeholders in `filename_pattern`, but they must not redefine component width, wildcard semantics, or timestamp format.

## 3.2 Station Revision

**Purpose**

A station revision is the frozen identity of a station configuration at the time a run is created.

**Required fields**

- revision identifier
- station identifier
- `station_name`
- content hash or equivalent immutable revision marker
- schema version
- effective timestamp or publication version

**Optional fields**

- additional human-readable label
- source repository commit

**Immutable vs mutable fields**

- Fully immutable.

**Creation trigger**

- Created whenever a station definition changes in a way that may affect execution semantics.

**Validation rules**

- Must uniquely identify the effective configuration used by a run.

**Failure behavior**

- If no valid station revision can be resolved, task preparation must fail.

**Persistence rules**

- Must be referenced by job orders, runs, and processing fingerprints.

## 3.3 Task

**Purpose**

A task is the immutable routing request that tells VeriProc what time window to process and where to send it.

**Required fields**

- `task_id`
- destination `station_id`
- `start`
- `end`
- routing history

**Optional fields**

- parent task identifier
- parent run reference, represented as `(parent_task_id, parent_retry_index)` when the parent is a run
- split-group identifier
- submission idempotency key
- force flag for intentional reprocessing
- client metadata
- priority

**Immutable vs mutable fields**

- Routing content is immutable after creation.
- Backend-maintained status summaries may change over time.

**Creation trigger**

- Created by API submission or by downstream creation from a completed run.

**Validation rules**

- `start` must be less than or equal to `end`.
- Destination station must resolve to a known station.
- Parent references, if present, must refer to existing records.
- A split-group identifier is optional for ordinary tasks, but mandatory for tasks that are members of a split group and mandatory for aggregation tasks created for a split group.
- A forced task must be recorded as forced so that canonical and non-canonical runs remain distinguishable.

**Failure behavior**

- Invalid tasks must be rejected before dispatch planning.

**Persistence rules**

- Must be stored durably before any run is created from it.

**Notes**

- A downstream task is a new task, not a mutable extension of its parent.
- `task_id` is the task's only durable identity. A task identifier may include the `station_id` as a prefix for operator readability and may use the configured task identifier timestamp source, but it must never encode cross-entity lineage, mutable lifecycle state, scheduler identity, working-root paths, provenance hints, or other context that belongs in first-class fields and relationships.
- Task identifiers may include the `station_id` as a prefix for operator readability, but the full task identifier must remain globally unique within the deployment scope.
- If the configured task identifier timestamp source is the task processing-window start time, that timestamp segment must still be treated as opaque identifier content by clients and internal control-plane logic. The authoritative processing window remains the task's `start` and `end` fields.
- The `station_id` prefix in a task identifier must match the task's `station_id` destination field.
- A bare `station_id` is not a valid task identity and must not be treated as such.
- Operator-readable task context must be exposed through separate fields such as station identity, processing window, state, parent references, latest run reference, canonical run reference, and creation timestamp.
- When a task references a parent run, the reference must identify the parent task and the parent run's task-scoped `retry_index`. A bare retry index or internal run key is not a valid conceptual parent-run reference.
- If the force flag is omitted by a client, it must default to `false` and be persisted as such.
- Implementations may store routing history embedded in the task payload or in a separate history table. At least one durable readable history representation must exist for each task.
- A submission idempotency key identifies one client submission attempt within the configured API idempotency scope. Reusing the same key with the same submission content must return the same logical task result; reusing it with conflicting content must be rejected or reported as an idempotency conflict.
- Submission idempotency deduplicates exact client retries. It must not be used to merge merely similar tasks unless an explicit API policy defines the matching rules.
- The backend must retain idempotency records for at least the documented retry window for the API deployment.

## 3.4 Routing History

**Purpose**

Routing history is the append-only, human-readable record of stations or tasks previously traversed by the data.

**Required fields**

- ordered entries containing prior task or station identity and completion time

**Optional fields**

- short status note

**Immutable vs mutable fields**

- Existing entries are immutable.
- New downstream tasks may append new entries derived from the parent.

**Creation trigger**

- Derived when a downstream task is created.

**Validation rules**

- Entries must remain ordered and internally consistent.

**Failure behavior**

- If history cannot be extended consistently, downstream task creation must fail.

**Persistence rules**

- Stored with the task for readability and debugging.

**Notes**

- Routing history is not sufficient as the full provenance model.

## 3.5 Provenance Link

**Purpose**

A provenance link records an explicit parent-child relationship between domain objects such as tasks, runs, and artifacts.

**Required fields**

- source object type and identifier
- target object type and identifier
- relationship type

**Optional fields**

- contribution role
- creation reason

**Immutable vs mutable fields**

- Immutable after creation.

**Creation trigger**

- Created when downstream tasks, artifacts, or aggregation relationships are materialized.

**Validation rules**

- Referenced objects must exist.
- Relationship type must be recognized.

**Failure behavior**

- If required provenance edges cannot be persisted, the enclosing finalization step must fail or remain incomplete.

**Persistence rules**

- Must be queryable independently of the task history text.

**Notes**

- At minimum, downstream task creation must create a provenance link from the producing parent run to each child task. A producing run is referenced by the composite `(task_id, retry_index)`.
- Each produced artifact recorded by the backend must have a provenance link from the producing run, referenced by `(task_id, retry_index)`, to the artifact.
- Split-group membership must be represented by provenance or equivalent membership links from the split group to member child tasks and, when aggregation is materialized, from the split group to the aggregation task.
- Aggregation outputs must remain attributable to the aggregation run that produced them, while retaining links back to the split group and contributing child results.

## 3.6 Job Order

**Purpose**

A job order is the immutable execution descriptor consumed by the station algorithm.

**Required fields**

- job order schema version
- task-scoped run identity, represented by `task_id` and `retry_index`
- task identifier
- station revision identifier
- processing window
- facility block
- root-level `log_level`
- root-level `dyn_params`
- resolved input references
- expected outputs

**Optional fields**

- runtime parameters
- manifest reference
- algorithm flags
- generator identity when a custom generator is used

**Immutable vs mutable fields**

- Immutable once written.

**Creation trigger**

- Created during run preparation after input resolution succeeds.

**Validation rules**

- Must validate against the job order schema.
- All referenced paths must resolve within the working root namespace.
- Default job-order inputs should be represented as a flat list keyed by `file_type`.
- Each flat-list input entry may reference one filesystem object or multiple filesystem objects for the same `file_type`. Each object may be a regular file or a directory.
- If the job order includes a readable run reference such as `scen2-20250703T111239000-a7sf7f/r5`, that reference must be derived from `task_id` and `retry_index` and must not replace those fields.
- Custom-generated job orders must satisfy the same schema and containment rules as system-generated job orders.

**Failure behavior**

- If job order generation or validation fails, the run must not be dispatched.

**Persistence rules**

- Must be written to the working root and associated with the run record.

## 3.7 Resolved Input Manifest

**Purpose**

The resolved input manifest is the frozen record of which inputs were selected, which optional inputs were absent, and why those selections were made.

**Required fields**

- task-scoped run identity, represented by `task_id` and `retry_index`
- one entry per declared input
- selection outcome for each entry

**Optional fields**

- checksum value, checksum algorithm, and checksum source when available under the instance integrity policy
- object kind for selected inputs, with at least `regular_file` and `directory` supported
- source directory precedence
- source rolling archive identifier when selected through a rolling archive
- resolved category folder source
- effective filename pattern
- applied `window_match` policy
- parsed mission identifier
- parsed start timestamp
- parsed end timestamp
- parsed generation timestamp
- parsed file type when the effective pattern includes `<FILE_TYPE>`
- parsed post-generation discriminator or suffix when present in the effective filename pattern
- logical interval identity or equivalent grouping key when structured filename matching is used
- source folder priority used by the winner rule
- version metadata
- tie-break reason, including the classical matching comparison keys when a selected object wins over other candidates

**Immutable vs mutable fields**

- Immutable once dispatch begins.

**Creation trigger**

- Created after input resolution and before job order generation completes.

**Validation rules**

- All mandatory inputs must resolve successfully.
- Each resolved input must retain its declared category and resolved folder source.
- Each resolved input entry may bind to one or several source filesystem objects, and that multiplicity must be preserved in the manifest. When structured filename matching selects multiple objects for one declared input, those objects must represent distinct logical interval groups.
- Directory inputs must satisfy the same effective naming contract as regular files by matching the directory entry name. When materialized into the working root, the input symlink must point to the selected source directory root.
- Each resolved input selected through filename parsing must retain the effective `filename_pattern`, parsed filename metadata, applied interval-matching policy, logical interval grouping key, source folder priority, and winner comparison metadata that justified the selection.
- Optional missing inputs must be marked explicitly.
- Under the default `available_only` integrity policy, manifest freezing must not require VeriProc to compute full-file checksums. Checksums may be recorded from sidecars, upstream metadata, or external metadata when already available. Directory inputs must not require MD5 or other checksum metadata, and VeriProc must not walk directory contents solely to compute a recursive digest.

**Failure behavior**

- Missing mandatory inputs must prevent dispatch.

**Persistence rules**

- Must be persisted durably in database records and referenced by the task-scoped run key `(task_id, retry_index)`.
- A serialized copy must be exported under the working root. That copy must include the same classical matching traceability metadata needed for audit or replay, but it must not replace the database records required for query and recovery.
- The manifest is the source of truth for the inputs used or missing in the run and must contain enough selection metadata to explain the choice without re-running folder search logic.

## 3.8 Run

**Purpose**

A run is one execution attempt for one specific task. A run is a task attempt, not an independently meaningful object. A run without a parent task is outside the VeriProc model.

**Canonical identity**

A run's canonical identity is the composite `(task_id, retry_index)`.

- `task_id` identifies the immutable parent task.
- `retry_index` identifies the attempt within that task.
- `retry_index` starts at `0` for the first attempt and increments for subsequent attempts under the same task.
- `retry_index` is not globally unique and must not be used without `task_id`.

The preferred display form is `<task_id>/r<retry_index>`, for example `scen2-20250703T111239000-a7sf7f/r5`. This display form is a presentation convention for the composite key, not a separate durable identifier.

**Required fields**

- `task_id`
- `retry_index`
- station revision identifier
- current state
- working root path once materialized

**Optional fields**

- active scheduler job reference
- finalization summary
- canonical or non-canonical classification
- processing fingerprint once computed
- failure reason
- internal unique run key, if required by implementation storage design

**Immutable vs mutable fields**

- `task_id`, `retry_index`, station revision, working-root path after assignment, generator identities after assignment, and processing fingerprint after computation are immutable.
- State and operational metadata are mutable until terminal state according to the run lifecycle.
- An internal unique run key, if present, is immutable but is not the conceptual run identity.

**Creation trigger**

Created when the backend decides to attempt execution for a task.

**Validation rules**

- Must reference an existing task.
- Must have a valid state transition path.
- Must use the next valid `retry_index` or a retry-safe documented attempt-allocation rule for the parent task.
- Must not reuse an existing `(task_id, retry_index)` pair.
- Must not exist without a parent task.

**Failure behavior**

- A failed run remains part of the durable audit history for its parent task.
- Retry must create a new run under the same task with a new `retry_index`.
- A retry must not mutate the original run attempt, its working root, its manifest, or its processing fingerprint.

**Persistence rules**

- Must be persisted before dispatch is considered successful.
- The canonical persisted reference to a run is `(task_id, retry_index)`.
- Implementations may store an internal unique run key for physical storage or joins, but it must be derived from or constrained by the canonical run key and must not become the first-class API or CLI identity.

**Notes**

- The required internal layout includes an `input/` directory containing symlinks to the resolved input filesystem objects. A symlink may target a regular file or the root of a selected source directory.

- One task may have multiple runs. Each run owns a distinct working root, and retrying a task must not reuse or overwrite a prior run's working root.
- Forced runs, ordinary retries, duplicate attempts, and recovery-created attempts use the same `(task_id, retry_index)` identity model.
- Operator-readable run context must be exposed through separate fields or projections such as task ID, retry index, run reference, station, task window, canonical classification, state, created-at timestamp, and working-root path.
- The backend decides a run's canonical or non-canonical classification during finalization, using the processing fingerprint, force flag, and deduplication policy.
- Only a canonical completed run may drive downstream task creation by default. A deployment may allow non-canonical reruns to create downstream work only through an explicit policy.
- Run lifecycle states, including `orphaned`, and reconciliation behavior are defined by the run state model in the architecture chapter.

## 3.9 Job

**Purpose**

A job is the concrete scheduler submission for a run.

**Required fields**

- task-scoped run reference, represented by `(task_id, retry_index)`
- submission timestamp

**Optional fields**

- scheduler identifier while submission is pending or uncertain
- queue or partition
- scheduler-native state
- cancellation timestamp

**Immutable vs mutable fields**

- The job record identity is immutable.
- Scheduler-native status fields may change until terminal state.

**Creation trigger**

- Created when the execution adapter submits the run.

**Validation rules**

- Must reference exactly one run.

**Failure behavior**

- If scheduler acknowledgment is uncertain, the run must enter reconciliation or orphan handling.

**Persistence rules**

- Scheduler identity must be stored durably as soon as it is known.

**Notes**

- A persisted job record may be created before the scheduler identifier is known. Once the execution adapter successfully obtains a scheduler identifier, that identifier becomes required for the job record and must be persisted durably.
- A job is attached to exactly one task-scoped run. A job may have its own globally unique `job_id`, but that does not make the associated run globally identified by a standalone run identifier.

- Reconciliation is the lifecycle process that compares persisted run and job records with scheduler-visible state after uncertainty or restart.
- Orphan handling applies when the backend cannot prove whether a scheduler submission belongs to a run or whether a submitted job was accepted. It is a run lifecycle condition, not a separate job entity.

## 3.10 Runtime Environment

**Purpose**

The runtime environment is the predefined set of environment variables injected into the algorithm process by the execution layer.

**Required fields**

- `VERIPROC_WORKING_ROOT`
- `VERIPROC_STATION_ID`
- `VERIPROC_TASK_ID`
- `VERIPROC_RETRY_INDEX`
- `VERIPROC_RUN_REF`
- `VERIPROC_JOBORDER_PATH`

**Optional fields**

- scheduler-native environment variables
- deployment-specific facility variables
- debug or tracing variables

**Immutable vs mutable fields**

- The effective VeriProc-defined environment for a run is immutable once the job starts.

**Creation trigger**

- Injected by the execution adapter immediately before scheduler submission or job launch.

**Validation rules**

- VeriProc-defined paths must resolve within the working root namespace.
- Environment-variable injection must remain consistent with the job order content.
- The runtime environment is external to the job-order schema unless a station-specific contract explicitly mirrors part of it.

**Failure behavior**

- Missing mandatory VeriProc-defined variables must fail dispatch preparation or be treated as an execution-adapter defect.

**Persistence rules**

- The documented environment contract must be versioned by implementation policy. The run record should reference the effective environment contract version when it affects reproducibility.
- Environment variables should be treated as execution-layer process state, not as mandatory serialized fields of the job order.

**Notes**

- `VERIPROC_WORKING_ROOT` is derived from the run's working root path.
- `VERIPROC_STATION_ID` is derived from the station's `station_id`.
- `VERIPROC_TASK_ID` is derived from `task_id`.
- `VERIPROC_RETRY_INDEX` is derived from the run's task-scoped attempt index.
- `VERIPROC_RUN_REF` is derived from `task_id` and `retry_index` using the preferred display convention, for example `scen2-20250703T111239000-a7sf7f/r5`.
- `VERIPROC_JOBORDER_PATH` is derived from the generated job order artifact path inside the working root.

## 3.11 Working Root

**Purpose**

The working root is the isolated filesystem workspace for one run.

**Required fields**

- root path
- association to one run
- generator identity or system-default marker
- exported copy of the input manifest

**Optional fields**

- exported provenance summary

**Immutable vs mutable fields**

- Path association is immutable.
- Contents evolve during execution and finalization.

**Creation trigger**

- Created during run preparation.

**Validation rules**

- Must be unique for the run.
- Must contain the required internal execution layout after the root path is assigned.
- Must be located under an allowed shared-storage root.
- Must be deterministic for the validated run context and the effective instance naming policy.
- Must be generated from an effective relative path template composed from normalized station, task, and run segments unless a conforming custom generator is configured.
- Must not collide with another run. If the readable expanded path can collide, the generator must append a deterministic disambiguation suffix to the final path component without reordering existing readable components.

**Failure behavior**

- Partially created working roots must be recoverable, cleaned up, or classified as orphaned by restart reconciliation.

**Persistence rules**

- Path must be stored in the run record.
- Generator identity or a system-default marker is required at the conceptual level. Persistence of the generator identity is required when the generator is output-affecting, custom, audit-relevant, or included in the processing fingerprint; implementations may rely on a documented fixed system-default marker when the default generator is not output-affecting.

**Notes**

- A working root belongs to exactly one run. Multiple runs of the same task must have distinct working roots so retry artifacts, manifests, logs, and task output descriptors cannot overwrite each other.
- The working-root path is not the run identity. It may contain readable station, task-window, retry, run-event timestamp, or deterministic uniqueness components, but those components must not be used as foreign keys, provenance targets, API identities, or deduplication owners.
- The top-level instance naming policy governs the working-root relative path template, station segment template, task segment template, run segment template, normalization, allowed characters, replacement behavior, collision suffix behavior, and maximum segment length. The template may produce one path component or multiple path components under the configured working-root base.
- Task-window timestamp components should use compact UTC millisecond precision; run-event timestamp components may use compact UTC microsecond precision.

## 3.12 Task Output Descriptor (`task-out.yaml`)

**Purpose**

The task output descriptor declares downstream tasks produced by a completed algorithm execution.

**Required fields**

- list of downstream task declarations

**Optional fields**

- split-group metadata
- routing annotations
- split-group or aggregation declarations

**Immutable vs mutable fields**

- Treated as immutable once read for finalization.

**Creation trigger**

- Written by the algorithm before completion.

**Validation rules**

- Must validate against the descriptor schema.
- Target stations must exist.
- Duplicate entries must be rejected or normalized by explicit policy.
- Split-group or aggregation declarations must be validated against station policy before they affect group membership, closure, readiness, or aggregation routing.

**Failure behavior**

- Malformed descriptors must fail finalization unless explicit fallback policy is configured.

**Persistence rules**

- The file path and validated content summary should be recorded in the run.

**Notes**

- The downstream effects of a task output descriptor are governed by the producing run's completion state and canonicality. By default, only the descriptor from the canonical completed run for a task may create downstream tasks.
- Split-group metadata in `task-out.yaml` is authoritative only after the backend validates and accepts it under the station's dynamic split-declaration policy.
- If multiple runs of the same task produce descriptors, non-canonical descriptors must remain audit artifacts unless an explicit rerun or promotion policy authorizes downstream creation from them.

## 3.13 Split Group

**Purpose**

A split group coordinates a grouped fan-out/fan-in processing set derived from one parent window.

Fan-out creates the member child tasks for the group. Fan-in evaluates those members for readiness and, when the group uses aggregation semantics, materializes the aggregation stage. A split group may also use completion-only semantics, in which readiness is recorded without creating an aggregation task.

**Required fields**

- `group_id`
- parent task reference or parent run reference represented by `(task_id, retry_index)`
- parent time window
- group evaluation mode (`aggregation` or `completion_only`)
- grouped evaluation target or stage
- membership basis
- closure state
- readiness state
- grouped evaluation state
- readiness policy

**Optional fields**

- expected child count
- explicit child task set
- dynamic membership predicate
- deterministic child-key derivation rule
- timeout policy
- partial-aggregation policy
- grouped-evaluation window override
- aggregation target station or stage when `group evaluation mode` is `aggregation`
- aggregation task identifier once materialized
- re-aggregation policy

**Immutable vs mutable fields**

- Identity and parent association are immutable.
- Membership may change only until the group is closed.
- Closure is irreversible once recorded.
- Readiness state and grouped evaluation state may change until terminal state.

**Creation trigger**

- Created when a splitter run declares downstream fractional work or when the backend materializes an equivalent grouped workflow from deterministic station configuration.
- A split group is mandatory for any fan-out whose children must later be evaluated together for aggregation or grouped completion.

**Validation rules**

- Must define how child membership is determined: by an explicit child task set, by an expected child count plus a deterministic child-key derivation rule, or by a dynamic membership predicate with an explicit closure event.
- If membership uses an expected child count, the group policy must define the child-key space from which member task identifiers are derived, for example indexed sub-window keys computed from the parent window and split rule. Expected count alone is not sufficient to define membership.
- Must define when membership is closed. Fan-in readiness must not be evaluated against an open-ended group unless the readiness policy explicitly supports partial aggregation after timeout.
- Must define which actor may close the group. Closure may be performed by the backend while finalizing the producing parent run, by processing a valid closure declaration from `task-out.yaml`, or by an explicit operator/API action allowed by policy.
- Closure must be valid only if the recorded membership satisfies the group's membership basis and duplicate-handling policy.
- Must define a deterministic readiness policy, including membership basis, completion criterion, failure handling, timeout behavior, and canonicality basis.
- Readiness must be evaluated over child tasks and their canonical completion results by default. Each child task may contribute at most one canonical completion result, even if it has multiple runs.
- Aggregation must not start until the group is closed, the readiness policy evaluates to true, and the group evaluation mode is `aggregation`.
- For `group evaluation mode: aggregation`, the split-group policy must identify the aggregation target station or stage. The aggregation target is part of the split-group definition, not ordinary per-child downstream routing.
- Completion of an individual child task must not directly create an aggregation task unless the split-group readiness policy for that specific `group_id` has already evaluated to true.
- The backend must create at most one aggregation task for a split group under the default policy. Additional aggregation tasks require an explicit re-aggregation operation or documented replacement policy.
- Readiness and aggregation decisions must be evaluated per `group_id`. Child tasks from different split groups must not be merged solely because they share station identity, product type, filename pattern, or overlapping time ranges.
- A child task must belong to at most one active split group unless an explicit multi-group membership policy is defined.
- Completion-only groups must not create aggregation tasks; they record readiness or failure according to the same membership and readiness rules.
- If partial aggregation is allowed, the policy must define which missing or failed children are excluded and how that exclusion is recorded.
- Duplicate child declarations must be rejected or normalized according to a deterministic policy before membership is closed.
- If station default downstream configuration creates a split group without `task-out.yaml`, the station configuration must provide enough deterministic split metadata to construct child membership, closure, and grouped evaluation behavior from the parent task and run context.

**Failure behavior**

- If the system cannot determine readiness safely, the group must not be marked ready and aggregation must not start.
- If a mandatory child task fails and policy does not allow exclusion or partial aggregation, the split group must remain not ready or transition to failed according to policy.
- If a child task is retried, readiness must wait for canonicality to be resolved for that child unless the readiness policy explicitly uses another completion basis.

**Persistence rules**

- Must be stored durably and updated transactionally with child-task bookkeeping where practical.

**Notes**

- Fan-out may be declared by `task-out.yaml` or by station default downstream configuration. When a valid `task-out.yaml` exists, it is authoritative for the downstream tasks and split-group membership produced by that run unless station policy explicitly allows fallback or merge behavior.
- When station default downstream configuration creates a split group, that station configuration is the source of the split policy. It must define the same membership, closure, readiness, and grouped-evaluation rules that dynamic split metadata would otherwise provide through `task-out.yaml`.
- The default membership model is task-based: the split group contains child tasks, not individual child runs. Runs are considered through the canonical completion result of each child task.
- Group closure records that no more child tasks may be added. A group may be closed immediately when an explicit bounded child set is created, or later through an explicit closure event for dynamic membership.
- For aggregation-mode groups, fan-in normally creates at most one aggregation task per split group after readiness becomes true. Re-aggregation requires an explicit operation or policy and must preserve the earlier aggregation record.
- Aggregation input selection must be defined by policy. The default input set is the validated output artifacts, or validated published artifacts when publication is required, from the canonical completed run of each contributing child task.
- For aggregation-mode groups, the backend must materialize the aggregation input set from split-group membership and the canonical completed result of each contributing child task.
- The aggregation station must not discover its contributing sub-windows or sub-granules by unconstrained archive scanning or by parsing routing-history text.
- The backend must expose selected aggregation inputs to the aggregation run through the normal run contract: resolved manifest entries, job-order input references, and symlinks under the aggregation run's `working_root/input/`.
- The aggregation run's resolved input manifest must record the exact child artifacts selected for aggregation, including contributing child task identity and producing run reference `(task_id, retry_index)` where available.
- Canonicality changes after an aggregation task has been materialized must not retroactively alter that aggregation or its input set unless explicit re-aggregation policy is invoked.
- Completion-only split groups record grouped readiness without an aggregation task; this must be represented by `group evaluation mode: completion_only`.

## 3.14 Artifact

**Purpose**

An artifact is any persisted filesystem object associated with a run, including outputs, logs, the job order, the task output descriptor, and manifest exports. Artifacts may be regular files or directories.

**Required fields**

- artifact identifier
- producing run reference `(task_id, retry_index)` or external origin reference
- logical artifact type
- path
- object kind, with at least `regular_file` and `directory` supported

**Optional fields**

- checksum value, checksum algorithm, and checksum source when available under the instance integrity policy
- size
- validation result
- content metadata
- rolling archive publication metadata

**Immutable vs mutable fields**

- Identity, producing run, and path are immutable.
- Validation metadata may be added during finalization.

**Creation trigger**

- Created when the file is first recorded by the backend.

**Validation rules**

- Path must remain within allowed storage policy.
- Mandatory output artifacts must satisfy station validation rules.
- Directory output artifacts must satisfy object-level validation: existence, expected object kind, effective name or naming-rule compliance, and any explicit station policy. Baseline validation must not require recursive inspection of directory children.
- Artifact checksum metadata is optional unless station or deployment integrity policy requires it for the applicable object kind. The artifact record must distinguish checksums computed by VeriProc from checksums obtained from sidecars, upstream metadata, or external metadata. Directory artifacts must not require MD5 or other checksum metadata in the baseline, and VeriProc must not walk directory contents solely to compute a recursive digest.

**Failure behavior**

- Missing mandatory artifacts must prevent the run from reaching `complete`.

**Persistence rules**

- Must be linked to the run that produced it.
- If copied or linked into a rolling archive, the publication target and mode must be recorded without changing the producing run identity.

## 3.15 Processing Fingerprint

**Purpose**

The processing fingerprint is the deduplication and canonicality key for a scientifically meaningful execution context.

**Required fields**

- station identity
- station revision identity
- processing window
- resolved input identities
- resolved category-folder sources when they can affect reproducibility
- generator identities when custom generation affects execution context
- output-affecting runtime parameters

**Optional fields**

- checksums
- facility mode
- algorithm image digest
- job order schema version
- rolling archive source identifiers when archive selection can affect reproducibility

**Immutable vs mutable fields**

- Immutable once computed for a run.

**Creation trigger**

- Computed during run preparation after manifest, station revision, configuration, generator identities, and output-affecting runtime parameters are frozen and before the run is eligible for dispatch.

**Validation rules**

- Must include every context element that can change scientific outputs under deployment policy.

**Failure behavior**

- If the fingerprint cannot be computed, the run must not be dispatched.

**Persistence rules**

- Must be stored with every prepared run.
- Must be stored in the deduplication registry only when the run becomes canonical and complete.

**Notes**

- Every prepared run must store its computed processing fingerprint either on the run record or through an associated fingerprint record, whether the run later becomes canonical or non-canonical.
- A run is canonical when it completes successfully and becomes the deduplication-record owner for its processing fingerprint.
- A non-canonical run may have the same or a different fingerprint, but it must not create or replace the canonical deduplication owner unless an explicit promotion or replacement action is applied.
- Forced tasks create runs that are non-canonical by default. They may be promoted to canonical only through an explicit operator action, API action, or documented automatic replacement policy.

---

## 3.16 Deduplication Record

**Purpose**

The deduplication record identifies which completed run currently owns a canonical processing fingerprint.

**Required fields**

- processing fingerprint
- owning run reference `(task_id, retry_index)`
- canonical status

**Optional fields**

- superseded-by reference
- promotion timestamp

**Immutable vs mutable fields**

- Fingerprint is immutable.
- Ownership metadata may change only through an explicit replacement or promotion operation.

**Creation trigger**

- Created when a run reaches canonical completion.

**Validation rules**

- Only one canonical owner may exist for a fingerprint at a time.
- A deduplication record's canonical status must be consistent with the owning run's canonical classification.

**Failure behavior**

- Conflicting ownership must fail transactionally and trigger operator-visible diagnostics.

**Persistence rules**

- Must be queryable independently of raw run records.

**Notes**

- The backend creates or updates deduplication records during finalization after output validation succeeds and before canonical downstream effects are emitted.
- Non-canonical runs retain their processing fingerprints through the run record or associated fingerprint record, but they do not own canonical deduplication records.
- Supersession or promotion of a canonical owner must be initiated by an explicit operator action, API action, or documented automatic policy. It must record both the previous owner and the replacing owner.

## 3.17 Facility

**Purpose**

Facility describes the operational context passed to the algorithm.

**Required fields**

- processing environment identifier

**Optional fields**

- acquisition station
- processing center
- test flag

**Immutable vs mutable fields**

- Immutable within a run.

**Creation trigger**

- Derived from deployment configuration during job order generation.

**Validation rules**

- Must satisfy the job order schema.

**Failure behavior**

- Invalid facility data must fail job order generation.

**Persistence rules**

- Must be recorded in the job order and therefore indirectly in the run context.

**Notes**

- Facility fields that can affect scientific outputs must be included in the processing fingerprint according to deployment policy.

## 3.18 State Store

**Purpose**

The state store is the relational persistence layer for all durable control data.

**Required fields**

- N/A at the entity level; this is the persistence substrate

**Optional fields**

- N/A

**Immutable vs mutable fields**

- N/A

**Creation trigger**

- Provisioned as part of deployment.

**Validation rules**

- Must enforce referential integrity and uniqueness where required for idempotency.

**Failure behavior**

- Loss of write availability must block state transitions that require durable commit.

**Persistence rules**

- SQLite may be used for development; Postgres should be used for production.

## 3.19 Instance Configuration

**Purpose**

Instance configuration defines deployment-level settings that are shared by all stations and runs in one VeriProc installation.

**Required fields**

- instance identifier
- working root base path
- station configuration root or registry reference
- facility defaults
- input category definitions through `product_categories`
- naming policy for generated path and filename segments
- integrity policy for checksum handling

**Optional fields**

- rolling archive definitions
- custom working-root generator module
- custom job-order generator module
- executor defaults
- retention and cleanup policy defaults

**Immutable vs mutable fields**

- The effective instance configuration used by a run must be frozen by reference or content hash.
- Future instance configuration changes must not retroactively alter existing run semantics.

**Creation trigger**

- Created or loaded at backend startup and may be reloaded through a controlled deployment operation.

**Validation rules**

- Referenced paths must be allowed shared-storage paths.
- Input category names declared through `product_categories` must be unique.
- Rolling archive identifiers must be unique.
- Custom generator module references must resolve and satisfy the required interface before use.
- Naming policy must define timestamp encodings, task identifier timestamp source, the working-root relative path template, working-root station/task/run segment templates, generated filename segment rules, allowed characters, unsafe-character replacement, station-case handling, collision-suffix behavior, and maximum segment length.
- The task identifier timestamp source must be either `creation` or `start` and must default to `creation` when omitted.
- Integrity policy must be one of `none`, `available_only`, or `required` unless the implementation documents an equivalent policy with the same semantics. The default must be `available_only`.

**Failure behavior**

- Invalid instance configuration must block backend startup or block creation of runs that depend on the invalid portion.

**Persistence rules**

- The effective instance configuration identity must be recorded with every run. Individual configuration fields may or may not be included in the processing fingerprint according to whether they can affect outputs under deployment policy.

**Notes**

- Naming policy applies to generated working-root relative paths, their component segments, and VeriProc-generated filenames or filename-adjacent segments. It must not define alternate durable identifiers.
- Integrity policy controls whether checksums are ignored, recorded only when available, or required/computed for regular files. Under `available_only`, input resolution, manifest freezing, artifact recording, and run completion remain valid without system-computed checksums. Directory inputs and artifacts remain non-recursive in the baseline and do not require MD5 or other checksum validation.

## 3.20 Generation Hook

**Purpose**

A generation hook is a deployment-provided module that overrides system-default working-root path generation or job-order generation.

**Required fields**

- hook type (`working_root` or `job_order`)
- module reference
- implementation version or content hash

**Optional fields**

- configuration payload
- timeout policy
- validation mode

**Immutable vs mutable fields**

- The hook identity used for a run is immutable once run preparation begins.

**Creation trigger**

- Declared in instance configuration.

**Validation rules**

- Must implement the required interface.
- Must be deterministic for the same validated inputs.
- Must not mutate backend state directly.
- Must preserve working-root containment and job-order schema validity.

**Failure behavior**

- Hook failure must fail run preparation before scheduler submission.
- A hook that returns invalid output must be treated as a preparation failure.

**Persistence rules**

- Hook identity must be recorded in run metadata or generated artifacts when it can affect execution context.

## 3.21 Rolling Archive

**Purpose**

A rolling archive is a named read-write directory used as operational short-term storage for input selection and optional publication of validated outputs.

**Required fields**

- archive identifier
- filesystem path
- retention period

**Optional fields**

- archive mode or publication permissions
- publication subdirectory policy
- checksum policy
- cleanup schedule
- allowed station list

**Immutable vs mutable fields**

- Archive identifier must be stable within an instance.
- Retention policy and path are deployment-managed and may change only through controlled configuration updates.

**Creation trigger**

- Declared in top-level instance configuration.

**Validation rules**

- Path must be visible to backend and compute nodes if used for symlinked input access.
- Station references such as `rolling:co2m_hot` must resolve to a declared archive.

**Failure behavior**

- Unavailable archives must fail input resolution if they are needed for mandatory inputs.
- Publication failure after successful job execution must keep the run in finalization or fail according to station policy; it must not silently create downstream tasks that depend on unpublished data.

**Persistence rules**

- Input manifest entries must record the archive identifier when a filesystem object is selected from a rolling archive.
- Publication records must record target archive, target path, publication mode, and source artifact.

## 3.22 Executor

**Purpose**

The executor is the adapter that translates runs into compute jobs.

**Required fields**

- N/A at the entity level; implementations must support submission and query

**Optional fields**

- cancellation support
- scheduler-native hints

**Immutable vs mutable fields**

- Adapter configuration is deployment-managed.

**Creation trigger**

- Provisioned as part of the backend.

**Validation rules**

- Must implement the required scheduler contract.

**Failure behavior**

- Submission uncertainty must be surfaced as reconciliation or orphan handling, not silently ignored.

**Persistence rules**

- Executor-specific ephemeral state should not be treated as the system of record.

## 3.23 Shared Storage

**Purpose**

Shared storage is the filesystem namespace accessible to both backend and compute nodes.

**Required fields**

- N/A at the entity level

**Optional fields**

- storage-class metadata

**Immutable vs mutable fields**

- Deployment-managed.

**Creation trigger**

- Provisioned as part of the environment.

**Validation rules**

- Must provide the consistency and path visibility required by the working-root contract.

**Failure behavior**

- Storage unavailability during preparation or finalization must fail the affected transition and be recoverable on restart.

**Persistence rules**

- Artifact bytes live here; control truth does not.

## 3.24 Glossary

| Term | Definition |
|---|---|
| Station | Declarative processing-step specification |
| Station revision | Frozen version of a station definition |
| Task | Immutable routing request for a processing window |
| Routing history | Readable append-only traversal log carried by tasks |
| Provenance link | Explicit graph edge between tasks, runs, or artifacts |
| Job order | Immutable execution descriptor consumed by the algorithm |
| Resolved input manifest | Frozen record of selected and missing inputs |
| Run | One execution attempt for one task |
| Job | Concrete scheduler submission for a run |
| Runtime environment | Predefined environment variables injected into the job process |
| Working root | Isolated filesystem workspace for one run |
| `task-out.yaml` | Optional descriptor declaring downstream tasks |
| Split group | Coordination record for fan-out/fan-in workflows |
| Artifact | Persisted file associated with a run |
| Processing fingerprint | Deduplication key for scientific execution context |
| Deduplication record | Canonical ownership record for a fingerprint |
| Facility | Operational context block passed to the algorithm |
| State store | Relational persistence layer for durable control state |
| Instance configuration | Deployment-level configuration for roots, archives, generators, and defaults |
| `product_categories` | Top-level ordered category definitions that determine folder search precedence |
| `rolling_folders` | Station-level override for category folder search order |
| Generation hook | User-defined module overriding default working-root or job-order generation |
| Rolling archive | Named operational directory for input selection and optional output publication |
| Executor | Adapter that submits and tracks compute jobs |
| Shared storage | POSIX-visible filesystem for working roots and artifacts |
