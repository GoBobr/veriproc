# 6. Command-Line Interface and Operator Workflows

This chapter defines the normative behavior of the VeriProc command-line interface, referred to in this chapter as the CLI. The CLI is a command-line client for operators, deployment automation, and scripted control-plane interaction. It is layered strictly on the VeriProc REST API defined in Chapter 5.

Unless explicitly marked informative, statements in this chapter are normative.

The CLI specification is language-neutral. The MVP reference CLI implementation may be written in Go, but command semantics, output behavior, exit-code behavior, and API mapping must not depend on Go-specific behavior or any particular command framework.

## 6.1 Scope and Role of the CLI

The CLI provides a reference operator and automation client for submitting tasks, querying tasks and runs, inspecting jobs, reading logs and artifact metadata, requesting cancellation, inspecting provenance, and checking backend health and readiness.

The CLI must interact with VeriProc control-plane state only through the REST API. It must not write directly to the database, mutate working roots, edit station-derived control artifacts, modify rolling archive publication metadata, submit scheduler jobs directly, or infer backend state by scanning shared storage. Any command that changes backend state must map to a documented API operation.

The CLI is optional for server conformance. A VeriProc backend may be conforming without shipping a CLI. However, the MVP should provide a CLI as a reference client because it gives operators and automated workflows a stable interface for common control-plane actions.

The CLI must preserve the identity distinctions defined by the rest of this specification. In particular, it must not collapse or reinterpret tasks, runs, jobs, job orders, artifacts, logs, split groups, provenance links, station revisions, processing fingerprints, or scheduler identifiers. If a command displays a summary that includes multiple related identifiers, the output must make their roles clear.

The CLI must treat canonical IDs as opaque durable identifiers. For runs, the canonical identity is the task-scoped composite `(task_id, retry_index)`. The CLI may display the preferred compact run reference `<task_id>/r<retry_index>`, for example `task-20250703T111239000-a7sf7f/r5`, but that display form is a rendering of the composite, not a second identity. The CLI must not parse station, time-window, retry, downstream, scheduler, or provenance meaning from task IDs, job IDs, artifact IDs, split-group IDs, or displayed run references. Operator readability must come from API-provided fields such as station, start, end, state, latest run reference, canonical run reference, retry index, canonical classification, created-at timestamp, and working-root path.

The CLI may perform local convenience checks such as detecting unreadable input files, malformed local flags, invalid output-format names, missing required command arguments, or syntactically invalid YAML or JSON. Such checks must not replace server-side validation. The backend remains authoritative for task validity, station resolution, idempotency behavior, lifecycle transitions, cancellation eligibility, authorization, and consistency.

## 6.2 CLI Design Principles

The CLI must follow these design principles.

**API-first behavior**

Commands that inspect or change VeriProc state must call the configured REST API endpoint. The CLI must not require local filesystem access to backend working roots, rolling archives, station configuration directories, scheduler state, or database files.

**Thin client behavior**

The CLI should remain a thin orchestration client, not a local decision engine. It may transform command-line flags and input documents into API requests and render API responses for humans or automation. It must not compute processing fingerprints, decide canonicality, resolve rolling archive inputs, create downstream tasks locally, evaluate split-group readiness locally, or implement scheduler reconciliation locally.

**Stable command semantics**

Command names, required arguments, flag meanings, output-format names, and exit-code mappings should remain stable within a CLI major version. Incompatible changes must be documented and versioned.

**Human-readable defaults**

The default output should be readable by an operator in a terminal. List commands should default to compact tabular or aligned summaries. Detail commands should default to a readable structured view that preserves important identifiers and state.

Default tables must not imply that readable path names, compact timestamps, station columns, or displayed context fields are alternate identities. Machine-readable output must preserve canonical identifiers and separate context fields using the API response field names or documented CLI equivalents.

**Machine-readable output**

The CLI must support machine-readable output for automation. At minimum, it should support `--output json`, `--output yaml`, and `--output table` where the command has a structured payload. Machine-readable output must be written to standard output and must use stable field names.

**Explicit exit-code behavior**

The CLI must return defined exit codes. Exit codes must distinguish successful execution, command-line usage errors, server validation errors, not-found responses, conflicts, authorization failures, dependency failures, timeouts, and indeterminate outcomes as defined in Section 6.10.

**Diagnostics on standard error**

The primary command payload must be written to standard output. Diagnostic messages, progress messages, warnings, validation diagnostics, and error summaries must be written to standard error unless a command explicitly documents another stream.

**Compatibility awareness**

The CLI should identify its own version and, where possible, the API version or versions supported by the configured backend. A CLI should fail clearly when the configured backend API version is unsupported.

**No hidden mutation**

The CLI must not perform hidden state-changing operations outside the documented API call for the invoked command. For example, a query command must not submit tasks, request cancellation, alter server configuration, mutate local profile state, or write output files unless explicitly requested by flags.

## 6.3 Command Groups

The CLI should expose command groups that correspond to the principal API resources and operator workflows. Physical command spelling may vary by implementation, but a conforming reference CLI should provide the command groups in this section or documented equivalents with the same semantics.

### 6.3.1 Task Submission: `submit`

**Purpose**

`submit` creates a task submission request through the API.

**Expected inputs**

The command must accept a structured request document from a file or standard input. YAML input should be supported for operator use. JSON input may be supported and should map to the same canonical submission semantics. The command may also support flags for common fields such as destination station, `proc_type`, window start, window end, idempotency key, force flag, priority, parent task, parent run, and client metadata.

**API mapping**

The command must map to the task-submission API operation, equivalent to `POST /tasks`.

**Minimum output expectations**

On success, output must include the submitted or existing `task_id`, task state, destination, processing window, force flag, and any latest-run or canonical-run reference fields returned by the API, such as `latest_retry_index`, `latest_run_ref`, `canonical_retry_index`, and `canonical_run_ref`. If the API indicates that the request matched an existing idempotency record, the CLI should make that visible.

**Failure behavior**

The command must surface server validation failures, idempotency conflicts, unknown destination errors, dependency failures, and authorization failures. The CLI must not create a local task record when the server rejects a submission.

### 6.3.2 Task Inspection: `task get`

**Purpose**

`task get` retrieves one task by identifier.

**Expected inputs**

The command must accept a task identifier. It may accept flags controlling output detail, related-run embedding, or machine-readable output.

**API mapping**

The command must map to an API operation equivalent to `GET /tasks/{task_id}`.

**Minimum output expectations**

Output must identify the task, destination, processing window, force flag, task state, parent references when present, split-group reference when present, latest run, canonical run, timestamps, and relationship links or summaries when returned by the API.

**Failure behavior**

If the task does not exist or is not visible to the caller, the command must report a not-found error and use the not-found exit code.

### 6.3.3 Task Listing: `task list`

**Purpose**

`task list` lists or searches tasks through API-backed query endpoints.

**Expected inputs**

The command should accept filters corresponding to the API, including destination station, `proc_type`, task state, processing-window overlap or containment, creation time range, parent task, parent run, split group, force flag, and canonical-run presence.

**API mapping**

The command must map to an API operation equivalent to `GET /tasks` with query parameters.

**Minimum output expectations**

Default output should include task identifier, station, start, end, task state, latest run reference, canonical run reference, and creation time. It may include force flag and priority when useful. Machine-readable output must preserve the list envelope, pagination metadata, applied filters, and ordering when returned by the API.

An informative default table shape is:

```text
TASK ID                      STATION   START                 END                   STATE    LATEST RUN REF                    CANONICAL RUN REF                 CREATED AT
task-20250703T111239000-a7sf7f SCENE-L2  2025-07-03T11:12:39Z 2025-07-03T11:30:00Z running  task-20250703T111239000-a7sf7f/r5 -                                2025-07-03T11:50:00Z
```

The CLI must obtain station, start, end, latest run, and canonical run values from the API response. It must not derive them from the task ID.

**Failure behavior**

Invalid filters or pagination parameters must be reported as usage errors if detected locally before an API call, or as server validation errors if returned by the API.

### 6.3.4 Run Inspection: `run get`

**Purpose**

`run get` retrieves one run by task-scoped run reference.

**Expected inputs**

The command must accept a task-scoped run reference. A conforming CLI should accept either the pair `--task <task_id> --retry <retry_index>` or the compact form `<task_id>/r<retry_index>`.

**API mapping**

The command must map to an API operation equivalent to `GET /tasks/{task_id}/runs/{retry_index}`.

**Minimum output expectations**

Output must identify the task-scoped run reference, task, station revision, run state, canonical classification, retry index, working-root path when exposed by the API, processing fingerprint or reference when exposed by the API, job-order artifact, manifest reference, active job, timestamps, failure reason when present, and finalization summary when present.

**Failure behavior**

A missing or inaccessible run must be reported as not found. If the API hides sensitive fields, the CLI must not attempt to reconstruct them through local filesystem access.

### 6.3.5 Run Listing: `run list`

**Purpose**

`run list` lists or searches runs through API-backed query endpoints.

**Expected inputs**

The command should accept filters corresponding to the API, including task identifier, retry index, station identifier, station revision, run state, canonical classification, processing fingerprint, creation time range, terminal time range, and scheduler identifier.

**API mapping**

The command must map to an API operation equivalent to `GET /tasks/{task_id}/runs` for task-scoped listing or `GET /runs` for broader filtered search.

**Minimum output expectations**

Default output should include task identifier, retry index, run reference, station, start, end, state, canonical classification, creation time, and working-root path when relevant and exposed by the API. It may include active or latest scheduler identifier and terminal time when useful.

An informative default table shape is:

```text
TASK ID                      RETRY RUN REF                             STATION   START                 END                   STATE    CANONICALITY CREATED AT              WORKING ROOT
task-20250703T111239000-a7sf7f 5     task-20250703T111239000-a7sf7f/r5 SCENE-L2  2025-07-03T11:12:39Z 2025-07-03T11:30:00Z running  pending      2025-07-03T11:50:02Z /shared/veriproc/work/SCENE-L2/task-20250703T111239000-a7sf7f/r5
```

The CLI must obtain station and time-window values from API run summaries, embedded task summaries, or documented API projections. It must not derive them from the run reference or working-root path.

**Failure behavior**

The command must distinguish an empty successful result set from a failed query. An empty list with a successful API response must exit with success.

### 6.3.6 Job Inspection: `job get`

**Purpose**

`job get` retrieves one scheduler job record by VeriProc job identifier or, where supported by the API, by scheduler identifier.

**Expected inputs**

The command must accept a VeriProc job identifier. It may support a `--scheduler-id` flag if the API supports lookup by scheduler identifier.

**API mapping**

The command should map to an API operation equivalent to `GET /jobs/{job_id}` or a documented job query endpoint.

**Minimum output expectations**

Output must include job identifier, task-scoped run reference, executor type, scheduler identifier when known, scheduler-native state, submission timestamp, last-observed timestamp when available, cancellation fields when present, and reconciliation status when relevant.

**Failure behavior**

If scheduler-derived state is stale, the CLI must display the server-provided last-observed timestamp when available. The CLI must not query the scheduler directly unless the API explicitly exposes a server-side operation for refreshing or querying scheduler state.

### 6.3.7 Job Listing: `job list` or `run jobs`

**Purpose**

`job list` or `run jobs` lists jobs associated with a run or searches jobs through API-backed filters.

**Expected inputs**

The command should accept a task-scoped run reference. It may accept executor type, scheduler state, submission time range, or reconciliation-status filters if the API supports them.

**API mapping**

The command should map to API operations equivalent to `GET /tasks/{task_id}/runs/{retry_index}/jobs` or `GET /jobs`.

**Minimum output expectations**

Default output should include job identifier, task identifier, retry index, run reference, executor type, scheduler identifier, scheduler-native state, submission timestamp, and last-observed timestamp.

**Failure behavior**

If the run does not exist, the command must report not found. If the run exists but has no jobs, the command should report an empty successful result.

### 6.3.8 Artifact Listing and Inspection: `artifact list` and `artifact get`

**Purpose**

Artifact commands inspect metadata for files associated with runs or tasks and, where the API supports it, fetch artifact content through API-controlled access paths.

**Expected inputs**

`artifact list` should accept a task-scoped run reference or task identifier and filters such as logical artifact type, file type, validation status, canonical-run only, latest-run only, and publication status. `artifact get` should accept an artifact identifier.

**API mapping**

The commands must map to API operations equivalent to `GET /tasks/{task_id}/runs/{retry_index}/artifacts`, `GET /tasks/{task_id}/artifacts`, `GET /artifacts/{artifact_id}`, or a documented artifact-content endpoint.

**Minimum output expectations**

Metadata output must identify artifact identifier, producing run or external origin, logical artifact type, path or access reference subject to access policy, availability status, creation or discovery timestamp, validation status, checksum when available, and publication summary when available.

**Failure behavior**

If artifact bytes are unavailable due to retention or access policy but metadata exists, the CLI must distinguish unavailable content from missing metadata when the API makes that distinction.

### 6.3.9 Log Access: `logs`

**Purpose**

`logs` inspects log metadata and retrieves log content for a run through the API.

**Expected inputs**

The command must accept a task-scoped run reference. It may accept a log name, artifact identifier, byte range, line range, cursor, `--follow` flag, or output destination if the API supports those access modes.

**API mapping**

The command must map to API operations equivalent to `GET /tasks/{task_id}/runs/{retry_index}/logs`, `GET /tasks/{task_id}/runs/{retry_index}/logs/{log_name}`, or `GET /artifacts/{artifact_id}/content`.

**Minimum output expectations**

Metadata output must identify log artifact identity and producing run. Content output should stream or print log bytes returned by the API without adding formatting that would corrupt the content unless a decorated output mode is explicitly selected.

**Failure behavior**

The CLI must not read log files directly from a working root. If the API reports that log content is unavailable, the CLI must report that condition and use the mapped exit code for the API response.

### 6.3.10 Provenance and Relationships: `relationships`

**Purpose**

`relationships` queries machine-readable provenance links for tasks, runs, artifacts, split groups, and aggregation workflows.

**Expected inputs**

The command should accept source object type and identifier, target object type and identifier, relationship type, split-group identifier, or convenience flags such as `--task`, `--run`, or `--artifact`. A run reference must be supplied as a task-scoped run reference.

**API mapping**

The command must map to API operations equivalent to `GET /tasks/{task_id}/relationships`, `GET /tasks/{task_id}/runs/{retry_index}/relationships`, or a generic relationship query endpoint.

**Minimum output expectations**

Output must preserve source object type, source identifier, target object type, target identifier, relationship type, contribution role when present, creation reason when present, and creation timestamp when returned by the API.

**Failure behavior**

The command must not reconstruct provenance by parsing routing-history text, inferring from filenames, or scanning rolling archives.

### 6.3.11 Cancellation: `cancel`

**Purpose**

`cancel` requests cancellation of a run through the API.

**Expected inputs**

The command must accept a task-scoped run reference. It may accept `--reason`, `--yes`, `--quiet`, or output-format flags.

**API mapping**

The command must map to a cancellation API operation equivalent to `POST /tasks/{task_id}/runs/{retry_index}/cancel`.

**Minimum output expectations**

Output must distinguish cancellation request accepted from cancellation completed. It must show the current run state returned by the API and, when available, scheduler cancellation request state, active job, and timestamps.

**Failure behavior**

The command must surface invalid state transitions, unsupported cancellation, reconciliation in progress, authorization failures, dependency failures, and not-found responses.

### 6.3.12 Health: `health`

**Purpose**

`health` reports backend liveness as exposed by the API.

**Expected inputs**

The command should require no resource identifier. It may accept output-format flags and timeout flags.

**API mapping**

The command should map to a health endpoint exposed by the backend.

**Minimum output expectations**

Output should include overall health status, backend version or build metadata when exposed, and request timing when useful.

**Failure behavior**

If the backend cannot be reached or returns an unhealthy response, the command must return an unavailable or generic failure exit code according to Section 6.10.

### 6.3.13 Readiness: `readiness`

**Purpose**

`readiness` reports whether the backend is ready for control-plane operations as exposed by the API.

**Expected inputs**

The command should require no resource identifier. It may accept output-format flags and timeout flags.

**API mapping**

The command should map to a readiness endpoint exposed by the backend.

**Minimum output expectations**

Output should include overall readiness and dependency states returned by the API, such as database, scheduler adapter, station registry, shared storage, and rolling archive configuration when exposed.

**Failure behavior**

The CLI must not perform its own dependency probing in place of the backend readiness endpoint. If the readiness endpoint reports a dependency unavailable, the CLI must surface that server-provided state.

### 6.3.14 Version: `version`

**Purpose**

`version` reports CLI version information and, where possible, API compatibility information for the configured backend.

**Expected inputs**

The command should work without contacting the backend. It may accept a flag such as `--check-api` to query the configured backend.

**API mapping**

The command may call an API metadata, health, or version endpoint when API compatibility checking is requested.

**Minimum output expectations**

Output must identify the CLI version. It should identify supported API versions and, when queried, the backend API version or versions reported by the server.

**Failure behavior**

Failure to contact the backend during an explicit API compatibility check must be reported without hiding the local CLI version.

### 6.3.15 Configuration Validation: `config validate`

**Purpose**

`config validate` may validate local YAML or JSON documents as a convenience for operators before submission or deployment.

**Expected inputs**

The command may accept task submission documents, station configuration documents, instance configuration documents, or job-order examples, depending on which schemas the CLI distribution includes or can retrieve from the API.

**API mapping**

If validation is local, the command must be described as local schema validation only. If validation is server-driven, the command must call a documented validation API endpoint. In both cases, validation must not mutate server state.

**Minimum output expectations**

Output should identify the document type, schema version, validation outcome, and field-level validation errors when available.

**Failure behavior**

Local validation success must not imply that the server will accept a later state-changing request. The server remains authoritative for station existence, instance configuration identity, access policy, deployment-specific validation, and task submission semantics.

## 6.4 Submission Semantics

The CLI must submit tasks by sending a structured task-submission request to the API. It must not write task files into a watched directory, create database records, create working roots, or trigger scheduler jobs directly.

The command should support YAML file input because YAML is the primary operator-facing configuration and task format used elsewhere in this specification. The command should also support reading from standard input, using a conventional file marker such as `-` where appropriate. JSON input may be supported. If both YAML and JSON are supported, they must map to the same canonical API request semantics.

When both a request document and command-line flags are supplied, the CLI must document the merge behavior. A conforming implementation should either reject conflicting duplicate fields or use a simple documented override rule. If flags override document fields, the CLI should make that behavior explicit in help text and should avoid silently changing safety-relevant fields such as `force`, parent references, or destination.

The CLI may allow an idempotency key to be supplied in a request document, command-line flag, or both. If the same idempotency key is supplied in multiple places, the values must match or the command must fail with a usage error before submission. The CLI may generate an idempotency key only when explicitly requested by the operator or by a documented automation mode. It must not silently generate a key in a way that changes duplicate-submission behavior without the caller's knowledge.

The force flag must map to the API force field. The CLI must not reinterpret force as permission to overwrite canonical runs, delete prior outputs, replace deduplication records, bypass output validation, or create downstream tasks from non-canonical runs. Forced-run canonicality is determined by the backend policy defined elsewhere in this specification.

Parent references supplied through CLI flags or request documents must be passed to the API as parent task and parent run references. A parent run reference must include the parent task and retry index, either as separate fields or a documented compact form. The CLI may check that parent identifiers are syntactically non-empty, but it must not decide parent consistency locally except for obvious malformed input. The backend remains authoritative for whether parent references exist and are consistent.

Destination may be specified by station identity or by `proc_type` if the API supports station resolution by `proc_type`. If both are supplied, the CLI must pass both or reject conflicting local inputs according to documented behavior, but the backend remains authoritative for resolving ambiguity or unknown destinations.

Processing-window timestamps should be accepted in RFC 3339 form when supplied as flags. The CLI may validate that a timestamp is syntactically parseable and may reject a local start time greater than an end time before submission. The server remains authoritative for accepted precision, timezone normalization, and deployment-specific timestamp rules.

Submission errors returned by the server must be surfaced without hiding the server's machine-readable error code. Human-readable output should show the error message and relevant field-level validation details. Machine-readable output must include the server error code, message, request identifier when present, and any field-level details returned by the API.

The CLI must not invent task semantics not present in the API. In particular, it must not implement local deduplication based on station and time window, local processing-fingerprint computation, local downstream task creation, local split-group membership assignment, or local rolling archive input resolution.

## 6.5 Query and Listing Behavior

Query and listing commands must use API-backed read endpoints. The CLI must treat the database-backed API response as the committed control-plane state exposed to the caller.

List commands should provide filter flags that correspond to documented API filters. If a filter is not supported by the configured backend API version, the CLI must either omit it from that version's help output or fail with a clear unsupported-filter error before or after the API response. The CLI should not emulate unsupported server-side filters by fetching broad result sets and filtering locally unless the command explicitly documents that behavior and the result set is bounded enough to avoid misleading pagination or ordering.

Pagination flags should map to the API pagination model. If the API uses continuation tokens, the CLI should expose those tokens without interpreting their internal structure. If the API uses offsets, the CLI should expose offset and limit consistently with the API. The CLI may provide a convenience option to follow all pages for automation, but it must document that multiple API requests may be made and must preserve deterministic ordering as returned by the server.

List commands must distinguish between an empty successful result and an error. An empty successful result must exit with success unless a command explicitly defines a non-empty expectation flag.

Default ordering should follow the API default ordering. If the CLI exposes ordering flags, they must map to documented API ordering parameters. The CLI must not imply that local display sorting changes server-side pagination semantics.

Commands should support summary and detail views. Summary views should include stable identifying fields and state fields suitable for scanning. Detail views should preserve all fields returned by the API that are relevant to the resource, subject to output-format constraints. Machine-readable output should include the complete API payload or a documented stable projection.

Task output must expose latest-run and canonical-run references distinctly when present, using stable fields such as `latest_retry_index`, `latest_run_ref`, `canonical_retry_index`, and `canonical_run_ref`. Run output must expose canonical classification distinctly from run state. The CLI must not imply that the latest run is canonical unless the API explicitly identifies it as canonical.

The CLI must tolerate unknown optional fields in API responses. It should preserve unknown fields in machine-readable passthrough modes when practical. It must not fail solely because the server adds optional fields, links, enum values, or metadata that the CLI does not understand, unless those fields are required for a command's safety semantics.

## 6.6 Logs and Artifact Access

Logs and artifact commands must operate through API metadata and content endpoints. The CLI must not assume access to backend host paths, working roots, shared storage, rolling archive directories, or scheduler spool files.

Artifact listing must show metadata rather than reading local files. At minimum, artifact metadata output should identify artifact ID, producing run or external origin, logical artifact type, file type when present, path or access reference subject to API access policy, validation status, availability status, checksum when available, size when available, and publication summary when available.

Log listing must show log artifacts or log streams associated with a run as returned by the API. Log content retrieval must preserve attribution to the producing run. If the API returns paged, ranged, cursor-based, or streaming log content, the CLI must respect that model.

When printing artifact or log content to standard output, the CLI should avoid adding headers, prompts, colors, or table formatting unless the command explicitly selects a decorated view. This is required so scripts can redirect content safely. Diagnostics and download progress must be written to standard error.

When downloading content to a file path specified by the caller, the CLI should fail rather than overwrite an existing local file unless an explicit overwrite flag is supplied. Local download behavior affects only the caller's filesystem and must not be represented as a VeriProc artifact publication or backend state change.

If the API denies access to content but allows metadata access, the CLI must show the metadata allowed by policy and report content denial separately. If the API reports content unavailable due to retention, storage failure, or pending validation, the CLI must report that state without attempting direct filesystem access.

## 6.7 Cancellation and Safety

The `cancel` command requests cancellation of a run. It must call the cancellation API and must not contact the scheduler directly.

Because cancellation is a state-changing operation, an interactive CLI should ask for confirmation by default when standard input is a terminal. Automation should be able to bypass the prompt with a documented flag such as `--yes`. If standard input is not a terminal and no explicit confirmation flag is supplied, the CLI should either require `--yes` or follow a documented non-interactive safety policy.

The confirmation prompt, when used, should identify the run reference, current state if it has been fetched or is available from the API response, and a concise warning that cancellation is a request and may not stop execution immediately. The prompt must not imply that cancellation deletes tasks, runs, jobs, logs, working roots, artifacts, or provenance.

Repeated cancellation requests should be handled idempotently where the API supports that behavior. If the target run is already terminal, the CLI must surface the server response and must not create another side effect. If the API reports invalid state, cancellation unsupported, reconciliation in progress, or dependency unavailable, the CLI must preserve the server error code and map it to the appropriate exit code.

Successful cancellation command output must distinguish at least these cases when the API exposes them:

- cancellation request accepted, run not yet terminal
- cancellation completed, run is `cancelled`
- run already terminal before or during cancellation request
- cancellation could not be determined because reconciliation is required

The CLI should warn operators when cancelling a run may leave finalization, publication, downstream routing, or scheduler state in progress according to the server response. The CLI must not locally mark a run as cancelled.

## 6.8 Health, Readiness, and Version Commands

Health and readiness commands inspect backend status through API endpoints.

`health` should report process liveness or general service health as exposed by the backend. It should not be used as proof that task submission, scheduler interaction, shared storage, or station registry access is available unless the backend health endpoint explicitly defines those semantics.

`readiness` should report whether the backend is ready for control-plane operations. If the API exposes dependency state, the CLI should show dependency names, states, last checked times, and diagnostic messages subject to access policy. Dependency names may include database, scheduler adapter, station configuration source, shared storage, rolling archive configuration, migration state, or other deployment-specific checks.

The CLI must not replace readiness with local checks. Local network reachability to the API endpoint is not equivalent to backend readiness.

`version` must report the CLI version. It should report build metadata when available, supported command schema version when defined, and supported API versions. Where the backend exposes API version metadata, `version --check-api` or an equivalent command should report the configured backend API version and compatibility status.

If API compatibility cannot be determined, the CLI should fail clearly for commands that depend on unsupported or unknown API behavior. Commands that do not require server contact, such as local version reporting, should remain usable.

## 6.9 Output Formats

The CLI must support output formats suitable for both operators and automation.

`table` output should be the default for list commands when the output stream is a terminal. Tables should include stable columns, avoid truncating identifiers unless clearly indicated, and remain readable in common terminal widths. If truncation is used, machine-readable modes must provide full values.

Human-readable detail output may use a structured text layout. It should preserve all important identifiers, state fields, timestamps, failure reasons, and links returned by the API. It should avoid hiding canonical classification, force flag, parent references, or split-group references.

`json` output must use valid JSON and should preserve the API response structure unless the command documents a stable projection. Field names in CLI-generated JSON must use stable names consistent with API field names where possible. JSON output must not include progress text, prompts, or diagnostics on standard output.

`yaml` output must use a deterministic YAML representation suitable for scripting and review. It should preserve the same fields as JSON output unless documented otherwise.

Timestamps in machine-readable output must use the canonical timestamp strings returned by the API. If the CLI adds local timestamps, it must document their meaning and should use RFC 3339 with explicit timezone information.

Null values in machine-readable output must be represented explicitly when the absence of a value is meaningful, such as `canonical_run_ref: null`, `canonical_retry_index: null`, or `scheduler_identifier: null`. Human-readable output may render null values as empty cells or `none`, but it must not imply a value exists.

Quiet mode may be supported for commands where scripts need only an identifier or success indication. Quiet mode must be documented per command. For state-changing commands such as `submit`, quiet mode should still print the primary created or resolved identifier unless a command explicitly supports no-output success.

Color, terminal styling, and interactive prompts must be disabled automatically or by flag in machine-readable output modes. Machine-readable output must be deterministic for equivalent API responses.

## 6.10 Exit Codes

The CLI must use a compact, documented exit-code model. The following exit codes are recommended for the MVP reference CLI and should be treated as normative for a conforming reference implementation.

| Exit code | Category | Required use |
|---:|---|---|
| 0 | Success | The command completed successfully. Empty successful query results use this code. |
| 1 | Generic failure | An unexpected local or remote failure occurred that does not fit a more specific category. |
| 2 | Usage or argument error | Command syntax, missing arguments, invalid local flags, unreadable input files, unsupported output format, or incompatible local flag combinations prevented a valid API request. |
| 3 | Validation or bad request | The server rejected the request as invalid, including malformed payloads, invalid timestamps, invalid filters, unknown stations reported as invalid request, or field-level validation failures. |
| 4 | Not found | The requested task, run, job, artifact, split group, relationship, station revision, or content resource does not exist or is not visible to the caller. |
| 5 | Conflict or invalid state | The server reported idempotency conflict, invalid state transition, cancellation unsupported as a state or policy conflict, duplicate request conflict, or reconciliation in progress when represented as a conflict. |
| 6 | Authentication or authorization failure | Authentication failed, credentials were missing or invalid, or the caller is not authorized for the operation. |
| 7 | Unavailable, timeout, or dependency failure | The API endpoint, backend dependency, scheduler adapter, database, shared storage, station registry, or rolling archive dependency is unavailable, or the CLI request timed out before a definitive response. |
| 8 | Partial or indeterminate outcome | The CLI cannot determine whether a state-changing API request completed, for example because the connection failed after request transmission and before a response was received. |

The CLI should map server error categories defined by the API error model to these exit codes consistently. When the server provides a machine-readable error code, the CLI must preserve it in diagnostics and in machine-readable error output where possible.

Exit code `8` is intended for operator safety. It should be used only when the CLI cannot determine the outcome of a potentially state-changing request. In that case, the diagnostic message should advise the caller to query the relevant resource or retry using the same idempotency key where applicable. The CLI must not assume failure for an indeterminate submission or cancellation request.

If multiple errors occur, the CLI should return the most specific actionable exit code. For example, an authentication failure response from a reachable server should return `6`, not `7`.

## 6.11 Configuration and Profiles

The CLI must support configuration of the API endpoint. It should support profiles so that operators can work with multiple VeriProc environments such as development, test, staging, and operations.

Configuration may come from built-in defaults, a configuration file, environment variables, and command-line flags. The precedence order must be documented. The MVP reference CLI should use the following precedence, from lowest to highest:

1. built-in defaults
2. configuration file defaults
3. selected profile in the configuration file
4. environment variables
5. command-line flags

At minimum, configuration should support:

- API base URL
- API version or version preference when required by the backend
- request timeout
- output format default
- selected profile name
- authentication token reference or credential source
- TLS or mTLS settings when required by deployment policy
- proxy settings when appropriate for the deployment environment

The CLI should define a default user-level configuration path appropriate to the operating system. On POSIX systems, the default may be under the user's configuration directory, such as `~/.config/veriproc/config.yaml`. Implementations may also support a project-local configuration file for automation, but project-local configuration must not silently override explicit environment variables or flags.

Environment variables should have a stable prefix, such as `VERIPROC_`. At minimum, the CLI should support environment variables equivalent to API base URL, selected profile, authentication token or token file, request timeout, and default output format.

Command-line flags must have highest precedence for the invocation in which they appear. A flag that selects a profile should affect values loaded from the configuration file before environment-variable and per-command flag overrides are applied, according to the documented precedence model.

Authentication configuration is deployment-specific. The CLI may support bearer tokens, token files, mTLS certificate paths, or other mechanisms required by the API. It must avoid printing secrets in ordinary diagnostics, debug output, or machine-readable command payloads. If credentials are missing or rejected, the command must use the authentication or authorization exit code.

The CLI may provide commands to inspect effective local configuration. Such commands must avoid printing secret values by default. Any command that writes local CLI configuration affects only the caller's CLI configuration and must not be represented as server configuration mutation.

## 6.12 Compatibility and Non-Goals

The CLI is not the normative source of backend semantics. The REST API and the control-plane specification define task submission, validation, state transitions, cancellation, output validation, downstream routing, split-group readiness, deduplication, provenance, and persistence behavior.

The CLI should be compatible with additive API changes where possible. It should tolerate unknown optional response fields, unknown links, new metadata blocks, and new enum values by preserving or displaying them without failing unless a command requires a known value for safety. The CLI may reject unknown values in local flags when the value cannot be mapped to a documented API parameter.

A CLI version should declare which API versions it supports. If a backend serves an unsupported API version, the CLI should fail clearly before performing state-changing operations. If a command is compatible with a subset of the backend API, the CLI may allow that command while warning that other commands are unsupported.

The CLI must not be treated as a substitute for direct API integration in all cases. Batch systems, workflow systems, dashboards, and other clients may integrate with the REST API directly. The CLI provides a stable operator and scripting surface, not an exclusive client interface.

The CLI must not provide an undocumented second control path. Local utilities such as `config validate` may validate documents for convenience, but they must not publish station revisions, modify instance configuration, mutate database state, create rolling archive entries, write working-root control files, or bypass API validation unless a future chapter defines explicit administrative API semantics for those operations.

Rich terminal user interfaces, graphical workflow editing, live dashboards, shell completion, interactive form-based submission, and long-running operator consoles are out of scope for the MVP unless explicitly provided as optional extensions. Such extensions must preserve the same API-first and identity-preserving rules.

The CLI should not promise stronger consistency than the API provides. If the API documents eventual consistency for scheduler-derived or filesystem-derived fields, the CLI must expose the relevant observed timestamps or availability states rather than hiding lag.

## 6.13 Example Commands

This section is informative. The examples illustrate one possible command spelling for a conforming CLI.

Submit a task from a YAML document:

```sh
veriproc submit --file task.yaml --idempotency-key client-req-7f84d0
```

Submit a task from standard input and return JSON:

```sh
veriproc submit --file - --output json < task.yaml
```

Submit a simple task using flags:

```sh
veriproc submit \
  --station SCENE-L2 \
  --start 2025-07-03T11:15:39Z \
  --end 2025-07-03T11:30:00Z \
  --idempotency-key client-req-7f84d0
```

Query a task and show the full response as YAML:

```sh
veriproc task get task-20250703T111239000-a7sf7f --output yaml
```

List running tasks for a station:

```sh
veriproc task list --station SCENE-L2 --state running --output table
```

List runs for a task and preserve the paginated API envelope:

```sh
veriproc run list --task task-20250703T111239000-a7sf7f --output json
```

Inspect one run:

```sh
veriproc run get task-20250703T111239000-a7sf7f/r5
```

List jobs for a run:

```sh
veriproc run jobs task-20250703T111239000-a7sf7f/r5
```

List output artifacts for the canonical run of a task:

```sh
veriproc artifact list --task task-20250703T111239000-a7sf7f --canonical-only --type output
```

Print log content through the API:

```sh
veriproc logs task-20250703T111239000-a7sf7f/r5 --name algorithm.log
```

Download an artifact through the API without overwriting an existing local file:

```sh
veriproc artifact get art-019dfc19-2005-77e4-88db-28904c85b6fd --content --output-file ./SCE_2__CSM.nc
```

Query provenance links for a run:

```sh
veriproc relationships --run task-20250703T111239000-a7sf7f/r5 --output json
```

Request cancellation with explicit non-interactive confirmation:

```sh
veriproc cancel task-20250703T111239000-a7sf7f/r5 --yes
```

Check backend readiness:

```sh
veriproc readiness --output table
```

Report CLI version and check backend API compatibility:

```sh
veriproc version --check-api
```

Validate a local task submission document without creating a task:

```sh
veriproc config validate --kind task-submission --file task.yaml
```
