# 1. Introduction and Goals

Inspired by NASA's S4P framework, VeriProc is a modern, lightweight orchestration system for satellite Earth Observation (EO) data processing. S4P proved that simple file-driven *stations* with cascading work orders can reliably scale high-volume science pipelines — as demonstrated across missions like TRMM and AQUA — without heavy databases or GUIs.

VeriProc adapts that core idea for contemporary cloud and hybrid HPC environments, replacing Perl scripts and token files with a clean REST API, YAML tasks, and a persistent state store. Orchestration is split into two layers: **tasks** that travel between stations and carry routing and provenance, and **job orders** that describe the concrete execution inside a single station. Station algorithms see only the job order — they are fully isolated from the orchestration infrastructure.

## Objectives

The system must:

- **Accept tasks** — a task identifies the destination station, the time window to process, and a history of the stations it has already visited; the backend uses the task together with the station config to generate a fully resolved job order.
- **Generate** YAML job orders by combining the incoming task with the station config; products and auxiliaries are located by searching ordered folder lists (`input_folders`) defined in the station config and symlinked into the working root.
- **Isolate** each job in a dedicated working directory (`working_root`); all resolved input files are symlinked into an `input/` subdirectory so the algorithm sees a fully self-contained workspace, and all artifacts — job order, logs, outputs — remain within that directory. The algorithm has no knowledge of the orchestration layer.
- **Deduplicate** automatically: the same combination of input product files never creates more than one run for a given station unless explicitly forced via the API.
- **Dispatch** each job order as an ephemeral SLURM job running in a dedicated container — no persistent station processes; one task, one job, one container lifetime.
- **Track** run state durably in a relational database (Postgres in production, SQLite in development), switchable via a single config value.
- **Chain** downstream processing automatically: on job completion the framework reads the algorithm's output task descriptors (or falls back to the station's `downstream` list) and creates follow-on tasks for the next stations, carrying forward the provenance history.
- **Split and aggregate** — support fractional processing where a larger input (e.g. 3-minute granule) is split into smaller processing units (e.g. 10-second granules), processed in parallel across stations, and reassembled downstream.
- **Expose** run status, logs, and artifacts through a REST API consumed by client applications.

Unlike S4P's always-on station runners, VeriProc never keeps a persistent worker waiting for work. Every job is a fresh, isolated container instance whose lifetime matches the task it processes. Autoscaling is handled natively by the executor (SLURM partition limits, K8s HPA); VeriProc tracks state, not resources.

## Scope

**In scope**

- Backend control plane with switchable Postgres/SQLite state store
- Pluggable execution layer (SLURM primary; K8s/HTCondor via adapters)
- YAML-defined stations with resource profiles and container images
- REST API with YAML payloads for all client frontends
- Dev and production deployments on NFS-shared VMs and HPC clusters

**Out of scope (MVP)**

- Backend-level autoscaling (delegated to the executor)
- Real-time streaming or sub-second latency pipelines
- Deployments without a shared filesystem (shared FS is assumed)
- Redis or additional database backends beyond Postgres/SQLite
- Multi-tenancy (single mission/tenant; extensible later)

## Target

Single-tenant MVP for L1→L2 satellite processing pipelines (e.g., CO2M granules), designed to be extended to further processing levels and additional missions.
