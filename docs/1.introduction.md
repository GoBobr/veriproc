# 1. Introduction and Goals

Inspired by NASA's S4P framework, VeriProc is a modern, lightweight orchestration system for satellite Earth Observation (EO) data processing. S4P proved that simple file-driven *stations* with directory triggers and cascading work orders can reliably scale high-volume science pipelines — as demonstrated across missions like TRMM and AQUA — without heavy databases or GUIs.

VeriProc adapts that core idea for contemporary cloud and hybrid HPC environments, replacing Perl scripts and token files with a clean REST API, YAML work orders, and a persistent state store.

## Objectives

The system must:

- **Trigger** on new data arriving via S3 prefix, NFS directory watch, or direct API call.
- **Generate** YAML work orders by pre-filling a per-station template with resolved inputs; products and auxiliaries are located by searching ordered folder lists (`product_folders`, `aux_folders`) defined in the station config.
- **Isolate** each job in a dedicated working directory (`working_root`); all resolved input files are symlinked into an `input/` subdirectory so the algorithm sees a fully self-contained workspace, and all artifacts — work order, logs, outputs — remain within that directory.
- **Deduplicate** automatically: the same combination of input product files never creates more than one run for a given station unless explicitly forced via the API.
- **Dispatch** each work order as an ephemeral SLURM job running in a dedicated container — no persistent station processes; one work order, one job, one container lifetime.
- **Track** run state durably in a relational database (Postgres in production, SQLite in development), switchable via a single config value.
- **Chain** downstream processing automatically: on job completion the backend evaluates the station's trigger rules against the new outputs and creates follow-on work orders where conditions are met.
- **Expose** run status, logs, and artifacts through a REST API consumed by client applications.

Unlike S4P's always-on station runners, VeriProc never keeps a persistent worker waiting for work. Every job is a fresh, isolated container instance whose lifetime matches the work order it processes. Autoscaling is handled natively by the executor (SLURM partition limits, K8s HPA); VeriProc tracks state, not resources.

## Scope

**In scope**

- Backend control plane with switchable Postgres/SQLite state store
- Pluggable execution layer (SLURM primary; K8s/HTCondor via adapters)
- YAML-defined stations with resource profiles and container images
- NFS and S3 directory triggers with configurable filename patterns
- REST API with YAML payloads for all client frontends
- Dev and production deployments on NFS-shared VMs and HPC clusters

**Out of scope (MVP)**

- Backend-level autoscaling (delegated to the executor)
- Real-time streaming or sub-second latency pipelines
- Deployments without a shared filesystem (shared FS is assumed)
- Redis or additional database backends beyond Postgres/SQLite
- Multi-tenancy (single mission/tenant; extensible later)

## Target

Single-tenant MVP for L1→L2 satellite processing pipelines (e.g., CO2M granules), designed to be extended to further processing levels and additional missions.
