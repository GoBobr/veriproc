# 3. Conceptual Model and Terminology

This chapter defines the core abstractions that VeriProc is built on. All other chapters reference these terms. Where S4P used analogous concepts — stations, work orders, triggers — the mapping is noted explicitly.

---

## Station

A **station** is the atomic unit of processing. It represents a single, named algorithm or processing step and encapsulates everything needed to run it:

- the container image and execution mode (Apptainer, Docker, Plane)
- the command template to invoke inside the container
- resource requirements (CPU, memory)
- the work order template to pre-fill before dispatch
- the input product and auxiliary file patterns it consumes
- the output file patterns it produces
- the trigger rules that activate it

Stations are defined statically in YAML configuration files. A station has no runtime process of its own — it is purely a specification. VeriProc instantiates it only when a trigger fires, creating a short-lived job for that specific execution.

> *S4P equivalent: a station directory with its `config.cfg` and `do_`-script, but without the always-running station process.*

---

## Trigger

A **trigger** is a rule attached to a station that defines the condition under which a new work order should be created. A station may have multiple triggers; any one match is sufficient to start a run.

| Trigger type | Description |
|---|---|
| `dir_poll` | Periodically scans a directory for files matching a filename pattern; fires when a new, complete file is detected. The trigger may specify a dedicated `folder` to scan; if omitted, the station's `product_folders` list is used in order. |
| `upstream` | Fires when a named upstream station completes successfully. Does not require its own folder — it initiates an input resolution pass against the station's `product_folders` using the completed run's output as the temporal anchor. |
| `api` | Fired programmatically via a REST API call from an external client or operator; supports a `force` flag to bypass deduplication. |

Triggers are evaluated independently: `dir_poll` triggers run on a configured polling interval; `upstream` triggers are evaluated by the backend immediately after a run reaches `complete` state. All trigger types are subject to the same deduplication check before input resolution proceeds.

---

## Work Order

A **work order** is a fully resolved YAML document that describes one concrete execution of a station. It is created from the station's `workorder_template` by substituting all variable placeholders with actual values: resolved input paths, output directories, timing parameters, and facility metadata.

Once written to the run's working root, the work order is immutable. The station's `command` receives the path to this file as its sole argument. The science algorithm reads all its configuration from the work order; it has no other interface to VeriProc.

All paths in a work order are expressed relative to the working root (e.g. `./input/filename.nc`, `./output/`). This ensures the algorithm is fully contained within the working root and does not reference external filesystem locations.

Key sections of a work order:

- **`station_id`** — which station definition governs this execution
- **`order`** — temporal bounds (start/end) of the processing window
- **`facility`** — operational context (processing centre, environment, test flag)
- **`inputs`** — list of `{file_type, path}` entries pointing to symlinks in `./input/`
- **`outputs`** — expected output file types with `./output/` as their target directory
- **`dyn_params`** — runtime parameters passed through to the algorithm

> *S4P equivalent: the work order file (`.wo`) placed in a station's input directory, but generated from a template and scoped to an isolated working directory.*

---

## Run

A **run** is a single execution attempt of a station against one specific work order. It is the primary trackable entity in VeriProc's state store.

Every run has a unique `run_id` and progresses through a defined state machine:

```
pending → dispatched → complete
                    ↘ failed
```

| State | Meaning |
|---|---|
| `pending` | Work order created; waiting to be submitted to the executor. |
| `dispatched` | SLURM job submitted; container is starting or running. |
| `complete` | Job exited successfully; all mandatory outputs validated on shared storage. |
| `failed` | Job exited with an error, timed out, or mandatory outputs are missing. |

A run record stores: `run_id`, `station_id`, work order path, SLURM job ID, state, timestamps, and log path. Failed runs can be re-submitted manually via the API without creating a new `run_id`.

---

## Job

A **job** is the ephemeral SLURM batch submission that executes a run. It is a one-to-one mapping: one run produces exactly one active job at a time. The job starts a fresh container, executes the station's command with the work order path, and exits. No process persists after the job ends.

The backend tracks job state by polling `sacct`; the job itself does not call back into VeriProc.

---

## Pipeline

A **pipeline** is an implicitly defined directed graph of stations connected by `upstream` trigger rules. There is no explicit pipeline object in VeriProc's configuration — the graph emerges from the trigger relationships declared in individual station configs.

A linear two-stage pipeline, for example, is expressed simply as:

```yaml
# scene-l2-station.yaml
triggers:
  - type: upstream
    station_id: SCENE-L1
```

Fan-out (one upstream, multiple downstream stations) and fan-in (multiple upstreams required before firing) are supported through multiple trigger entries and input matching rules.

---

## Input Product and Auxiliary

Inputs to a station are categorised into two classes:

- **Product inputs** — primary science data files whose availability determines whether a run can be formed. Typically time-bounded by a sensing window with configurable temporal margins.
- **Auxiliary inputs** — supporting files (calibration data, configuration, look-up tables). An auxiliary may be marked `mandatory: False`, in which case the run proceeds without it. Auxiliaries may additionally have `satid_strict: True` to require satellite-ID matching.

Both classes are declared in the station config as filename patterns. Resolution is performed by searching ordered folder lists:

- **`product_folders`** — an ordered list of directories searched for product files. The backend scans each folder in sequence and uses the first matching file found. This allows a hot rolling archive to be listed before a slower deep archive.
- **`aux_folders`** — the equivalent ordered list for auxiliary files.

Once resolved, the actual source files are never copied. The backend creates a symlink for each resolved file inside the run's `working_root/input/` directory. All paths injected into the work order point to these symlinks.

---

## Working Root

The **working root** is a unique directory created on shared storage for each run, at the path `<working_root_base>/<station_id>/<run_id>/`. It is the self-contained workspace for the entire lifecycle of a run:

```
<working_root>/
  workorder.yaml    ← populated work order (written before dispatch)
  input/            ← symlinks to resolved product and auxiliary source files
  output/           ← output products written by the algorithm
  logs/             ← job.stdout and job.stderr captured by SLURM
  temp/             ← algorithm temporary files
```

The SLURM job is submitted with the working root as its working directory (`--chdir`). All relative paths in the work order resolve correctly without any path manipulation inside the container. The working root persists after job completion and serves as the definitive record of what was run, with what inputs, and what was produced.

---

## Input Deduplication

VeriProc maintains a **processed-file registry** in the state store — a table that records every product input file path that has been successfully processed by each station. Before creating a new work order, the backend checks whether the triggering product file is already present in this registry for the target station.

- If it **is** registered: the trigger event is discarded silently. No run is created.
- If it **is not** registered: input resolution proceeds normally.
- The registry entry is written only when the run reaches `complete` state, ensuring that a failed or partial run does not block a retry.
- Any trigger type (including `dir_poll` and `upstream`) can be overridden with a `force: true` flag via the API, which bypasses the deduplication check and creates a new run regardless.

This mechanism guarantees that on-disk data appearing multiple times (e.g. from archive re-ingestion or polling overlap) does not cause duplicate processing.

---

## Artifact

An **artifact** is any file produced within a run's working root — output products, logs, the work order YAML, and temporary files. Artifacts are referenced in the database by their path under the working root; they are never moved or managed by VeriProc after creation.

Output artifacts declared in the station config with `mandatory: True` are checked for existence in `working_root/output/` before a run is marked `complete`. Optional outputs (`mandatory: False`) are recorded if present but do not affect the final run state.

---

## Facility

**Facility** is the operational context block carried in every work order. It records static metadata about the environment in which a run executes — processing centre identifier, acquisition station, operational vs. test mode — and is passed through unchanged to the science algorithm. VeriProc populates it from the backend's deployment configuration.

---

## State Store

The **state store** is VeriProc's relational database — SQLite in development, Postgres in production. It holds all durable control state: station definitions, run records, trigger history, and artifact references. It is the single source of truth for any query made via the REST API. The shared filesystem holds artefact bytes; the state store holds everything else.

---

## Executor

The **executor** is the pluggable component responsible for translating a dispatched run into a running job on the underlying compute infrastructure. The default executor submits `sbatch` jobs to SLURM; alternative executors (K8s, HTCondor) implement the same adapter interface. The executor has no persistent state — it submits, and the backend polls.

---

## Shared Storage

**Shared storage** is the filesystem accessible to both the VeriProc backend and all SLURM compute nodes. It carries input data, resolved work order files, output products, and logs. VeriProc assumes a POSIX-compatible shared filesystem (NFSv4 or AWS EFS); no file transfer occurs between the backend and the job — all paths are absolute and valid on all nodes.

---

## Glossary

| Term | Short definition |
|---|---|
| Station | Named processing step specification (config + template + triggers) |
| Trigger | Rule that fires when a station's input conditions are met |
| Work order | Fully resolved YAML document describing one concrete execution; lives in the working root |
| Run | Single traceable execution attempt; has a state and a `run_id` |
| Job | Ephemeral SLURM batch submission backing one run |
| Pipeline | Implicit directed graph formed by station trigger dependencies |
| Product input | Primary science data file required to form a run |
| `product_folders` | Ordered list of directories searched for product files; first match wins |
| Auxiliary input | Supporting file (cal/config); may be optional |
| `aux_folders` | Ordered list of directories searched for auxiliary files; first match wins |
| Working root | Isolated per-run directory holding the work order, symlinked inputs, outputs, and logs |
| Input deduplication | Mechanism preventing the same product file from triggering more than one run per station |
| Processed-file registry | State store table recording product files already successfully processed |
| Artifact | Any file produced within a working root and tracked by VeriProc |
| Facility | Operational context metadata block in every work order |
| State store | Relational DB holding all VeriProc control state |
| Executor | Adapter that submits and queries jobs on the compute backend |
| Shared storage | POSIX filesystem accessible to backend and compute nodes |
