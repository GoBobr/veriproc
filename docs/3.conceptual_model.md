# 3. Conceptual Model and Terminology

This chapter defines the core abstractions that VeriProc is built on. All other chapters reference these terms. Where S4P used analogous concepts — stations, work orders — the mapping is noted explicitly.

---

## Station

A **station** is the atomic unit of processing. It represents a single, named algorithm or processing step and encapsulates everything needed to run it:

- the container image and execution mode (Apptainer, Docker, Plane)
- the command template to invoke inside the container
- resource requirements (CPU, memory)
- the input product and auxiliary file patterns it consumes
- the output file patterns it produces
- the default `downstream` station list for task routing

Stations are defined statically in YAML configuration files. A station has no runtime process of its own — it is purely a specification. VeriProc instantiates it only when a task arrives, creating a short-lived job for that specific execution.

> *S4P equivalent: a station directory with its `config.cfg` and `do_`-script, but without the always-running station process.*

---

## Task

A **task** is the orchestrator-level token that travels between stations. It is the primary unit of work visible to the control plane and carries three pieces of information:

- **`id`** — a compound identifier consisting of a 4-letter `proc_type` prefix (identifying the destination station) and a globally unique numeric sequence, separated by an underscore (e.g. `sce2_123456`). The numeric part is drawn from a single global auto-increment sequence, ensuring IDs are unique across all stations and loosely time-ordered.
- **`start` / `end`** — the time window to process. These values flow directly into the job order's `order.start` and `order.end` fields.
- **`history`** — an ordered log of every station the data has already passed through, each entry recording the task ID and the completion timestamp.

Tasks can enter the system in two ways:

1. **External submission** — a client submits a task via the REST API, specifying the target station and time window.
2. **Framework generation** — after a station job completes, the framework reads the algorithm's `task-out.yaml` (if present) or falls back to the station's `downstream` config to create follow-on tasks. The framework automatically appends the completed task to each new task's `history`.

A task is not an execution record — it is a *request*. Once the framework receives a task it resolves inputs, generates the job order, and dispatches the job. The execution itself is tracked by the **run** entity.

> *The task has no S4P equivalent. S4P's cascading was driven by file appearance in station directories; VeriProc introduces the task as an explicit routing and provenance token.*

---

## Job Order

A **job order** is a fully resolved YAML document that describes one concrete execution of a station. It is generated by the framework from the incoming task and the station config — there is no separate template file. The framework combines the task's time window with the station's input/output definitions and the resolved file paths to produce a self-contained execution descriptor.

Once written to the working root, the job order is immutable. The station's `command` receives the path to this file as its sole argument. The science algorithm reads all its configuration from the job order; **it has no other interface to VeriProc** — it knows nothing about tasks, pipelines, or orchestration.

All paths in a job order are expressed relative to the working root (e.g. `./input/filename.nc`, `./output/`). This ensures the algorithm is fully contained within the working root and does not reference external filesystem locations.

Key sections of a job order:

- **`station_id`** — which station definition governs this execution
- **`order`** — temporal bounds (start/end) of the processing window, taken from the task
- **`facility`** — operational context (processing centre, environment, test flag)
- **`inputs`** — list of `{file_type, path}` entries pointing to symlinks in `./input/`
- **`outputs`** — expected output file types with `./output/` as their target directory
- **`dyn_params`** — runtime parameters passed through to the algorithm

> *S4P equivalent: the work order file (`.wo`) placed in a station's input directory, but now generated programmatically and scoped to an isolated working directory.*

---

## Run

A **run** is a single execution attempt of a station for one specific task. It is the execution-layer tracking entity that links a task to its SLURM job.

Every run has a unique `run_id` and progresses through a defined state machine:

```
pending → dispatched → complete
                    ↘ failed
```

| State | Meaning |
|---|---|
| `pending` | Job order generated; waiting to be submitted to the executor. |
| `dispatched` | SLURM job submitted; container is starting or running. |
| `complete` | Job exited successfully; all mandatory outputs validated on shared storage. |
| `failed` | Job exited with an error, timed out, or mandatory outputs are missing. |

A run record stores: `run_id`, `task_id`, `station_id`, job order path, SLURM job ID, state, timestamps, and log path. The task is the *what*; the run is the *how*. One task maps to one run (retries create a new run for the same task).

---

## Job

A **job** is the ephemeral SLURM batch submission that executes a run. It is a one-to-one mapping: one run produces exactly one active job at a time. The job starts a fresh container, executes the station's command with the job order path, and exits. No process persists after the job ends.

The backend tracks job state by polling `sacct`; the job itself does not call back into VeriProc.

---

## Pipeline

A **pipeline** is an implicitly defined directed graph of stations connected by `downstream` routing lists. There is no explicit pipeline object in VeriProc’s configuration — the graph emerges from the relationships declared in individual station configs. Tasks travel through this graph, accumulating history at each step.

A linear two-stage pipeline, for example, is expressed simply by listing the next station in the `downstream` config of the previous one.

Fan-out (one upstream, multiple downstream stations) and fan-in (multiple upstreams required before firing) are supported through `downstream` lists and the `task-out.yaml` mechanism. Fractional processing — where a station splits input into smaller units, processes them in parallel across stations, and aggregates the results — is a natural extension of fan-out/fan-in expressed through task routing.

---

## Input Product and Auxiliary

Inputs to a station are categorised into two classes:

- **Product inputs** — primary science data files whose availability determines whether a run can be formed. Typically time-bounded by a sensing window with configurable temporal margins.
- **Auxiliary inputs** — supporting files (calibration data, configuration, look-up tables). An auxiliary may be marked `mandatory: False`, in which case the run proceeds without it. Auxiliaries may additionally have `satid_strict: True` to require satellite-ID matching.

Both classes are declared in the station config as filename patterns. Resolution is performed by searching the station's **`input_folders`** — a single ordered list of directories. The backend scans each folder in sequence and uses the first matching file found. This allows a hot rolling archive to be listed before a slower deep archive, and both product and auxiliary files to be located from the same search path.

Once resolved, the actual source files are never copied. The backend creates a symlink for each resolved file inside the task's `working_root/input/` directory. All paths injected into the job order point to these symlinks.

---

## Working Root

The **working root** is a unique directory created on shared storage for each task, at the path `<working_root_base>/<station_id>/<task_id>/`. It is the self-contained workspace for the entire lifecycle of a task's execution:

```
<working_root>/
  joborder.yaml     ← generated by framework from station config + task
  input/            ← symlinks to resolved product and auxiliary source files
  output/           ← output products written by the algorithm
  task-out.yaml     ← written by algorithm (optional); describes downstream tasks
  logs/             ← job.stdout and job.stderr captured by SLURM
  temp/             ← algorithm temporary files
```

The SLURM job is submitted with the working root as its working directory (`--chdir`). All relative paths in the job order resolve correctly without any path manipulation inside the container. The working root persists after job completion and serves as the definitive record of what was run, with what inputs, and what was produced.

---

## Deduplication

VeriProc maintains a **deduplication registry** in the state store that tracks which time windows have been successfully processed by each station. Before creating a new job order for an incoming task, the backend checks whether the task's time window has already been completed for the target station.

- If it **has** been processed: the task is discarded silently. No run is created.
- If it **has not** been processed: input resolution proceeds normally.
- The registry entry is written only when the run reaches `complete` state, ensuring that a failed or partial run does not block a retry.
- Any task can be submitted with a `force: true` flag via the API, which bypasses the deduplication check and creates a new run regardless.

This mechanism guarantees that duplicate task submissions (e.g. from archive re-ingestion) do not cause duplicate processing.

---

## Artifact

An **artifact** is any file produced within a task's working root — output products, logs, the job order YAML, `task-out.yaml`, and temporary files. Artifacts are referenced in the database by their path under the working root; they are never moved or managed by VeriProc after creation.

Output artifacts declared in the station config with `mandatory: True` are checked for existence in `working_root/output/` before a run is marked `complete`. Optional outputs (`mandatory: False`) are recorded if present but do not affect the final run state.

---

## Facility

**Facility** is the operational context block carried in every job order. It records static metadata about the environment in which a run executes — processing centre identifier, acquisition station, operational vs. test mode — and is passed through unchanged to the science algorithm. VeriProc populates it from the backend's deployment configuration.

---

## State Store

The **state store** is VeriProc’s relational database — SQLite in development, Postgres in production. It holds all durable control state: station definitions, task records (including history), run records, and artifact references. It is the single source of truth for any query made via the REST API. The shared filesystem holds artefact bytes; the state store holds everything else.

---

## Executor

The **executor** is the pluggable component responsible for translating a dispatched run into a running job on the underlying compute infrastructure. The default executor submits `sbatch` jobs to SLURM; alternative executors (K8s, HTCondor) implement the same adapter interface. The executor has no persistent state — it submits, and the backend polls.

---

## Shared Storage

**Shared storage** is the filesystem accessible to both the VeriProc backend and all SLURM compute nodes. It carries input data, job order files, output products, and logs. VeriProc assumes a POSIX-compatible shared filesystem (NFSv4 or AWS EFS); no file transfer occurs between the backend and the job — all paths are absolute and valid on all nodes.

---

## Task Output Descriptor

The **task output descriptor** (`task-out.yaml`) is an optional file written by the algorithm into the working root. It lists the downstream tasks to create after the current job completes. Each entry specifies the target station (by `proc_type`) and the time window.

If the algorithm does not write a `task-out.yaml`, the framework falls back to the station's `downstream` config list and creates one task per entry using the same time window as the completed task.

This mechanism gives algorithms full control over routing and is the foundation for fractional processing: a splitter station can emit N tasks with sub-windows targeting a parallel processing station, and an aggregator can emit a single task covering the recombined window.

---

## Fractional Processing

**Fractional processing** is a pattern where a larger input granule is split into smaller processing units, processed in parallel, and then aggregated back. VeriProc supports this through the task and `task-out.yaml` mechanism:

1. A splitter station receives a task with a wide time window (e.g. 3 minutes). Its algorithm writes a `task-out.yaml` with N entries, each targeting the processing station with a narrow sub-window (e.g. 10 seconds).
2. The framework creates N independent tasks, each inheriting the splitter's history. These are dispatched concurrently.
3. An aggregation station is triggered when all sub-tasks for a given parent window have completed. It receives a task covering the original wide window and produces the consolidated output.

The task history carries the splitter's task ID, so lineage can be traced back through the split point without referencing the individual sub-tasks.

---

## Glossary

| Term | Short definition |
|---|---|
| Station | Named processing step specification (config + downstream routing) |
| Task | Orchestrator-level token carrying destination station, time window, and provenance history |
| Job order | Fully resolved YAML execution descriptor generated from task + station config; the algorithm's sole interface |
| `task-out.yaml` | Optional file written by the algorithm describing downstream tasks to create |
| Run | Execution-layer record linking a task to a SLURM job; has a state and a `run_id` |
| Job | Ephemeral SLURM batch submission backing one run |
| Pipeline | Implicit directed graph formed by station downstream dependencies |
| Fractional processing | Pattern where input is split into sub-tasks, processed in parallel, and aggregated |
| Product input | Primary science data file required to form a run |
| Auxiliary input | Supporting file (cal/config); may be optional |
| `input_folders` | Ordered list of directories searched for product and auxiliary files; first match wins |
| Working root | Isolated per-task directory holding the job order, symlinked inputs, outputs, and logs |
| Deduplication | Mechanism preventing the same time window from being processed twice per station |
| Processed-file registry | State store table recording product files already successfully processed |
| Artifact | Any file produced within a working root and tracked by VeriProc |
| Facility | Operational context metadata block in every work order |
| State store | Relational DB holding all VeriProc control state |
| Executor | Adapter that submits and queries jobs on the compute backend |
| Shared storage | POSIX filesystem accessible to backend and compute nodes |
