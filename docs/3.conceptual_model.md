# 3. Conceptual Model and Terminology

This chapter defines the domain entities used by VeriProc. Each entity is specified using a fixed template so that implementers can answer the same questions consistently: what the entity is, who creates it, what fields it carries, whether it is mutable, what validation applies, how it is persisted, and how failure is handled.

Unless otherwise stated, all identifiers must be globally unique within the deployment scope.

---

## 3.1 Station

**Purpose**

A station is the declarative specification of one processing step.

**Required fields**

- `station_id`
- `proc_type`
- execution mode
- execution image or executable reference
- command template
- resource requirements
- input folder references, including rolling archive references where used
- input definitions
- output definitions

**Optional fields**

- default downstream list
- output publication policy
- station-specific runtime parameters
- validation hooks
- timeout policy
- cancellation policy

**Immutable vs mutable fields**

- A persisted station revision is immutable.
- The logical station name may evolve only by creating a new revision.

**Creation trigger**

- Created by configuration load or configuration publication.

**Validation rules**

- Must validate against the station configuration schema.
- Must reference a valid execution mode.
- Must reference only configured rolling archive identifiers when using `rolling:<id>` folder references.
- Must define all mandatory output declarations needed for completion checks.

**Failure behavior**

- An invalid station revision must not be used for run generation.

**Persistence rules**

- The exact station revision used by a run must be recorded durably.

---

## 3.2 Station Revision

**Purpose**

A station revision is the frozen identity of a station configuration at the time a run is created.

**Required fields**

- revision identifier
- content hash or equivalent immutable revision marker
- schema version
- effective timestamp or publication version

**Optional fields**

- human-readable label
- source repository commit

**Immutable vs mutable fields**

- Fully immutable.

**Creation trigger**

- Created whenever a station definition changes in a way that may affect execution semantics.

**Validation rules**

- Must uniquely identify the effective configuration used by a run.

**Failure behavior**

- If no valid station revision can be resolved, task preparation must fail.

**Persistence rules**

- Must be referenced by job orders, runs, and processing fingerprints.

---

## 3.3 Task

**Purpose**

A task is the immutable routing request that tells VeriProc what time window to process and where to send it.

**Required fields**

- `task_id`
- destination station or `proc_type`
- `start`
- `end`
- routing history

**Optional fields**

- parent task identifier
- parent run identifier
- split-group identifier
- submission idempotency key
- force flag for intentional reprocessing
- client metadata
- priority

**Immutable vs mutable fields**

- Routing content is immutable after creation.
- Backend-maintained status summaries may change over time.

**Creation trigger**

- Created by API submission or by downstream creation from a completed run.

**Validation rules**

- `start` must be less than or equal to `end`.
- Destination station must resolve to a known station.
- Parent references, if present, must refer to existing records.
- A forced task must be recorded as forced so that canonical and non-canonical runs remain distinguishable.

**Failure behavior**

- Invalid tasks must be rejected before dispatch planning.

**Persistence rules**

- Must be stored durably before any run is created from it.

**Notes**

- A downstream task is a new task, not a mutable extension of its parent.

---

## 3.4 Routing History

**Purpose**

Routing history is the append-only, human-readable record of stations or tasks previously traversed by the data.

**Required fields**

- ordered entries containing prior task or station identity and completion time

**Optional fields**

- short status note

**Immutable vs mutable fields**

- Existing entries are immutable.
- New downstream tasks may append new entries derived from the parent.

**Creation trigger**

- Derived when a downstream task is created.

**Validation rules**

- Entries must remain ordered and internally consistent.

**Failure behavior**

- If history cannot be extended consistently, downstream task creation must fail.

**Persistence rules**

- Stored with the task for readability and debugging.

**Notes**

- Routing history is not sufficient as the full provenance model.

---

## 3.5 Provenance Link

**Purpose**

A provenance link records an explicit parent-child relationship between domain objects such as tasks, runs, and artifacts.

**Required fields**

- source object type and identifier
- target object type and identifier
- relationship type

**Optional fields**

- contribution role
- creation reason

**Immutable vs mutable fields**

- Immutable after creation.

**Creation trigger**

- Created when downstream tasks, artifacts, or aggregation relationships are materialized.

**Validation rules**

- Referenced objects must exist.
- Relationship type must be recognized.

**Failure behavior**

- If required provenance edges cannot be persisted, the enclosing finalization step must fail or remain incomplete.

**Persistence rules**

- Must be queryable independently of the task history text.

---

## 3.6 Job Order

**Purpose**

A job order is the immutable execution descriptor consumed by the station algorithm.

**Required fields**

- job order schema version
- run identifier
- task identifier
- station revision identifier
- processing window
- facility block
- resolved input references
- expected outputs

**Optional fields**

- runtime parameters
- manifest reference
- algorithm flags
- generator identity when a custom generator is used

**Immutable vs mutable fields**

- Immutable once written.

**Creation trigger**

- Created during run preparation after input resolution succeeds.

**Validation rules**

- Must validate against the job order schema.
- All referenced paths must resolve within the working root namespace.
- Custom-generated job orders must satisfy the same schema and containment rules as system-generated job orders.

**Failure behavior**

- If job order generation or validation fails, the run must not be dispatched.

**Persistence rules**

- Must be written to the working root and associated with the run record.

---

## 3.7 Resolved Input Manifest

**Purpose**

The resolved input manifest is the frozen record of which inputs were selected, which optional inputs were absent, and why those selections were made.

**Required fields**

- run identifier
- one entry per declared input
- selection outcome for each entry

**Optional fields**

- checksum
- source directory precedence
- source rolling archive identifier when selected through a rolling archive
- version metadata
- tie-break reason

**Immutable vs mutable fields**

- Immutable once dispatch begins.

**Creation trigger**

- Created after input resolution and before job order generation completes.

**Validation rules**

- All mandatory inputs must resolve successfully.
- Optional missing inputs must be marked explicitly.

**Failure behavior**

- Missing mandatory inputs must prevent dispatch.

**Persistence rules**

- Must be persisted durably and referenced by the run.

---

## 3.8 Run

**Purpose**

A run is one execution attempt for one task.

**Required fields**

- `run_id`
- `task_id`
- station revision identifier
- current state
- working root path

**Optional fields**

- scheduler job identifier
- retry index
- finalization summary
- canonical or non-canonical classification
- failure reason

**Immutable vs mutable fields**

- `run_id`, `task_id`, and station revision are immutable.
- State and operational metadata are mutable until terminal state.

**Creation trigger**

- Created when the backend decides to attempt execution for a task.

**Validation rules**

- Must reference an existing task.
- Must have a valid state transition path.

**Failure behavior**

- A failed run remains part of the durable audit history.
- Retry must create a new run.

**Persistence rules**

- Must be persisted before dispatch is considered successful.

---

## 3.9 Job

**Purpose**

A job is the concrete scheduler submission for a run.

**Required fields**

- run identifier
- scheduler identifier once known
- submission timestamp

**Optional fields**

- queue or partition
- scheduler-native state
- cancellation timestamp

**Immutable vs mutable fields**

- The job record identity is immutable.
- Scheduler-native status fields may change until terminal state.

**Creation trigger**

- Created when the execution adapter submits the run.

**Validation rules**

- Must reference exactly one run.

**Failure behavior**

- If scheduler acknowledgment is uncertain, the run must enter reconciliation or orphan handling.

**Persistence rules**

- Scheduler identity must be stored durably as soon as it is known.

---

## 3.10 Working Root

**Purpose**

The working root is the isolated filesystem workspace for one run.

**Required fields**

- root path
- association to one run
- generator identity or system-default marker

**Optional fields**

- exported copy of the input manifest
- exported provenance summary

**Immutable vs mutable fields**

- Path association is immutable.
- Contents evolve during execution and finalization.

**Creation trigger**

- Created during run preparation.

**Validation rules**

- Must be unique for the run.
- Must contain the required directory layout.
- Must be located under an allowed shared-storage root.

**Failure behavior**

- Partially created working roots must be recoverable, cleaned up, or classified as orphaned by restart reconciliation.

**Persistence rules**

- Path must be stored in the run record.

---

## 3.11 Task Output Descriptor (`task-out.yaml`)

**Purpose**

The task output descriptor declares downstream tasks produced by a completed algorithm execution.

**Required fields**

- list of downstream task declarations

**Optional fields**

- split-group metadata
- routing annotations
- aggregation hints

**Immutable vs mutable fields**

- Treated as immutable once read for finalization.

**Creation trigger**

- Written by the algorithm before completion.

**Validation rules**

- Must validate against the descriptor schema.
- Target stations must exist.
- Duplicate entries must be rejected or normalized by explicit policy.

**Failure behavior**

- Malformed descriptors must fail finalization unless explicit fallback policy is configured.

**Persistence rules**

- The file path and validated content summary should be recorded in the run.

---

## 3.12 Split Group

**Purpose**

A split group coordinates a fan-out/fan-in processing set derived from one parent window.

**Required fields**

- `group_id`
- parent task or parent run identifier
- parent time window
- aggregation target or stage
- readiness policy

**Optional fields**

- expected child count
- explicit child task set
- timeout policy
- partial-aggregation policy

**Immutable vs mutable fields**

- Identity and parent association are immutable.
- Membership and state may change until terminal state.

**Creation trigger**

- Created when a splitter run declares downstream fractional work or when the backend materializes an equivalent grouped workflow.

**Validation rules**

- Must define how readiness is determined.

**Failure behavior**

- If the system cannot determine readiness safely, aggregation must not start.

**Persistence rules**

- Must be stored durably and updated transactionally with child-task bookkeeping where practical.

---

## 3.13 Artifact

**Purpose**

An artifact is any persisted file associated with a run, including outputs, logs, the job order, the task output descriptor, and manifest exports.

**Required fields**

- artifact identifier
- producing run identifier or external origin reference
- logical artifact type
- path

**Optional fields**

- checksum
- size
- validation result
- content metadata
- rolling archive publication metadata

**Immutable vs mutable fields**

- Identity, producing run, and path are immutable.
- Validation metadata may be added during finalization.

**Creation trigger**

- Created when the file is first recorded by the backend.

**Validation rules**

- Path must remain within allowed storage policy.
- Mandatory output artifacts must satisfy station validation rules.

**Failure behavior**

- Missing mandatory artifacts must prevent the run from reaching `complete`.

**Persistence rules**

- Must be linked to the run that produced it.
- If copied or linked into a rolling archive, the publication target and mode must be recorded without changing the producing run identity.

---

## 3.14 Processing Fingerprint

**Purpose**

The processing fingerprint is the deduplication and canonicality key for a scientifically meaningful execution context.

**Required fields**

- station identity
- station revision identity
- processing window
- resolved input identities
- generator identities when custom generation affects execution context
- output-affecting runtime parameters

**Optional fields**

- checksums
- facility mode
- algorithm image digest
- job order schema version
- rolling archive source identifiers when archive selection can affect reproducibility

**Immutable vs mutable fields**

- Immutable once computed for a run.

**Creation trigger**

- Computed during run preparation before dispatch.

**Validation rules**

- Must include every context element that can change scientific outputs under deployment policy.

**Failure behavior**

- If the fingerprint cannot be computed, the run must not be dispatched.

**Persistence rules**

- Must be stored with the run and in the deduplication registry if the run becomes canonical and complete.

---

## 3.15 Deduplication Record

**Purpose**

The deduplication record identifies which completed run currently owns a canonical processing fingerprint.

**Required fields**

- processing fingerprint
- owning run identifier
- canonical status

**Optional fields**

- superseded-by reference
- promotion timestamp

**Immutable vs mutable fields**

- Fingerprint is immutable.
- Ownership metadata may change only through an explicit replacement or promotion operation.

**Creation trigger**

- Created when a run reaches canonical completion.

**Validation rules**

- Only one canonical owner may exist for a fingerprint at a time.

**Failure behavior**

- Conflicting ownership must fail transactionally and trigger operator-visible diagnostics.

**Persistence rules**

- Must be queryable independently of raw run records.

---

## 3.16 Facility

**Purpose**

Facility describes the operational context passed to the algorithm.

**Required fields**

- processing environment identifier

**Optional fields**

- acquisition station
- processing center
- test flag

**Immutable vs mutable fields**

- Immutable within a run.

**Creation trigger**

- Derived from deployment configuration during job order generation.

**Validation rules**

- Must satisfy the job order schema.

**Failure behavior**

- Invalid facility data must fail job order generation.

**Persistence rules**

- Must be recorded in the job order and therefore indirectly in the run context.

---

## 3.17 State Store

**Purpose**

The state store is the relational persistence layer for all durable control data.

**Required fields**

- N/A at the entity level; this is the persistence substrate

**Optional fields**

- N/A

**Immutable vs mutable fields**

- N/A

**Creation trigger**

- Provisioned as part of deployment.

**Validation rules**

- Must enforce referential integrity and uniqueness where required for idempotency.

**Failure behavior**

- Loss of write availability must block state transitions that require durable commit.

**Persistence rules**

- SQLite may be used for development; Postgres should be used for production.

---

## 3.18 Instance Configuration

**Purpose**

Instance configuration defines deployment-level settings that are shared by all stations and runs in one VeriProc installation.

**Required fields**

- instance identifier
- working root base path
- station configuration root or registry reference
- facility defaults

**Optional fields**

- rolling archive definitions
- custom working-root generator module
- custom job-order generator module
- executor defaults
- retention and cleanup policy defaults

**Immutable vs mutable fields**

- The effective instance configuration used by a run must be frozen by reference or content hash.
- Future instance configuration changes must not retroactively alter existing run semantics.

**Creation trigger**

- Created or loaded at backend startup and may be reloaded through a controlled deployment operation.

**Validation rules**

- Referenced paths must be allowed shared-storage paths.
- Rolling archive identifiers must be unique.
- Custom generator module references must resolve and satisfy the required interface before use.

**Failure behavior**

- Invalid instance configuration must block backend startup or block creation of runs that depend on the invalid portion.

**Persistence rules**

- The effective instance configuration identity should be recorded with runs when it can affect generation, storage layout, input selection, or publication behavior.

---

## 3.19 Generation Hook

**Purpose**

A generation hook is a deployment-provided module that overrides system-default working-root path generation or job-order generation.

**Required fields**

- hook type (`working_root` or `job_order`)
- module reference
- implementation version or content hash

**Optional fields**

- configuration payload
- timeout policy
- validation mode

**Immutable vs mutable fields**

- The hook identity used for a run is immutable once run preparation begins.

**Creation trigger**

- Declared in instance configuration.

**Validation rules**

- Must implement the required interface.
- Must be deterministic for the same validated inputs.
- Must not mutate backend state directly.
- Must preserve working-root containment and job-order schema validity.

**Failure behavior**

- Hook failure must fail run preparation before scheduler submission.
- A hook that returns invalid output must be treated as a preparation failure.

**Persistence rules**

- Hook identity must be recorded in run metadata or generated artifacts when it can affect execution context.

---

## 3.20 Rolling Archive

**Purpose**

A rolling archive is a named read-write directory used as operational short-term storage for input selection and optional publication of validated outputs.

**Required fields**

- archive identifier
- filesystem path
- retention period

**Optional fields**

- archive mode or publication permissions
- publication subdirectory policy
- checksum policy
- cleanup schedule
- allowed station list

**Immutable vs mutable fields**

- Archive identifier must be stable within an instance.
- Retention policy and path are deployment-managed and may change only through controlled configuration updates.

**Creation trigger**

- Declared in top-level instance configuration.

**Validation rules**

- Path must be visible to backend and compute nodes if used for symlinked input access.
- Station references such as `rolling:co2m_hot` must resolve to a declared archive.

**Failure behavior**

- Unavailable archives must fail input resolution if they are needed for mandatory inputs.
- Publication failure after successful job execution must keep the run in finalization or fail according to station policy; it must not silently create downstream tasks that depend on unpublished data.

**Persistence rules**

- Input manifest entries must record the archive identifier when a file is selected from a rolling archive.
- Publication records must record target archive, target path, publication mode, and source artifact.

---

## 3.21 Executor

**Purpose**

The executor is the adapter that translates runs into compute jobs.

**Required fields**

- N/A at the entity level; implementations must support submission and query

**Optional fields**

- cancellation support
- scheduler-native hints

**Immutable vs mutable fields**

- Adapter configuration is deployment-managed.

**Creation trigger**

- Provisioned as part of the backend.

**Validation rules**

- Must implement the required scheduler contract.

**Failure behavior**

- Submission uncertainty must be surfaced as reconciliation or orphan handling, not silently ignored.

**Persistence rules**

- Executor-specific ephemeral state should not be treated as the system of record.

---

## 3.22 Shared Storage

**Purpose**

Shared storage is the filesystem namespace accessible to both backend and compute nodes.

**Required fields**

- N/A at the entity level

**Optional fields**

- storage-class metadata

**Immutable vs mutable fields**

- Deployment-managed.

**Creation trigger**

- Provisioned as part of the environment.

**Validation rules**

- Must provide the consistency and path visibility required by the working-root contract.

**Failure behavior**

- Storage unavailability during preparation or finalization must fail the affected transition and be recoverable on restart.

**Persistence rules**

- Artifact bytes live here; control truth does not.

---

## 3.23 Glossary

| Term | Definition |
|---|---|
| Station | Declarative processing-step specification |
| Station revision | Frozen version of a station definition |
| Task | Immutable routing request for a processing window |
| Routing history | Readable append-only traversal log carried by tasks |
| Provenance link | Explicit graph edge between tasks, runs, or artifacts |
| Job order | Immutable execution descriptor consumed by the algorithm |
| Resolved input manifest | Frozen record of selected and missing inputs |
| Run | One execution attempt for one task |
| Job | Concrete scheduler submission for a run |
| Working root | Isolated filesystem workspace for one run |
| `task-out.yaml` | Optional descriptor declaring downstream tasks |
| Split group | Coordination record for fan-out/fan-in workflows |
| Artifact | Persisted file associated with a run |
| Processing fingerprint | Deduplication key for scientific execution context |
| Deduplication record | Canonical ownership record for a fingerprint |
| Facility | Operational context block passed to the algorithm |
| State store | Relational persistence layer for durable control state |
| Instance configuration | Deployment-level configuration for roots, archives, generators, and defaults |
| Generation hook | User-defined module overriding default working-root or job-order generation |
| Rolling archive | Named operational directory for input selection and optional output publication |
| Executor | Adapter that submits and tracks compute jobs |
| Shared storage | POSIX-visible filesystem for working roots and artifacts |
